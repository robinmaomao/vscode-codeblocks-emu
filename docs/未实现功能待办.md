## 1. A 组：调试器（vs `debuggergdb` 插件 + `*-dlg.cpp`）

> 原生已覆盖、不重复实现：Watches（Watch 面板）、Call stack（调用堆栈）、Threads（线程）、
> 断点列表（Breakpoints 面板）——分别对应 CB 的 `watchesdlg / backtracedlg / threadsdlg / breakpointsdlg`。

### A1 反汇编视图
- **状态**：✔ 已实施（0.8.76-dev）
- **CB 依据**：`src/src/disassemblydlg.cpp`
- **功能作用**：查看当前 PC 周围机器码，配合源码/符号显示，用于底层排错（无源码/优化代码）。
- **现状**：DAP 未实现 `disassemble` 请求 → VS Code 反汇编视图（含右键「打开反汇编视图」）不可用。
- **实现方式**：`gdbDebugAdapter.ts` 增加 `disassemble` 处理：声明 `supportsDisassembleRequest`；
  以请求的 `memoryReference` 为起点，优先 `-data-disassemble -s <start> -e <end> -- 1`（源码+汇编），
  条数不足按 `instructionCount` 预估步长重试；回填 `{address, instruction, symbol, location/line}`。
- **影响**：`gdbDebugAdapter.ts` / `gdbMiSession.ts` ≈120 行；新增返回解析纯函数+测试；风险中
  （指令长度估算、混合模式解析）。
- **建议**：⭐ 实施（价值高，嵌入式/优化场景刚需）。

### A2 内存查看（Examine memory）
- **状态**：✔ 已实施（0.8.76-dev）
- **CB 依据**：`src/src/examinememorydlg.cpp`
- **功能作用**：按地址查看/修改内存（十六进制/十进制/反汇编三种解释），排查指针/缓冲区问题。
- **现状**：无；VS Code Memory 视图依赖 DAP `readMemory`/`writeMemory`，未声明。
- **实现方式**：声明 `supportsReadMemoryRequest`/`supportsWriteMemoryRequest`；`readMemory` →
  `-data-read-memory-bytes <addr> <count>`；`writeMemory` → `-data-write-memory-bytes <addr> <hex>`；
  地址先用 `-data-evaluate-expression` 求值。另在 `variables` 响应为指针/数组回填 `memoryReference`
  （名称路径取 `-var-info-path-expression`，地址取 `&(path)`），使变量右键「查看二进制数据」可用。
- **影响**：≈110 行 + 测试；风险中（地址求值失败、越界保护）。
- **建议**：⭐ 实施。

### A3 CPU 寄存器视图
- **状态**：✔ 已实施（0.8.76-dev）
- **CB 依据**：`src/src/cpuregistersdlg.cpp`
- **功能作用**：查看/修改全部 CPU 寄存器（嵌入式常见），停驻即可读。
- **现状**：无；VS Code 无原生寄存器视图。
- **实现方式**：新增 Registers TreeView（`codeblocks.debug.registersView`，建议挂 `views.debug` 调试容器，与变量/监视并列）：
  启动后 `-data-list-register-names` 取名单，停止事件时 `-data-list-register-values x` 刷新；
  支持行内编辑写回 `-gdb-set $<name>=<value>`；命令 `codeblocks.debug.refreshRegisters`。
- **影响**：新视图 + 命令 ≈150 行 + 测试；风险中低。
- **建议**：⭐ 实施（无原生替代）。

### A4 数据断点（watchpoint）
- **状态**：✔ 已实施（0.8.76-dev）
- **CB 依据**：`src/src/databreakpointdlg.cpp`
- **功能作用**：变量被读/写时中断（watch/rwatch/awatch），排查「谁改了它」。
- **现状**：无；DAP `dataBreakpoints` 未声明。
- **实现方式**：声明 `supportsDataBreakpoints`；实现 `dataBreakpointInfo`（对变量返回 `dataId` =
  表达式+访问类型）与 `setDataBreakpoints`（`-break-watch/-break-rwatch/-break-awatch` →
  编号映射，删除走 `-break-delete`）。VS Code 变量右键「数据断点」、断点面板原生 UI 自动可用。
- **影响**：≈80 行 + 测试；风险低。
- **建议**：⭐ 实施。

### A5 指令级步进
- **状态**：✔ 已实施（0.8.76-dev）
- **CB 依据**：`debugger_menu.xrc`（Next/Step instruction）
- **功能作用**：按机器指令单步（配合反汇编排错）。
- **现状**：无。
- **实现方式**：声明 `supportsSteppingGranularity`；`next/stepIn` 收到 `granularity:'instruction'` 时

- **影响**：≈30 行；风险低；与 A1 配套。
- **建议**：⭐ 实施。

### A6 命中次数 / 日志断点
- **状态**：✔ 已实施（0.8.76-dev）
- **CB 依据**：`breakpointsdlg.cpp`（ignore count、条件）

## 2. B 组：编译器与构建设置

### B1 全局编译器设置编辑（Compilers settings）
- **状态**：✖ 评估后不做（2026-09-27 用户确认方案 A）
- **评估结论**：default.conf 为 Code::Blocks 本体私有配置（CB 退出/打开设置对话框时整文件覆写，写入竞态无法消除）；
  且程序路径已由「Detect Compilers → `compilerPrograms`」与 default.conf `user_sets` 读取双重覆盖，
  全局搜索目录/选项/库已被完整读取并注入构建；**收益 < 成本**。
- **替代**：命令 `codeblocks.openDefaultConfig`（Settings → Default Config…，打开 default.conf 手工编辑，
  保存后扩展读取立即生效、CB 本体需重启）+ 文档指引。若未来「从 VS Code 改全局配置」成为高频需求，仍可按下方方案后补（无架构损失）。
- **CB 依据**：`src/src/compilersettingsdlg.cpp`（+ `compilergcc/compileroptionsdlg.cpp` 全局层）
- **功能作用**：图形化维护编译器集：工具链程序、搜索目录（含库）、编译/链接选项、库列表、正则。
- **现状**：构建已全量读取 default.conf（搜索目录/选项/库/正则）；仅「Detect Compilers」写程序
  路径、`codeblocks.masterPath` 设置；**无编辑 UI**。
- **实现方式**：新 Webview 面板（仿项目 Build Options）：左侧编译器集下拉（来自 `options_*.xml`），
  右侧分组「程序路径 / 搜索目录 / 编译选项 / 链接库」（正则只读）；写回
  `default.conf /compiler_sets/<id>`——沿用 keybindings 的**条目级文本手术**（保留其它节点/注释，
  首次备份 `default.conf.codeblocks-backup`，回读校验失败回滚），写后失效扩展缓存；
  面板顶部提示「Code::Blocks 本体需重启后生效」。
- **影响**：新面板 + `codeblocksConfigWriter.ts` ≈450 行 + 往返测试；风险中（写第三方配置文件）。
- **建议**：✖ 不做（2026-09-27 评估 A；如未来高频需求出现再按上述方案后补）。
