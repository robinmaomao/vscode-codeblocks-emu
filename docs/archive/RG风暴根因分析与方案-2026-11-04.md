# RG 风暴根因分析与修复方案

> 状态：**R0 验证已完成**（根因确认为路径 glob 元字符，见 §16），**待确认实施**（未修改扩展代码）
> 适用版本：0.8.135；计划版本：0.8.136
> 分析日期：2026-11-04（第二轮：同日上午，见 §14；第三轮：同日下午，见 §15）
> 现场环境：Windows 10 x64 / VS Code 1.144.1 / 8 逻辑核 / E: 机械盘 / 工程路径含 `[内部]`
> 现象：同一份 `.cbp`，在路径 A 构建时 CPU 100%、出现 100+ 个 `rg.exe` 与 `conhost.exe`；在路径 B 构建正常。

---

## 1. 结论摘要

> **第二轮更新（2026-11-04 上午）**：用户补充了新现象——工作区打开 SDK 工程后，**在 `E:\Work_Share\2026\10` 下增删文件会触发风暴，在 `E:\Work_Share\2026` 和 `E:\Work_Share\2026\11` 下不会**。经调试器取证，搜索范围与调用链已精确定位：
>
> - 每次风暴都是 VS Code 的 **ripgrep 文件搜索**（`FileSearchEngine.cmdTraversal` → `spawnRipgrep`），命令行为 `--files ... --no-config`，**不带任何 `-g` 包含/排除参数**，等于整棵树枚举；
> - 该搜索的**基准目录是 `E:\Work_Share\2026\10`**（不是工作区目录），文件模式是 `<工程相对路径>/.github/instructions` 与 `<工程相对路径>/.claude/rules`；
> - 它由 **VS Code 的 AI 指令文件发现（AI customization：`.github/instructions`、`.claude/rules`）** 发起，并且**由文件变更触发**：静置 30 s 内 `rg` 唯一进程数为 0，写入 10 个文件后 25 s 内命中 12 次搜索请求（`rg` 唯一进程 19、并发峰值 9）。因此 `2026\10` 及其子目录的任何增删都会触发，兄弟目录 `2026\11`、`2026\test` 不会；
> - 因为 `shouldGlobMatchFilePattern=true`（模式在 JS 侧匹配），ripgrep 拿不到任何过滤参数 → 每次都要枚举 `2026\10` 下 **4620 个文件**，叠加并发后即上百个 `rg.exe` + `conhost.exe`。详见 **§14**。

**根因不在 `.cbp`、编译器或 Code::Blocks 扩展本身。** 第一轮的取证结论（下文 §3）指出坏窗口的 Copilot CLI Agent 会话把搜索根设在父目录 `E:\Work_Share\2026\10`；第二轮进一步把"谁在扫、扫什么、为什么扫"落到具体代码路径（§14），并修正了第一轮"仅靠 Copilot 索引设置即可解决"的推断。

**关键结论：**

1. `files.watcherExclude` / `search.exclude` 只影响 VS Code 核心的文件监视/搜索，**不能阻止 Copilot 的 `findFiles('**/*')` / CLI Agent 枚举**。实测写入已排除的 `Output/obj` 仍产生 23 个 `rg`。
2. 工作区级 3 项 Copilot 索引设置（`localIndex` / `enableCodeSearch` / `codeSearchExternalIngest`）是有效的官方键，但**单独使用不足以阻止 CLI Agent**；关闭 Chat 面板只是隐藏 UI，不等同于结束会话。
3. 好路径的父目录 `test_sdks` 也有 4221 个文件，但好窗口没有 CLI Agent 会话，`rg` 为 0——**路径大小不是决定因素，会话/窗口状态才是**。
4. 推荐先做 **A（操作层止血）**，再做 **B（0.8.136 构建守卫）**；**C（输出外移）**改动大、风险高，作为后续可选。

## 4. 根因链

```text
构建写入 56 个对象文件（Output/obj）
        │
        ▼
VS Code / Copilot 收到文件创建事件
        │
        ▼
Copilot CLI Agent（agent-host-copilotcli）重新枚举其搜索根
        │
        ├─ 搜索根 = E:\Work_Share\2026\10（工程父目录，4048 文件）
        ├─ 执行 rg --files ... --no-config（无 -g 排除）
        └─ 每次刷新派生 rg.exe + conhost.exe
        │
        ▼
多个 CLI 会话 + 多个重复 VS Code 窗口
        │
        ▼
上百个短命 rg.exe / conhost.exe → CPU 100%、VS Code 进程组暴增、扩展宿主卡顿
```

关键点：

1. **触发源**是构建写文件；**放大器**是 Copilot CLI Agent 的全树枚举；**乘数**是 3 个 CLI 会话 + 多个窗口。
2. `watcherExclude` / `search.exclude` 对 Copilot 的 `findFiles` 不生效；实测已排除目录仍触发 23 个 `rg`。
3. 3 项 Copilot 设置只覆盖普通 workspace index，不覆盖 `agent-host-copilotcli` 会话；Reload 后仍可复现 9/14。
4. Chat 面板隐藏（`isHidden: true`）不影响后台 CLI 会话；关闭面板不是可靠修复。

## 5. 为什么同一份 `.cbp` 换路径就正常

| 因素 | 坏路径 | 好路径 |
|---|---|---|
| `.cbp` / 源码 | 相同 | 相同 |
| 父目录文件数 | 4048 | 4221（更大） |
| 工作区文件数 | 315 | 316 |
| Chat 会话数 | 5 | 1 |
| CLI Agent 会话 | **3** | 0 |
| 当前 Chat 模型 | `agent-host-copilotcli:...` | 普通 `deepseek/deepseek-v4-flash` |
| 重复窗口 | 多个（含 junction） | 单个 |

## 6. 方案 A：操作层规避（零代码）

### 6.1 目标

不修改扩展、不修改 `.cbp`，通过结束/切换 Copilot CLI Agent 会话、关闭重复窗口，立即消除构建期 `rg` 风暴。

### 6.2 步骤

1. **停止当前 Chat 请求**
   - 打开 Chat（`Ctrl+Alt+I`），如有停止按钮先点停止；
   - 或命令面板执行 `Chat: Cancel`（`workbench.action.chat.cancel`）。

2. **切换 Chat 模型**
   - 坏窗口当前模型是 `agent-host-copilotcli:customendpoint/...`；
   - 在 Chat 底部模型选择器中改选普通模型，例如 `DeepSeek V4 Flash`（`deepseek/deepseek-v4-flash`）；
   - 不要选择任何带 `agent-host-copilotcli` 前缀的条目。

3. **删除 3 个 CLI 会话**
   - 在 Chat 会话列表中找到 `agent-host-copilotcli` 的会话（当前均为空会话）；
   - 逐个删除；若当前版本无单条删除，使用 Chat `...` 菜单清空该工作区历史（当前 5 个都是空会话，影响小）。

4. **关闭重复窗口**
   - 只保留一个 SDK 窗口；
   - 关闭 `cbbad`、`cbgood`、重复的 `SDK... - VSCode` 窗口；
   - 不要把 `E:\Work_Share\2026\10` 作为工作区打开，也不要在该目录启动 Chat/CLI。

5. **可选工作区设置**
   在项目 `.vscode/settings.json` 写入：

   ```json
   {
     "github.copilot.chat.localIndex.enabled": false,
     "github.copilot.chat.workspace.enableCodeSearch": false,
     "github.copilot.chat.workspace.codeSearchExternalIngest.enabled": false
   }
   ```

   这 3 项是官方键，但**单独使用不能阻止 CLI Agent**，只作为辅助。

6. **Reload 并验证**
   - `Developer: Reload Window`；
   - 确认空闲时 `rg.exe` 为 0；
   - 向父目录连续写 10 个文件，`rg` 峰值应 ≤2；
   - 再执行完整构建，记录构建时间与 `rg` 峰值。

### 6.3 影响

| 项目 | 影响 |
|---|---|
| 扩展代码 | 无改动 |
| 工程源码 / `.cbp` | 无改动 |
| 新增文件 | 可选 `.vscode/settings.json` |
| Chat 功能 | 该工作区不再使用 CLI Agent；普通 Copilot Chat 仍可用 |
| Chat 历史 | 删除 3 个空 CLI 会话；如用“清空历史”会清空该工作区全部 Chat 历史 |
| 构建 / 调试 | 完全不变 |
| 回滚 | 重新选择 CLI 模型 / 重新打开会话；删除 `.vscode/settings.json` |
| 持久性 | 低：再次选择 CLI 模型、恢复会话或打开父目录窗口后可能复发 |

### 6.4 风险与局限

- 依赖用户操作，扩展无法保证。
- 若根因是普通 Copilot Chat 的 workspace index 而非 CLI 会话，A 之后仍需加 3 项设置，或临时禁用 `GitHub.copilot-chat`（Workspace）。
- 删除会话前确认没有真实对话内容；当前坏工作区 5 个会话均为空，风险低。

### 6.5 验收标准

- 父目录连续写 10 个文件：`rg` 峰值 ≤2（理想 0）。
- 完整重建约 14s；扩展宿主停顿 ≤10%；VS Code 组 CPU ≤15%。
- 若仍 >5，追加“禁用 Copilot Chat (Workspace)”再测。

### 6.6 工作量

5–10 分钟；无测试、无发布。

## 7. 方案 B：0.8.136 内置“索引风暴守卫”（推荐）

### 7.1 目标与非目标

**目标：**

- 构建时自动发现 `rg` / `conhost` 风暴；
- 给出可定位证据（峰值、命令行、工作区/父目录、Copilot 设置状态）；
- 提供一键引导修复：写工作区 Copilot 设置、打开扩展页、打开模型选择器、Reload；
- 不强行杀进程、不修改 `.cbp`、不影响构建结果。

**非目标：**

- 不自动禁用其他扩展（VS Code API 不提供该能力）；
- 不自动结束 Copilot 会话（无公开 API）；
- 不替代用户确认。

### 7.2 新增设置与命令

**设置：**

```json
"codeblocks.build.indexerGuard": {
  "type": "string",
  "enum": ["off", "prompt", "auto"],
  "default": "prompt",
  "description": "构建时检测 Copilot/扩展的全工作区 rg 风暴；prompt=只提示，auto=自动写入工作区 Copilot 设置并打开修复页面"
}
```

可选：

```json
"codeblocks.build.indexerGuardThreshold": {
  "type": "number",
  "default": 10,
  "description": "rg.exe 峰值达到该值时判定为风暴"
}
```

**命令：**

- `Code::Blocks: 诊断工作区索引`（`codeblocks.diagnoseWorkspaceIndex`）
- `Code::Blocks: 修复工作区索引`（`codeblocks.fixWorkspaceIndex`）

**警告动作：**

- `停止当前 Chat 请求` → `workbench.action.chat.cancel`
- `切换 Chat 模型` → `workbench.action.chat.changeModel`
- `打开 Copilot Chat 扩展页` → `workbench.extensions.search`，参数 `@id:GitHub.copilot-chat`
- `写入工作区设置`（auto 模式或用户点击）
- `Reload Window`
- `不再提示`（写 `indexerGuard=off`，工作区级）

> **限制：** VS Code 扩展 API 不能直接禁用另一个扩展。所谓“一键修复”是“写设置 + 打开扩展页 + 打开模型选择器”，最后一步 `Disable (Workspace)` 仍需用户点击；文案必须写清楚，不能承诺全自动禁用。

### 7.3 检测实现

**采样：**

- 复用 [systemSampler.ts](../../src/build/systemSampler.ts) 的 `SAMPLE_SCRIPT`。
- 当前脚本只输出 CPU 毫秒，无法知道 `rg` 峰值数量；需扩展协议：
  - 新增一行 `C;<elapsedMs>;rg=<count>;conhost=<count>;copilot-runtime=<count>`；
  - `SystemSample` 增加 `counts: Map<string, number>`；
  - `aggregateSamples` 增加 `peak: { rg, conhost, copilotRuntime }`；
  - 更新 [test-system-sampler.js](../../tests/test-system-sampler.js) 的解析/聚合用例。
- 采样周期保持 1s；`Get-Process -Name rg,conhost,copilot-runtime` 计数开销很小。
- `indexerGuard != off` 时，即使 `build.sampleSystem=false` 也启动采样；非 Windows 直接 no-op。

**判定：**

满足任一条件即警告：

- `rgPeak >= 10`；
- `scannerPct >= 8`（沿用现有 `reportWatcherStorm` 阈值）；
- `copilotRuntimeCount > 0 && rgPeak >= 3`。

再加“构建确实写了文件”的门控：`compiledCount >= 5`，避免空构建误报。

**证据内容：**

- `rg` / `conhost` / `copilot-runtime` 峰值；
- `scanner` CPU 占比；
- 本次编译单元数、构建耗时；
- `rg` 命令行（`--files --hidden ... --no-config`，无 `-g`）；
- 工作区根、公共父目录、父目录文件数；
- 当前 3 项 Copilot 设置的工作区/全局有效值；
- 提示：“搜索根通常是工作区或其父目录；CLI Agent 可能把根设在父目录”。

> 生产代码精确读取 `rg` 的 cwd 需要读 PEB，成本高；B 不强行取 cwd，只报告命令行 + 工作区/父目录，并明确“无 `-g` 即全树枚举”。诊断命令可保留现有 3 秒 `rg` 峰值采样。

**去重：**

- 每个工作区、每次构建最多一条警告；
- 用 `context.workspaceState` 记录 `lastWarnedBuildId` / `lastWarnedAt`；
- 用户点“不再提示”写 `codeblocks.build.indexerGuard=off`（工作区级）。

### 14.2 抓到的真实命令与 cwd

### 14.3 这次搜索到底在找什么

在 `cmdTraversal` 入口下断点，读取 `this.config`（一次 25 s 采样，含 10 文件写入）：

25 s 内共 12 次请求，全部同基准目录，只有两种模式，各 6 次：

|---:|---|---|

### 14.4 调用链：来自工作台（renderer）的委托，不是扩展 API

```text
_doInvokeHandler → _invokeHandler → _receiveRequest → _receiveOneMessage → ...
```

说明：

- `$provideFileSearchResults` 是**工作台进程调用扩展宿主**的 RPC 方法；`e === this._internalFileSearchHandle` 分支走 `doInternalFileSearch`，即"由扩展宿主内置 ripgrep 执行"。
- 在 `_findFilesImpl`（`vscode.workspace.findFiles` / `findFiles2` 的唯一入口）下断点，**在 `rg` 风暴期间一次都没有命中** → 排除"某个扩展调用 `workspace.findFiles`"。
- 进一步印证：`files.watcherExclude` / `search.exclude` 也帮不上忙——这次搜索根本没有 exclude 参数，而且基准目录在**工作区之外**，工作区的相对 glob 本来就套不上。

### 14.5 是"文件变更"触发，不是定时轮询

| 条件 | 观测 |
|---|---|
| 静置 30 s（无任何写入，200 ms 采样） | `rg` 唯一进程数 **0**、峰值 **0** |
| 在 `2026\10` 写 10 个文件 | 25 s 内断点命中 **12 次**搜索请求；`rg` 唯一进程 19、并发峰值 9 |

→ 变更触发。数量≈每处理一批变更就重新逐项确认一次"指令目录是否存在"，每个 `.github/instructions` / `.claude/rules` 各一次，于是每次构建写 56 个对象文件就叠出上百次全树枚举。

### 14.6 修订后的根因表述

> **直接烧 CPU 的进程**：VS Code 内置 ripgrep 文件搜索（每次派生 `rg.exe` + 一个 `conhost.exe`）。
> **发起者**：VS Code 工作台侧的 **AI 指令/规则文件发现（AI customization：`.github/instructions`、`.claude/rules`）**，属于 Copilot Chat / Agent 链路的上下文收集。
> **放大条件**：该搜索的**基准目录被设成了 `E:\Work_Share\2026\10`**（工程父目录，4620 个文件），而不是 315 个文件的工程目录；并且 `shouldGlobMatchFilePattern` 让 ripgrep 无任何过滤参数，等于每次全量枚举。
> **触发者**：`2026\10` 及其子孙目录内的任何文件增删（构建写对象文件即典型来源）。

因此：

- 第一轮的"Copilot CLI Agent 会话"判断**方向正确**：是会话/Agent 这条链路把搜索根定在了父目录 `2026\10`（工作区级 Chat 状态也印证：坏窗口 3 个 `agent-host-copilotcli` 会话、当前模型为 CLI 模型）。
- 但更准确的表述是：**具体烈度由"AI 指令文件发现"这个常驻功能决定，它的作用域跟着会话根走**。所以"只关 Chat 面板"无效（会话仍在）、"只加 `watcherExclude`"无效（不是同一条链路）、"只改 3 项索引设置"也不够（不一定覆盖 customization 发现）。

### 14.7 由此修订的建议

**立刻可做（不需要改扩展代码）**

1. **让搜索基准目录变小**：把工程放到"独占父目录"下（例如 `E:\SDKs\<工程名>`，父目录里只有这一个工程）；或把 `2026\10` 里不再用的历史工程打包移走，把该目录文件数从 4620 降到数百量级。这一条与"换到 `test_sdks` 就正常"的现象一致——差别不在工程内容，而在**父目录规模**与**会话根指向**。
2. **让 AI 上下文功能在该工作区停用**：`Disable (Workspace)` 对 `GitHub.copilot-chat`，或对当前会话切换为非 CLI 模型并删除 `agent-host-copilotcli` 会话；随后 Reload。验收标准仍是"写 10 个文件，`rg` 峰值 ≤2"。
3. **不要在 `2026\10` 这一层打开 / 挂载任何 AI 会话**，也不要在该层做"复制整份工程"这类批量写入；如必须，先停用 Chat。

**0.8.136 扩展侧（方案 B 修订点）**

- 现有 `systemSampler` 已能统计 `rg` / `conhost` 的 CPU 与峰值；建议把告警文案从"加 `watcherExclude` 就好"改为**"检测到 IDE 侧全量文件枚举"**，并给出可操作的三件事：
  1) 报告工作区**父目录**文件数（超过阈值明确提示"父目录太大，AI 索引会整树枚举"）；
  2) 提示检查 Copilot Chat/Agent 会话的根目录与模型（CLI 模型 / 父目录会话是高风险组合）；
  3) 一键打开 `Code::Blocks: 诊断工作区索引`，引导禁用工作区级 Copilot Chat 后 Reload。
- **不要**再承诺"写 `files.watcherExclude` 即可解决"（§7.5 与 `watcherExclude.ts` 顶部注释中的旧结论需一并修正）。

**方案 C（输出外移）的价值提升**

既然枚举根是工程父目录、且与工作区无关，那么"把对象/产物移出工作区"只能减少触发频率（少一批写入事件），**不能改变枚举范围**。因此 C 的优先级应下降；真正有效的是"缩小基准目录"或"停用该 AI 发现链路"。

### 15.1 先把"已实测无效"的手段划掉

| 手段 | 实测结果 | 原因 |
|---|---|---|
| `files.watcherExclude` / `search.exclude` 加 `Output/obj`、`Output/bin` | 写入已排除目录仍产生 23 个 `rg` | 搜索请求**没有任何 exclude 参数**，且基准目录在工作区之外 |

结论：**能动的只有"作用域"和"路径形状"，不是"排除规则"。**

### 15.2 三个残余根因候选（按可验证性排序）

| 候选 | 依据 | 若成立的根治手段 |
|---|---|---|
| **P1 路径含 glob 元字符 `[` `]`** | 搜索基址恰好是**第一个 `[` 之前的前缀**（`...\2026\10`），文件模式恰好从 `[内部]` 开始；同机无方括号路径的仓库窗口在写入时 **0 次**探测 | 把父目录里的 `[...]` 改成 `(...)`/`_`，**零构建风险** |

### 16.3 机制（已闭环）

```js
// workbench.desktop.main.js
function xgn(s){ /* 段内含 * ? 或成对 [ ] / { } → true */ }
function Eao(type, uri){
  if (type !== "instructions" && type !== "prompt") return { searchRoot: uri };
  const seg = uri.path.split("/");
  let t = 0;
  while (t < seg.length && xgn(seg[t]) === false) t++;   // 找到第一个"含 glob 元字符"的路径段
  if (t === seg.length) return { searchRoot: uri };       // 无元字符 → 整条路径就是搜索根（只 stat）
  const root = uri.with({ path: seg.slice(0, t).join("/") });
  return { searchRoot: root, filePattern: seg.slice(t).join("/") };  // 否则退化为"前缀目录 + glob"
}
```

- `[内部]5756C_lvd_reset` 含成对 `[ ]` ⇒ `xgn` 返回 true ⇒ 搜索根被**截断到 `2026\10`**，其余部分变成 glob。
- 由于该 glob 在 JS 侧匹配（`shouldGlobMatchFilePattern`），ripgrep **拿不到任何 `-g`**，只能把 `2026\10` 整棵树（当前 2499 个文件）列一遍。
- 因为搜索根 `2026\10` **不在工作区内**，`getWorkspaceFolder(root)` 为空 ⇒ 连 `excludePattern` 都没有 ⇒ 任何排除设置都无效。
- 每次"指令位置刷新"（文件变更触发）会对 `.github/instructions` 与 `.claude/rules` 各跑一次 ⇒ 一次构建写 N 个文件就叠出 N×2 次全树枚举，`rg` + `conhost` 成百上千。

### 16.4 两个已验证的根治方案

| 方案 | 做法 | 实测效果 | 代价 |
|---|---|---|---|
| **F1 路径去元字符（首选）** | 把父目录 `[内部]5756C_lvd_reset` 改名为不含 `[ ] { } * ?` 的名字（如 `(内部)5756C_lvd_reset` 或 `内部_5756C_lvd_reset`） | `Eao` 返回完整 instructions 路径、**无 filePattern** ⇒ **不再启动 rg**（代码级已证） | 仅改目录名；`.cbp` 内是相对路径，构建/调试不受影响；**指令文件发现仍可用** |
| **F2 关闭这两个定制目录的扫描（兼容/立即可用）** | 工作区 `.vscode/settings.json`：`"chat.instructionsFilesLocations": { ".github/instructions": false, ".claude/rules": false }` | **实测（无需 Reload）：`rg` 唯一 0、峰值 0** | `.github/instructions` / `.claude/rules` 的**指令自动发现被关闭**（本工程无这两个目录，当前无损失）；Copilot Chat 其余功能不受影响 |

> 重要修正：**`chat.instructionsFilesLocations: {}` 是无效写法**——`promptSourceFolders()` 的实现是"以默认列表为基线，只有显式 `false` 才剔除"。这正是第二轮"设为 `{}` + Reload 仍复现"的原因；必须写 **显式 `false`**。

### 16.5 结论与建议

1. **根因确认**：工程路径中的 `[ ]` 被 VS Code `PromptFilesLocator` 当作 glob，导致 AI 指令发现把搜索根从工程目录**放大到祖父目录** `E:\Work_Share\2026\10`，每次文件变更都做一次无过滤的全树 `rg --files`。
2. **最小根治**：**F1 改名**（推荐，功能零损失）；**F2 设置**可作为不改路径时的等价方案（30 秒生效）。
3. **扩展侧仍建议做**（防复发 + 可诊断）：`Code::Blocks: 检查工程路径`（检测 `[ ] { } * ?`、父目录文件数、给出一键建议）+ `codeblocks.build.indexerGuard`（构建期 `rg` 峰值告警，默认 `prompt`），并修正 `reportWatcherStorm` / `watcherExclude.ts` 中"加 watcherExclude 即可"的过时结论。
4. **上游反馈**：可直接引用 `Eao` 的实现与 §16.2 的对照表——"路径段含 glob 元字符时，指令发现的搜索根会被放大到祖先目录，且不带任何过滤参数，导致整树枚举"。
