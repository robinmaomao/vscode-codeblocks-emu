# 测试方案（Code::Blocks for VS Code）

> 面向本仓库的**分层自动化测试方案**：契约 → 无头单元 → 真实工程 E2E → 像素视觉 → 性能 → 打包 → 真实宿主。
> 运行环境、门禁阈值与产物约定见下；覆盖台账见 [测试覆盖矩阵](./测试覆盖矩阵.md)，性能数据见 [性能基准](./性能基准.md)。

## 1. 分层结构

| 层 | 目录 | 内容 | 运行方式 |
|----|------|------|----------|
| L-1 静态契约 | `tests/contract/` | 贡献点/激活事件/命令注册交叉校验、语言语法、调试器 schema、资源与版本一致性、NLS 键集合、**文档一致性**（覆盖矩阵汇总/性能基准条目/文档命令与相对链接/版本标记） | `npm run test:contract` |
| L0 无头单元/集成 | `tests/test-*.js` | 解析/写回/命令行/宏/缓存/键位/书签/工具等 135+ 项（dist 层，无 VS Code 宿主） | `npm test` |
| L1 真实工程 E2E | `tests/e2e/` | 真实工具链构建矩阵、工作区依赖、工具类功能（临时目录探针工程） | `npm run test:e2e` |
| L2 真实宿主 | `tests/host/` | 用 `@vscode/test-electron` 启动**真实 VS Code**（默认下载 `engines.vscode` 最低版本 1.85.0，可用 `CB_VSCODE_PATH` 指向本机安装）驱动真实命令/视图/调试/设置写入 | `npm run test:host` |
| L3 像素视觉回归 | `tests/visual/` | 12 个 WebView HTML 面 × 2 主题 = 24 基线；pixelmatch 容差判定 | `npm run test:visual` |
| L4 性能基准 | `tests/perf/` | 12 项微基准 + 真实构建耗时；硬预算 fail / 漂移 warn | `npm run test:perf` |
| L5 打包与安装 | `tests/pack/` | VSIX 打包内容核对 + 隔离 user-data-dir 安装激活冒烟 | `npm run test:pack` |
| L6 手工验收 | [手工验收清单](./手工验收清单.md) | 拖拽排序、悬停菜单、原生 UI 截图留档等不可自动化项 | 人工 |
| CI | `.github/workflows/ci.yml` | windows-latest：契约 + 无头 + 打包冒烟必跑；E2E 按工具链门控；视觉/性能/宿主为手动可选作业（另有每周定时巡检）；npm 与 `.vscode-test` 缓存；覆盖矩阵汇总写入 job summary | GitHub Actions |

一键串联：

```powershell
npm run test:all          # contract + unit + e2e + visual + perf + pack（不含 host）
npm run test:all:host     # 追加真实宿主集成（需 GUI 会话）
```

## 2. 统一运行器

`tests/run-all.js` 支持分组、筛选与 JSON 报告：

```powershell
node tests/run-all.js --group unit                # 默认（等价 npm test，仍写 .cbtest.txt）
node tests/run-all.js --group visual --filter props   # 只跑工程属性面板相关面（visual 层按「面 id」筛选）
node tests/run-all.js --group all --json out.json
```

- `--filter` 按**脚本名**筛选（子串）；**visual 层例外**：其 `--filter` 透传为 `--only=<子串>`（面 id 筛选）。
- **筛选未命中任何脚本 → 报错退出（exit 2）**，不再静默全绿（视觉面筛不到时也会由脚本自身报「未匹配任何面」并 exit 1）。

- 每层独立退出码；`all` 中任一层失败即整体失败。
- 缺失的层（尚未创建脚本）→ `(无脚本) SKIP`，不计失败。
- 结果 JSON 默认落 `.cb-tools/report-<group>.json`（临时目录，不入库）。

## 3. 视觉回归（L3）

- **范围**：仅 WebView HTML 面（原生 VS Code UI 不做像素门禁，改由宿主测试截图留档 + 手工清单覆盖）。
- **面清单**：工程属性面板 9 个 tab（构建目标/虚拟目标/文件/构建选项/搜索目录/构建脚本/项目设置/备注/调试器）、快捷键面板、编译选项面板、HTML 构建日志 —— 共 12 面 × dark/light 两主题。
- **HTML 来源**：dist 真实代码生成（`ProjectPropertiesPanel.buildHtml()` 等），不维护手写快照。
- **确定性措施**：固定视口与 DPR=1；注入 `--vscode-*` 主题变量与固定字体栈；HTML 头部注入时间/随机冻结与 `acquireVsCodeApi` shim；禁用动画/过渡/光标、隐藏滚动条；等待字体与双 rAF 后截图。
- **判定（两层，默认未被放宽）**：
  - **同环境（严格）**：`pixelmatch threshold=0.1` 且差异像素占比 **≤ 0.5%**——当前渲染指纹与入库基线指纹一致时生效。
  - **跨环境（容差）**：`threshold=0.2` 且 **≤ 2%**——指纹不一致（OS/浏览器主版本/DPI/字体度量哈希任一不同）时自动降级，**逐条标注 `OK(P)` 并打印提示**；超容差仍失败，且失败信息区分「跨环境容差仍超限 → 疑似真实界面变化」与「同环境严格判定失败 → 界面变化或本机渲染漂移」。**不存在静默放宽**。
- **基线**：`tests/visual/baselines/<theme>/<surface>.png`（入库，PR 可评审）+ `tests/visual/baselines/.fingerprint.json`（入库基线的渲染环境元数据：OS / 浏览器通道与主版本 / DPI / 字体度量哈希）。
- **刷新基线**：`npm run visual:baseline`（或 `node tests/visual/test-visual.js --update`）——指纹**匹配**时写入库基线并刷新元数据；指纹**不匹配**时写入 `.cb-tools/visual/<指纹>/`（本机自校准，**不触碰入库基线**），需 `--canonical` 才改入库目录。
- **失败产物**：`.cb-tools/visual-diff/<指纹>/<theme>/<surface>.{expected,actual,diff}.png`。
- **浏览器**：默认系统 Edge（`CB_VISUAL_BROWSER=msedge`）；如需 Chromium 固定版本：`npx playwright install chromium` 并设 `CB_VISUAL_BROWSER=chromium`。
- **相关开关**：`--fingerprint`（打印当前/基线/目录指纹后退出）、`--portable`（强制容差判定，跨环境筛查）、`--only <面 id 子串>`、`--theme dark|light`、`--canonical`、`--record-fingerprint`。
- **跨机假失败量化**（`node tests/visual/probe-portability.js`，对照 0px）：DPI/缩放 1.25 → 尺寸即 1280×800→1600×1000（回缩后仍差 **10.1–12.2%**）；字体集不同 → **8.7–14.3%**；关闭 LCD 文本渲染 → 0.43–0.62%（其中 `compiler-options` 0.618% **本机即已超严格上限**）。跨机复现：在另一台机器执行 `--fingerprint` 比对指纹，再默认跑一次看是否走容差分支。

## 4. 性能基准（L4）

- **口径**：warmup 后取 N 次采样，报告 median / p95 / min；单线程串行执行（真实构建类基准独占）。
- **判定**（双阈值）：**预算门禁用 `min`**（最小采样 → 抗机器负载尖峰）`min > 预算` → **失败**；`median > 1.8 × 基线` → **告警（不失败）**；首次超预算会自动**复核一次**，复核通过降级为告警。
- **预算来源**：首次基线固化时自动取 `max(3×median, 下限)`，可在 [tests/perf/baseline.json](../tests/perf/baseline.json) 人工调整后提交。
- **基准清单**：大工程解析（1200 文件/6 目标）、解析缓存命中、序列化往返、编译命令行生成+宏展开（1200 文件）、输出解析→诊断（2 万行/2000 条）、选项 XML 加载、LRU+盘符归一化、虚拟文件夹索引、增量判定 `isUpToDate`、真实全量构建、真实增量 up-to-date、真实单文件编译。
- **产物**：报告 [性能基准.md](./性能基准.md)（生成，含「趋势」小节）；原始结果 `.cb-tools/perf/perf-<时间戳>.json`。
- **趋势记录与漂移对比**（`--trend`）：每次运行把结果追加到 `.cb-tools/perf-history.jsonl`（本机历史，gitignored——跨机历史无比较价值，入库结论以报告「趋势」小节沉淀），逐项给出「较上次 / 较最近 N 次中位数 / 较基线」相对变化；`median` 较参照**恶化 > 阈值（默认 25% 且 +3ms）** 时打印 `⚠️ 趋势告警`，**不影响退出码**（硬门禁仍只看 `min ≤ 预算`）。开关：`--trend` / `--no-history` / `--trend-window N` / `--trend-threshold 0.25` / `--trend-min-abs 3` / `--history-file <path>`。
- **趋势读法与噪声**（实测 5 次样本）：小基准的 `min`/`median` 都会随负载大幅波动（如 B6 min 摆动 61%、median 225%；B1 min 77%），故告警需配合 `--trend-min-abs` 绝对下限；**排查回归应优先看「较最近 N 次中位数」列并尽量在静默机器上复跑**，单次「较上次」用于快速提示。相关单元自测：`node tests/test-perf-trend.js`（38 断言，覆盖阈值边界/绝对下限/窗口中位数/跨机排除/坏行/裁剪）。
- **刷新基线**：`npm run perf:baseline`。
- **环境前置**：B7–B10 需要 `gcc` 在 PATH；缺失时自动跳过并记录。

### 5.0 工具链安装（W6，可选）

工具链测试层会自动在 **PATH → `CB_TOOLCHAIN_ROOT`（分号分隔多根）→ `<repo>/.cb-tools/toolchains/**/bin`** 中探测，
因此无需改动系统 PATH：解包到 `.cb-tools/toolchains/<name>/`（已 gitignore）即可被识别。

| 工具链 | 下载 | 覆盖场景 | 本机状态 |
|--------|------|----------|----------|
| LLVM/clang | `llvm/llvm-project` releases → `clang+llvm-*-x86_64-pc-windows-msvc.tar.zst` | clang 构建+运行（`--target=x86_64-w64-mingw32` 复用 MinGW 运行时）、`--target=riscv64-unknown-elf` 交叉 | ✅ 23.1.3（riscv 后端可用；官方构建**未含** avr/msp430 后端） |
| AVR GCC | `ZakKemble/avr-gcc-build` releases → `avr-gcc-*-x64-windows.zip` | AVR 交叉编译（`-mmcu=atmega328p`，ELF `e_machine=83`） | ✅ 16.1.0 |
| RISC-V GCC | `xpack-dev-tools/riscv-none-elf-gcc-xpack` releases → `*-win32-x64.zip` | RISC-V 交叉编译（ELF `e_machine=243`） | ✅ 15.2.0 |
| MSP430 GCC | TI MSP430 GCC（需交互下载，未纳入自动安装） | 未装时 SKIP | ❌ 未安装 |
| SDCC | SourceForge（稳定版仅 `*-setup.exe` 安装器；nightly 快照有 ~38MB zip） | MCS51 交叉编译 | ❌ 未安装（已评估：安装器/快照质量与被限速的 SourceForge 下载不成比例，保持 SKIP） |
| TCC | `download.savannah.nongnu.org/releases/tinycc/` → `tcc-0.9.27-win64-bin.zip`（~0.5MB，官方发布区） | 异构 C 编译器：全量构建 + 运行产物 | ✅ 0.9.27（解包到 `.cb-tools/toolchains/tcc/bin/`；其 `-o` **不补 `.exe`**——D-13 后由扩展按 `extension_auto` 补平台扩展名，测例用**无扩展名输出**验证该行为） |

> `.tar.zst` 解包：Windows 自带 `bsdtar` 需要外部 `zstd`，且官方 LLVM 包使用 1GB 窗口 → 需
> `zstd -d --long=30 -c <file> | tar -xf - -C <dest> --strip-components=1`。
>
> 网络受限环境提示：直连 GitHub release 资产可能被限速（实测 ~15 KB/s）；`curl`/Node 若报
> `CRYPT_E_NO_REVOCATION_CHECK` / `UNABLE_TO_VERIFY_LEAF_SIGNATURE`，说明出口代理做了 TLS 中间人，
> 可导出系统根证书后用 `NODE_EXTRA_CA_CERTS=<pem>`；加速可走清华 TUNA
> `mirrors.tuna.tsinghua.edu.cn/github-release/...`（LLVM，实测 13MB/s）或 `ghfast.top` 代理（xpack/ZakKemble）。

## 5.1b L1 边界/异常 E2E（`tests/e2e/test-e2e-boundary.js`）

真实工程探针 × 可激活扩展（`tests/_harness/extensionActivation.js` + `dist` 产物 + 真实 gcc）。观测口径：mock 输出通道 `lines[]`、`app.mock.warnings`（用户可见提示）、`app.records.warningButtons`、真实文件系统与 `tasklist` 并发进程采样（`PING.EXE`）——不依赖宿主私有 API。

| 场景组 | 断言要点 |
|--------|----------|
| S1 畸形工程 | 截断/未闭合 XML → **可读中文「XML 结构错误」**（不再静默降级）；合法但无 `<Target>` → 中文「项目没有构建目标」；未知 `<Option>`/节点被忽略且工程仍可构建；空/纯空白 `.cbp` → 中文「不是有效的 .cbp 文件」；引用不存在的源文件 → 构建失败 + 诊断 + 无产物；缺 `<Output>` → 中文「未配置输出文件名」且**不生成畸形链接命令**；缺 `title` → 中文早退；重复 `<ExtraCommands>` → 两处命令都保留 |
| S2 只读 / 写盘失败注入 | 真实只读目录（Windows 非管理员下通常不可构造 → SKIP 并说明）；输出/对象目录被同名文件占位 → 中文「无法创建输出目录，目标 "Debug" 中止」或「无法创建目录」+ 构建失败 + 占位文件未被破坏 + 移除注入后重建成功 |
| S3 超长路径 / UNC | `\\?\` 前缀（实测 277 字符）可打开、构建有界收敛；不可达 UNC 主机/共享 → 秒级中文「打开项目失败」；可达 UNC（管理共享）→ 断言「可打开 + 构建有明确结论（产 exe 或失败有诊断）且不崩溃」——**不写死「必须构建成功」**（GNU 工具链对 UNC 工作路径的支持视环境而定，CI runner 实测构建失败且有诊断；本机管理共享默认不可达 → SKIP；`CB_BOUNDARY_UNC_DIR` 可强制走该分支） |
| S4 构建取消 | 真实慢 pre-build 子进程在位时 `codeblocks.build.stop` → 有界收敛、无 exe、摘要「构建已取消」、**toast 也是「构建已取消」而非「构建失败」**、探针子进程清零、随后同会话重建成功 |
| S5 并发/重入 | 构建进行中的第二次 Build → 警告「已有构建正在进行」；**同 tick 双发 → 第二次毫秒级被拒**（互斥原子性）；双发后 Promise 全部收敛、无残留进程、互斥已释放 |

> 本组用例在阶段 5 先复现 **6 条真实缺陷（C1–C6 → 登记 D-14…D-19）**，产品修复后断言自动转绿；
> 收口阶段又追加 **S6 编译器程序路径作用域（D-20 回归，3 条）**，现为 **38 pass / 0 fail / 3 skip**
> （本机；CI runner 上管理共享可达 ⇒ 39 / 0 / 2）。
> SKIP 口径：前置不可构造时**必须**打印原因，绝不静默通过；能力缺口不伪造断言。

当前 **24 用例 / 0 fail / 0 skip**（跨工具链用例在无交叉工具链的 runner 上按 SKIP 计，退出码仍 0）。

**宿主层三条硬约束（实测，勿踩）**：

1. **不要从测试扩展调用 `vscode.debug.startDebugging`**：`--extensionTestsPath` 方式下该 API 会永久挂起（内置 `ms-vscode.js-debug` 的 `pwa-node` 同样挂起，且工作台仍能响应其它命令）——属测试宿主限制而非扩展缺陷。改用「工作台侧发起」：写 `.vscode/launch.json` + 触发 `workbench.action.debug.start`，只以事件与 `activeDebugSession` 观测结果。
2. **断点必须落在会话所属工作区文件夹内**：VS Code 只把该文件夹内的断点下发给适配器（文件夹外的断点不会产生 `setBreakpoints`）。探针源文件因此在工作区内生成并现场编译。
3. 单用例超时（`CB_HOST_TEST_TIMEOUT`，默认 180s）+ DAP 请求级超时：任何 UI 等待都会失败而不是挂死整轮。另外 `outputChannel.clear()` **不截断** `persistLog` 落盘日志（据此判「输出为空」会假阳性），`tabGroups.all` 不可靠（以 `onDidChangeTabs` 事件流为准）。
4. **跨工具链用例的程序路径注入**：宿主内无法交互驱动「探测编译器」QuickPick，故按产品文档化机制写 `codeblocks.compilerPrograms`
   （**按编译器 id 作用域**：`{ "<id>": { C, … } }`，D-20 后形态；用例结束恢复原值）。
5. **宿主层改动 `src/` 后必须 `npm run bundle`**：扩展入口是 `package.json.main = ./bundle/extension.js`
   （宿主加载的是 bundle，不是 `dist/`）——只跑 `npm run compile` 会让宿主用例跑在**旧代码**上而误判（曾导致跨工具链用例「看似产品坏了」）。

## 5.4 L1 调试 E2E（DAP 协议级，`tests/e2e/test-e2e-debug.js`）

直接以 DAP 客户端驱动扩展的 gdb 适配器（真实 gdb 8.1 + MI），覆盖 **143 条断言**：
断点四类型（普通/条件/命中次数/日志断点）、单步四类（含指令级）、线程与栈、变量嵌套与 `setVariable`、表达式求值、反汇编、内存读写、数据断点、指令断点、运行到光标、SetNextStatement、异常断点、用户命令（MI/CLI）、多会话路由、terminate、能力请求（`modules`/`loadedSources`/`pause` 能力探测）、**attach / Detach（目标进程仍存活）**、**多线程切帧**、**运行中请求防护**（未停止时 `threads` 回缓存、其余请求快速失败并附中文说明，替代 30s MI 超时）、**`stopOnEntry` 入口首停**（S10b：入口临时断点 → `stopped(reason=entry)`；含 `stopOnEntry:false` 对照、GUI `-mwindows`/`-municode` 入口符号候选（`WinMain`/`wWinMain`，排除 CRT 的 `main` 桩）与 `strip -s` 无符号表用例）。

> 本机 GDB 8.1 限制（已实测并据实断言）：被调试进程内函数求值 `-data-evaluate-expression "add(2,3)"` 与全量寄存器读取会触发 GDB 崩溃（0xC0000005），故寄存器全量读取由 `codeblocks.debug.registers`（默认关）门控（本层唯一 SKIP）；`jump file:line` 语义为「从新地址继续执行」；运行中（未停止）同步 MI 不回应任何命令，Windows 原生 GDB 下 `-exec-interrupt` 既不产生 `*stopped` 又让 GDB 永久失去回执（`mi-async` 无效）——`stopOnEntry` 因此用**入口临时断点**而非中断实现。
> `stopOnEntry` 的入口选取（C-01）：`-break-insert -t main` 对 `-mwindows` GUI 程序的 CRT `main` 桩返回 `^done` 但**无 `func`/`file`/`line`**（`at="<main+9>"`）且永不命中 ⇒ 只接受**带源码位置**的解析结果，按 `main` → `WinMain` → `wWinMain` 依次尝试；均不可用（如 `strip -s` ⇒ "No symbol table is loaded"）时用 `info files` 的 `Entry point` 作地址断点兜底（该停点无源码行，帧名 `??`，符合 DAP「入口」语义）。
> **可重定位镜像分支**（跨环境差异，用例按产物属性分支断言，两个环境各真实执行一条）：PE 置了 `DYNAMICBASE`（新 binutils 默认 `--dynamicbase`）时加载器可能重定位映像 ⇒ 文件内入口地址运行前不可知，地址断点会在 `-exec-run` 时插入失败并**中止整个启动**（CI runner GDB 17.1 实测：`Cannot insert breakpoint 1. Cannot access memory at address 0x1400013f0` → `Command aborted.`）。适配器改为：`src/debug/peImage.ts` 解析 PE 标志 → 可重定位镜像**跳过**地址兜底并给出精确原因；同时 `-exec-run` 失败且存在入口断点时**撤断点重试一次**（stopOnEntry 失效可以接受，程序起不来不可以）。用例断言「程序不被中止 + 正常跑完 + 说明可读」（`tests/test-pe-image.js` 16 断言 + `tests/test-debug-entry-failsafe.js` 9 断言覆盖判定与重试逻辑）。两条分支各 4/6 条断言 ⇒ 本机固定基址共 **143** 条、CI runner 可重定位共 **141** 条，均为 0 fail。

## 7. 维护约定

- 新增无头测试：`tests/test-*.js`，末行输出 `N pass, M fail` 摘要。
- 新增分层测试：放对应目录并匹配 `test-*.js`（host 层为 `runTest.js`）。
- 修改 WebView HTML/样式后：`npm run visual:baseline` 刷新基线，并在提交信息中说明视觉变更。
- 产品改动涉及热路径时：`npm run test:perf` 确认预算未被击穿。
- 契约变化（命令/设置/视图/语法）后：`npm run coverage:matrix` 刷新台账——`npm run test:contract` 里的
  `tests/contract/test-doc-consistency.js` 会校验「覆盖矩阵汇总 == 明细 == 贡献面」与「测试报告 §2 台账 == 覆盖矩阵汇总」，
  漂移会**直接失败**（不只是告警；CI 的 job summary 另有一份漂移提示）。
- **不要用绝对行号做断言**：无关代码增删会让断言误报（曾因 `gdbDebugAdapter.ts` 增行 44 行使 main CI 变红）。静态读点断言请用「语义/同语句特征」判定（例：`tests/test-settings-coverage.js` 断言键所在行是一次真实 `.get(...)` 取值）。
- **不要用固定 `sleep` 等异步就绪**：一律轮询「条件成立」（带超时），并给 `spawnSync` 显式 `timeout`；真实进程类用例在失败路径上清理长驻进程（`taskkill`），必要时「清理半成品 + 重试 1 次」（例：`tests/test-debug-detach-symbol.js`、`tests/test-makefile-export.js`）。
- **能力缺口不伪造断言**：宿主/GDB 能力缺失时用 `ctx.skip` / `skipCheck` 记录现状与原因（例：调试 E2E 中 GDB 8.1 全量寄存器读取、工具链矩阵里缺失的 MSP430/SDCC），并登记到 [遗留问题决策清单](./遗留问题决策清单.md)。
