## 1. T1 CppCheck 集成（建议：不实施，用扩展替代）

### 1.1 CB 行为（file:line 取证）

| 环节 | 取证 |
|---|---|
| 入口/操作 | 插件菜单执行（`CppCheck.cpp:161` Execute；`:163` 日志「Running cppcheck/vera++ analysis...」；`:178` 读 `operation` 配置选择 **cppcheck 或 vera++**） |
| 文件列表 | 写入 `CppCheckInput.txt`，每行一个 `relativeFilename`（`:201/221`），供 `--file-list` 使用 |
| 参数来源 | 目标/工程的 include → `-I"dir"`（`:238/248`）；`-D` 开头的宏 → 原样收集（`:262/274`） |
| **命令** | `cppcheck <args> --file-list=CppCheckInput.txt <includes>`，默认参数 **`--verbose --enable=all --enable=style --xml`**（`:282-294`，默认值见 `ConfigPanel.cpp:77`） |
| 结果 | 解析 XML → 列表日志（`Id : Severity : Message`，`:387-449`）+ 输出通道；可定位到文件/行 |
| Vera++ | 备选后端 `vera++ <args> --inputs <file>` + 行正则 `(.+):([0-9]+):(.+)`（`:495-518`） |
| 路径探测 | cppcheck 不在 PATH 时自动补 PATH（`:603-650`） |

### 1.2 扩展现状

- `src/` 下 `cppcheck|vera++` **0 命中**；无可复用分析器 UI。
- 可复用件：输出通道、`toolRunner`（E1 自定义工具的三种输出模式）、**`codeblocks.generateCompileCommands`（compile_commands.json 导出，Build 菜单）**。

### 1.3 VS Code 扩展替代评估（安装量＝量级参考）

| 扩展 | 名称 | 契合点 | 局限 |
|---|---|---|---|
| `cppchecksolutionsab.cppcheck-official`（2.9k） | Cppcheck Official（**Cppcheck 团队支持**） | 保存时对 C/C++ 文件跑 cppcheck，诊断进 Problems | 偏「编辑器诊断」；不读 .cbp 目标文件集 |
| `jbenden.c-cpp-flylint`（736k） | C/C++ Advanced Lint | cppcheck 后端可配（含参数）、诊断面板 | 配置面偏大；需自行配置参数 |
| `emielestivenartentity.cppcheck-turbo`（1.1k） | Cppcheck Turbo | **消费 `compile_commands.json`** + `.cppcheck-config` | 依赖 compile_commands.json 存在 |
| `brobeson.vscode-cppcheck`（15k） | Cppcheck | 简单直接：对文件跑 cppcheck | 功能单一 |
| `qiumingge.cpp-check-lint`（51k）/ `ebikelabs.cpp-checker`（5.6k） | cppcheck+cpplint | 双后端 | 维护活跃度一般 |

**结论**：CB 工作流 = 以**工程模型**（目标文件集 + 每目标 `-I/-D`）为输入一次性跑全目标分析；
市场扩展 = 以**文件/工作区**为输入、诊断进 Problems（更符合 VS Code 习惯）。
两者衔接点：本扩展已能导出 `compile_commands.json`，cppcheck-turbo / Cppcheck Official 可直接消费 →
**等效度高**。因此建议**不实施**，在文档中提醒替代组合：安装上述任一扩展 +
（可选）用 `Code::Blocks: Export compile_commands.json…` 提供工程口径。

### 1.4 若仍要 CB 对齐（回退方案）

薄命令（S）：`codeblocks.runCppCheck` —— 优先 `cppcheck --project=compile_commands.json`（无则按目标文件 +
`includeDirs`/defines 组装），输出写通道 + 解析为 Problems 诊断。

### 2.2 扩展现状与替代评估

### 5.1 CB 行为

| 环节 | 取证 |
|---|---|
| 入口 | 插件菜单：先配置对话框（`symtab.cpp:97`），再执行对话框（`:132-134`） |
| 两种模式 | ① **目录批量**：枚举 `*.a/*.lib/*.o/*.obj/*.so/*.dll`（`symtabexec.cpp:311-319`），逐库 nm 并**搜索目标符号**（`:298-340`，无结果提示 `:364`）；② **单库 + 符号**（`:375-393`） |
| **命令** | `nm <param> "<library>"`（`:83-87` 组装，nm 路径可在配置中改；`:403-434` 执行） |
| 参数/过滤 | 配置复选框：包含类型（A/Lib/O/Obj/So/Dll）与符号过滤 Debug/Defined/Demangle/Extern/Special/Synthetic（`symtabconfig.cpp:248-343` 对应 nm 选项） |
| 结果 | 解析 nm 行（含 `Class::Method` 冒号处理，`:496-542`）→ 可排序列（`:45/241`）；可「Save NM output to file」（`:153-168`） |

### 5.2 扩展现状与替代评估

- `src/` 下 `objdump|readelf` 等 **0 命中**。
- 替代评估：

| 扩展 | 名称 | 契合点 | 局限 |
|---|---|---|---|
| `wibren-wiersma.nm-tool`（344） | Nm tool | 直接集成 GNU **nm + objdump** | **单文件**查看；安装量极小 |
| `sqlpassion.vscode-binutils`（3.6k） | vscode-binutils | 二进制分析工具集 | 非 nm 专项 |
| `trond-snekvik.gnu-mapfiles`（457k） | GNU Linker Map files | linker `.map` 符号列表（构建时可生成） | 需 `-Wl,-Map`；非库文件搜索 |
| `elf-ripper-devteam.elf-ripper`（2.1k） | ELF-Ripper | ELF/readelf 分析（嵌入向） | 非符号搜索场景 |

- **核心差异**：CB 的主打场景是「**在一个库目录里跨多个库搜索某符号**（它是哪个库定义的）」；
  市场扩展偏**单文件**查看 → 该场景**无替代**。
- 结论：**实施跨库符号搜索**（S）——选目录（默认当前目标 output/依赖库目录）→ 枚举库文件 → 逐个 `nm` →
  过滤符号 → 结果列出来源库/地址/类型（QuickPick 或输出通道）；nm 路径探测（gcc 同目录/PATH）。
  单库逐条查看留给市场扩展（文档提醒）。

## 9. 风险与边界

1. **T1/T4 替代即「不做」**：以文档提醒为主；若日后仍要 CB 对齐，回退方案见 §1.4/§4.3（S 级薄实现）。
2. **T2**：需要目标带 `-pg`（否则无 `gmon.out`，CB 亦如此提示）；Windows 下 gprof 输出编码/路径需处理；
   与 CB 的「Profile Code when executed」对齐可用目标级开关或文档提示起步。
3. **T5**：依赖 binutils `nm`（MinGW 通常自带）；`nm` 输出随工具链版本差异（POSIX vs BSD 格式），解析需容错；
   搜索库数量大时需限时/取消。
4. **市场数据时效**：安装量/评分为查询时点；扩展可用性与维护状态会变化，实施时以文档注记日期为准。
5. 与既有能力重叠：T1 诊断可对照 Build Log 的错误解析（不改动）；T5 与 Symbols 视图（源码级）互不冲突。
