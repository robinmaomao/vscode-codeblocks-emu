## 2. 开关类待决（F 组）

### F2 启动自动恢复 + 自动打开工程

- **现状**：`activate()` 末尾无条件执行 `restorePersistedProjects()`（恢复上次会话）+ `autoDetectAndOpenProject()`（唯一 `.cbp`/`.workspace` 直接打开、多个弹 QuickPick）+ 工作区文件夹变化监听 + `**/*.cbp` 创建/删除监视器（800ms 去抖重扫——在工程目录新建 `.cbp` 也可能被自动打开）。
- **CB 依据**：`/environment/blank_workspace` 默认 **true**＝启动不加载上次工作区（`app.cpp:766-769`；UI：Settings → Environment → General → On application start-up）。CB 无「扫描目录并自动打开」等价行为（扩展新增能力，无 CB 开关可对齐）。
- **建议方案**：新增 `codeblocks.project.autoOpenOnStartup`：`restore`＝现行为 / `blank`＝对齐 CB（不恢复、不自动打开，仅保留状态栏入口与检测列表）/ `detect`＝扫描但仅提示（不自动打开单文件、不弹多选）。
- **默认值待确认**：`restore`＝维持现状；`blank`＝对齐 CB（行为变化需在 release notes 显著标注）。
- **落点**：`package.json`、`extension.ts`（activate 末尾三处 + 监视器）、`使用说明.md` §5.1/§13、新增 `tests/test-startup-open.js`。

### F3 编辑器激活自动切换活动工程

- **现状**：`onDidChangeActiveTextEditor → syncActiveProjectToEditor()` 无条件；归属唯一时自动 `setActiveProject`（影响状态栏 Target/Compiler、F9 构建对象、共享文件 clangd 归属）。**性能已优化**（0.8.114-dev 属主索引 + 记忆化），但行为门控未做。
- **CB 依据**：editor `/sync_editor_with_project_manager` 默认 **false**（且仅做工程树定位，不改「活动工程」）。
- **建议方案**：新增 `codeblocks.ui.syncActiveProjectWithEditor`（布尔）。默认值待确认：`true`＝现状（`使用说明` 已宣传该行为）；`false`＝对齐 CB。
- **落点**：`package.json`（ui）、`extension.ts` 监听处、`使用说明.md` §13、测试断言。

### F4 工程树文件固定字母序

- **现状**：`sortDirNodes()` 与根层排序无条件按 label 字母序（`src/ui/projectTreeProvider.ts`）。
- **CB 依据**：project_manager `/sort_alpha` 默认 **false**＝按 `.cbp` 原始顺序（开启后 CB 会禁用 Project Up/Down 菜单）。
- **建议方案**：新增 `codeblocks.projectTree.sortAlphabetically`（布尔）。默认值待确认：`true`＝现状；`false`＝对齐 CB 原序。
- **落点**：`package.json`、`projectTreeProvider.ts` 两处排序、文档、测试。

### F6 构建进度显示固定开启

- **现状**：三处构建入口均 `withProgress(Notification, cancellable)` + 状态栏 250ms `Building… (Ns)` spinner（0.8.114-dev 已做空闲零开销渲染优化，仅渲染时机）。
- **CB 依据**：compiler `/build_progress/bar`、`/build_progress/percentage` 默认 **false**。
- **建议方案（可选）**：新增 `codeblocks.build.showProgress`（`notification`（默认）/`statusBar`/`none`）。注意：通知进度承担「取消构建」入口，改 `none` 后保留状态栏停止入口（spinner 点击）。
- **落点**：`package.json`、`extension.ts` 三处 withProgress + spinTimer、文档、测试。

### F7 use_folders / hide_folder_name

- **现状**：物理目录模式恒等价 CB `use_folders=true`，无平铺/隐藏文件夹名模式；现有 `codeblocks.projectTree.categorize` 仅在「类型分组 / 物理目录」间切换。
- **CB 依据**：`/use_folders` 默认 true、`/hide_folder_name` 默认 false。
- **建议**：**记录不移植**（当前默认组合与 CB 默认一致；如需要可做两个布尔 `projectTree.useFolders` / `hideFolderNames`）。

### C-01 `stopOnEntry`（✔ 已实施）

- **现象**：`launch` 的 `stopOnEntry` 从未被消费——设置后程序直接运行，没有入口首停（`package.json` 的 launch schema 也未声明该属性）。
- **复现**：`node tests/e2e/test-e2e-debug.js`（S10b；修复前为「记录现状 + SKIP」）。
- **修复（第一轮）**：`src/debug/gdbDebugAdapter.ts` 新增 `prepareStopOnEntry()`——`-exec-run` 前插入口**临时断点** `-break-insert -t main`（实测对比过 `-interpreter-exec console "start"`：后者返回 `^running`、断点编号只能从 CLI 文本间接获得），命中在 `*stopped` 里按 `bkptno` 精确映射为 `reason='entry'`；attach/远程目标给出「不适用」提示。`package.json` 的 launch schema 补充 `stopOnEntry` 布尔属性（默认 false）。
- **修复（第二轮，收紧判定 + 入口兜底）**：第一轮仍有一条真实缺口——`-mwindows` GUI 程序的 `main` 是 MinGW CRT 桩符号，`-break-insert -t main` 返回 `^done` 但**无 `func`/`file`/`line`**（`at="<main+9>"`，`info address main` = "in a file compiled without debugging"），GUI 启动路径 `WinMainCRTStartup` 直接调 `WinMain` ⇒ 该断点**永不命中**，旧实现因「有编号、非 pending」当成可用入口而**静默失效**。现改为：
  1. 按 `main` → `WinMain` → `wWinMain` 依次尝试，**只接受带 `file`/`line` 的解析结果**（CRT 桩无源码行 ⇒ 删断点试下一档）；
  2. 三者都不可用（如 `strip -s` 无符号表 ⇒ 全部报 "No symbol table is loaded"）时**兜底到程序入口地址**：`-interpreter-exec console "info files"` 解析 `Entry point: 0x…` → `-break-insert -t *<addr>`（该停点无源码行，DAP 侧仍为 `reason=entry`），并输出一行中文说明；
  3. 仅当符号与入口地址都不可用才回退为「不首停 + 中文说明」（不卡死、不阻塞程序）。
  `*stopped` 的入口描述改为动态标注实际落点（`main` / `WinMain` / `wWinMain` / `0x…`），不再写死 `main`。
- **修复（第三轮，可重定位镜像保护 + 启动兜底）**：CI（`windows-latest`，GDB **17.1** + 新 binutils 默认 `--dynamicbase`）暴露该兜底会**反过来破坏启动**——镜像被加载器重定位后，「首选基址 + 入口 RVA」（`0x1400013f0`）是**未映射地址**，断点插入在 `-exec-run` 时失败：
  `Cannot insert breakpoint 1. Cannot access memory at address 0x1400013f0` → `^error,msg="Command aborted."` ⇒ **程序完全起不来**（比「不首停」更糟）。两项修复：
  1. **事先判定**：新增纯函数模块 `src/debug/peImage.ts`（解析 PE `DllCharacteristics.DYNAMICBASE`，只读文件头）；可重定位镜像**跳过地址兜底**，直接给精确原因（「程序为可重定位镜像（PE DYNAMICBASE，加载后基址可能变化），入口地址在加载前不可知；带调试符号编译即可用 stopOnEntry」）；非 PE（如 Linux ELF）不受影响（GDB 默认禁用 ASLR）；
  2. **启动兜底**：`onConfigurationDone` 里的 `-exec-run`/`-exec-continue` 抽到 `startTarget()`——若启动失败且**存在入口临时断点**，撤掉该断点**重试一次**，并输出 `stopOnEntry 未能生效（原因），已撤销入口断点并重新启动程序`。原则：stopOnEntry 失效可以接受，**绝不能让程序起不来**。
- **验证**：调试 E2E **114 → 127**（第一轮）**→ 142**（第二轮）**→ 143 pass / 0 fail / 1 skip**（第三轮），S10b 共 **30 条断言**：
  - CLI 正例 12 条（`reason=entry` + 停在 `main` 首行 + continue 收尾）；
  - `stopOnEntry:false` 对照 1 条；
  - GUI 候选两条镜像形态（`-mwindows` 仅 `WinMain`、`-municode -mwindows` 仅 `wWinMain`）各 5 条（含「描述标注实际入口符号」「停在用户源码入口行」）；
  - 无符号表按产物 `DYNAMICBASE` **分支断言**（本机 binutils 2.30 默认固定基址；CI 新 binutils 默认可重定位，两条分支在两个环境各被真实执行）：
    固定基址 6 条（入口地址首停 + 首帧无 source + 中文说明 + continue 跑完）、可重定位 4 条（**程序不被中止** + 正常跑完 + 说明含「无法生效/可重定位」+ 无「无法启动程序」）+ 会话收尾 1 条。
  **差分实测**（本机 MinGW GCC + GDB 8.1，`dist/` 前后对比）：`-mwindows` 程序修复前 6s 内无 `*stopped`、程序静默跑完；修复后 286ms 首停于 `gui-entry-probe.c:7`（`func="WinMain"`）。`strip -s` 程序修复前不首停；修复后 374ms 首停于 `0x4014e0`（`func="??"`，`-mwindows` 版入口为 `WinMainCRTStartup`）。强制 `-Wl,--dynamicbase` 产物走可重定位分支：4 条断言全绿（程序正常跑完，不再被中止）。
  **单元层**：`tests/test-pe-image.js`（16 断言：PE32/PE32+、DYNAMICBASE 位与其它位组合、非 PE、截断/损坏头、文件形态与目录/缺失文件）、`tests/test-debug-entry-failsafe.js`（9 断言：失败→撤断点→重试成功的调用序列、无入口断点不重试、重试仍失败返回真实错误、静态接线）。
