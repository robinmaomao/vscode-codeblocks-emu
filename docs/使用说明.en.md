## 1. Introduction

Code::Blocks for VS Code is a "mini IDE kernel": it parses `.cbp` / `.workspace` project files directly, embeds the Code::Blocks command templates and macro expansion engine, and spawns processes to compile / link / debug. It is not a bridge that translates `.cbp` into `tasks.json`, so its behavior closely matches Code::Blocks:

- Incremental builds (source files + `#include` headers + link input files such as `.ld` compared by mtime)
- File type detection aligned with Code::Blocks (`FileTypeOf`): assembly sources (`.S` / `.s` / `.asm`) are compiled and linked correctly; non-source files such as linker scripts (`.ld`) are neither compiled nor linked by default
- `Rebuild` = Clean + Build (aligned with Code::Blocks; **a confirmation dialog appears first**)
- pre/post build scripts (`.bat` / commands); project-level pre/post runs once per build, post-build is gated by "commands actually produced" (aligned with the Code::Blocks state machine)
- Forced relink when external dependencies change (`external_deps` / `additional_output` / updated link libraries) + global compiler search directories + project custom variable macro expansion
- **Stop the build at any time**: the ❌ button in the build notification or `Code::Blocks: Stop Build`
- Automatic object directory creation, common top-level directory object layout
- GBK output decoding (GCC errors are readable on Chinese Windows)
- Error count truncation (`max_reported_errors`)
- Dedicated syntax highlighting (`.ld` / `.lcf` linker scripts, `.S` / `.s` assembly, `.xm` configuration scripts, including automatic token colors)

> For the item-by-item alignment evidence (with Code::Blocks source locations), see [Alignment with Code::Blocks](./对齐对照.md).

## 2. Installation

### 2.1 Install from VSIX

```powershell
code --install-extension codeblocks-vscode-0.8.133.vsix --force
```

### 2.2 Build from source

```powershell
npm install
npm run package
code --install-extension codeblocks-vscode-0.8.133.vsix --force
```

> `npm run package` = `vsce package` (before packaging, the `vscode:prepublish` hook runs `tsc` compilation (`dist/`, for local testing) + the **esbuild single-file bundle** (`bundle/extension.js`, the release entry));
> Running `npx vsce package` / `npx vsce publish` directly also builds automatically, so a stale or missing `bundle/` is never shipped;
> Use `npm run compile` when you only need the compile step, and `npm run bundle` to rebuild the bundle alone (the `.vscode` task `build-extension` covers both).
> On Windows, prefer `npm.cmd` / `npx.cmd` (PSReadLine execution policy).

### 2.3 Development debugging

```powershell
code --extensionDevelopmentPath="." --disable-extensions --new-window
```

## 3. UI layout

After installation, the **Code::Blocks** icon appears in the Activity Bar on the left; click it to expand the sidebar (Project / Analysis; **Symbols is hidden by default**); **Build Log** lives in the bottom Panel (open with `Ctrl+J`, then select the "Build Log" tab); **Menu** sits at the far left of the status bar:

| Entry | Location | Description |
|------|------|------|
| **Menu** | Far left of the status bar (`⊞ Menu`) | The Code::Blocks menu bar (File / Edit / View / Search / Project / Build / Debug / Tools / Settings): click to open a two-level menu (Project tree / Folding / Case / Line / Errors etc. are **submenus** you can drill into); the list shows **keybindings** and separators, and when no project is open the related items are marked **(no project)**; **hover to expand** common command links in place |
| **Project** | Sidebar (main body) | Project tree: multiple projects + nested folders + file browsing (drag to reorder, right-click actions); hovering a project row shows quick **Build / Rebuild / Clean / Properties** buttons |
| **Analysis** | Sidebar | Project analysis: shows key `.cbp` properties per project (Summary / Build targets / Build commands / Search directories / Files / Virtual targets / Variables / Notes); **hover to show the matching .cbp snippet**, **click a property to locate it in the .cbp**, right-click to copy the snippet; the top holds a "recent build" shortcut (click to open Build Log) |
| **Symbols** | Sidebar (hidden by default) | Symbol browser: lists project symbols grouped by Function / Macro / Type / Variable; click to jump to the definition; reachable from the view container's **⋯ → Views** menu, or controlled by the `codeblocks.ui.symbolsView` setting |
| **Build Log** | Bottom Panel (tab) | Structured build summary tree (compiler / compile statistics / link result / error and warning groups) |

- The **position, side-by-side/stacked arrangement and size** of views can all be dragged and adjusted freely; VS Code saves them automatically and restores them the next time you open the window.
- **Menu dynamic area**: **Workspace** lists the build order by dependency topology (click to set the active project); **Recent Projects** lists recent projects (the **Clear Recent Projects** item at the end clears the history).
- Run **`Code::Blocks: Reset View Layout`** to restore the default layout in one click (Build Log back to the bottom Panel, sidebar order Project → Symbols → Analysis, with Symbols hidden by default).
- When no project is open, the **Project** view shows an empty-state guide (open project / new project / compile single file / detect compilers).
- The **Analysis view** is fully collapsed by default (only the first project's "Summary" is expanded); the **⟳** button in the title bar refreshes manually, and it also refreshes automatically when a project is opened/removed and when a build finishes.
- **Project view title bar**: the persistent buttons are determined by the `codeblocks.ui.projectToolbar` setting (default Build Workspace / Rebuild Workspace / Clean Workspace); buttons that are not pinned move into the **⋯** overflow menu automatically (new/open project, Build / Rebuild / Clean, Run / Debug, Compiler options / Project properties, code statistics).

Other status bar items: **build target (Target)**, **build menu (Build)**, **compiler (Compiler)**.

- **Build menu (Build)**: click to open a menu — Build (incremental build of the active project, `Ctrl+F9`) / Rebuild (full build of the active project, `Ctrl+F11`) / **Build Workspace** (incremental build of all projects) / **Rebuild Workspace** (Clean + Build all projects, with a confirmation dialog); hovering expands the four command links in place.
- **Build in progress**: the Build item becomes `$(sync~spin) Building… (Ns)` (live seconds); **clicking it again (or hovering and clicking "Stop build") stops the build**.

## 4. Quick start

1. Open a folder containing `.cbp` / `.workspace` (the extension detects it automatically and prompts you to choose which project to open),
   or run **`Code::Blocks: Open Project (.cbp)`** from the Command Palette.
2. Browse project files in the **Project** view of the **Code::Blocks** panel on the left.
3. Click **Target** in the status bar to choose the build target; click **Build** or press `Ctrl+F9` to start building.
4. Build results appear as a tree in the **Build Log** view; press `F4` / `Shift+F4` to cycle through errors.

## 5. Project management

### 5.1 Opening projects

- Command Palette: `Code::Blocks: Open Project (.cbp)`
- Or open the folder containing the `.cbp` directly and select projects from the prompt
- **Detection and auto-open are configurable (adjust this for workspaces with many projects under one parent directory)**:
  - `codeblocks.detect.autoOpen`: `all` (default, show the multi-select list) / `single` (open automatically only when a single project is detected) / `off` (no auto-detection; the status bar entry still works)
  - `codeblocks.detect.autoOpenThreshold` (default `20`): when the number of unopened projects **exceeds this value, the multi-select list is no longer shown** (status bar entry + Output channel hint only); it also limits how many projects are restored for the session
  - The multi-select list **only pre-checks recently used projects** by default (no longer selects everything); `.cbp` additions/removals are registered incrementally and do not trigger a workspace-wide full scan
- **Diagnosing workspace scan cost**: run `Code::Blocks: Workspace Scan Report` from the Command Palette → prints scan duration, number of detected projects, number of project directories, current ripgrep process count and a "use a single project directory" recommendation to the "Code::Blocks" Output channel (use it to pinpoint why the machine slows down during builds in large directories / on network drives / with antivirus enabled)

### 5.2 Multiple projects

- After opening several `.cbp` files, the **Project** view lists them in order (**that order is the compile order**).
- Drag project nodes to change the compile order; right-click a project node to **Move Up / Move Down / Remove** (also available from Menu → Project → Project tree, applied to the active project).
- `Alt+F5` / `Alt+F6` **cycle** the active project among the open projects (aligned with Code::Blocks Activate prior/next project).
- The **active project** (marked with a solid green dot in the tree) determines the status bar Target / Compiler and what `F9` builds.
- **Clicking any node in the project tree** (project / folder / file) makes the project that owns that node the active project; **editing a file of a project makes the active project follow it** (switches to the project that owns the file).
- **Shared files** (the same file appearing in several projects): clicking a node under a specific project subtree switches to that project; editing a shared file directly in the editor keeps the active project unchanged (the ownership is ambiguous, so no jumping).
- Right-clicking **Build / Rebuild (single project build)** on a project also switches the active project to it.
- The active project is remembered across windows: it is restored after a reload.
- Completion / navigation for **shared files** resolves against the **active project's** compile commands; switching the active project regenerates the compilation database and, when files are open, restarts clangd to refresh the red squiggles (switch `codeblocks.clangd.restartOnActiveProjectSwitch`).

### 5.3 Context menus

**Project node:**

| Command | Description |
|------|------|

**Folder / virtual folder / file group node:**

| Command | Description |
|------|------|
| Add Files... / Add Files Recursively... | Add files only to the project owning that directory (scoped to the project) |
| Find File... | Search only **within that node's scope** (directory including subdirectories / virtual folder / file group) |

**File node:**

| Command | Description |
|------|------|
| Compile File | Toggle whether the file takes part in compilation (written back to the `.cbp`) |
| Link File | Toggle whether the file takes part in linking (written back to the `.cbp`) |

> **Find File (Find File…)**: when invoked from the Command Palette, the scope is the **active project** (with multiple projects, all of them are listed); `*.cbp` files in a workspace with no open project
> are listed as "project file" entries, and selecting one **opens the project directly**. Behavior is aligned with Code::Blocks:
> it locates only in the project tree by default (`select + focus + expand`); with **`codeblocks.ui.findFileOpen`** enabled (default `false`,
> corresponding to the CB `Find file → Open file` checkbox), it locates and opens the file at the same time.

### 5.4 New projects and templates

The `Code::Blocks: New Project` wizard ships with **12 templates**:

| Template | Description |

**User templates** (aligned with CB File → New → From template… / Save project as template…):

| Command | Description |

## 6. Build system

| Feature | Keybinding | Menu / command |
|------|--------|-------------|
| Build (incremental build, active project) | `Ctrl+F9` | `Code::Blocks: Build` |
| Compile Current File (compile the current file) | `Ctrl+Shift+F9` | Menu Build → Compile Current File (aligned with CB Ctrl-Shift-F9) |
| Build Workspace (all projects) | — | `Code::Blocks: Build Workspace` |
| Build and Run | `F9` | `Code::Blocks: Build and Run` |
| Run | `Ctrl+F10` | `Code::Blocks: Run` |
| Rebuild (full build) | `Ctrl+F11` | `Code::Blocks: Rebuild` |
| Clean | — (aligned with CB; no shortcut) | `Code::Blocks: Clean` |
| Rebuild Workspace | — | `Code::Blocks: Rebuild Workspace` |
| Debug / Continue | `F8` | `Code::Blocks: Debug` (while debugging = continue) |
| **Stop Build (stop the build at any time)** | ❌ button in the notification | Menu Build → Abort / `Code::Blocks: Stop Build` |
| Next / Previous Error | `F4` / `Shift+F4` | Menu Build → Errors → Next/Previous Error |
| Clear All Errors | — | Menu Build → Errors → Clear All Errors (also clears the output panel and the Problems diagnostics) |
| Clear Build Output | — | Build Log view title bar `$(clear-all)` / `Code::Blocks: Clear Build Output` (clears the output panel + Build Log tree + Problems diagnostics) |
| Build File (compile a single file) | — | Right-click a file in the project tree → `Build File` |
| Compile File (no project) | — | `Code::Blocks: Compile File (Without Project)` |
| Clean File (clean a single file) | — | Right-click a file in the project tree → `Clean File` |

- **Incremental builds**: source files and `#include` headers are compared by mtime, so updating a header also triggers recompilation.
- **Rebuild** is aligned with Code::Blocks: it cleans the object directory first, then recompiles everything; **a modal confirmation dialog appears before it starts** (a normal Build does not prompt).
- **Rebuild Workspace**: every open project is cleaned first and then built (dependency topology order, with a confirmation dialog; aligned with Code::Blocks `RebuildWorkspace`).
- **Clean**: deletes each target's object files, `.depend` dependency files and output files (including the `.exe` that Windows appends to extension-less outputs, and the import library of a dynamic library).
- **Stop the build at any time**: the ❌ button in the top-right corner of the build notification or the `Stop Build` command from the Command Palette; on Windows `taskkill /T /F` forcefully kills the whole process tree (cmd → gcc → cc1/as, no leftovers), the cancellation reports "⚠ Build cancelled" instead of "build failed", and completed compile counts are reported accurately.
- **Forced relink on external dependencies**: when a link library / `external_deps` / `additional_output` is newer than the output, the link is forced even if the build is "up to date" (aligned with Code::Blocks `AreExternalDepsOutdated`); a missing dependency file produces a WARNING (aligned with `directcommands.cpp:707-720`).
- **Relink on link input changes (protective enhancement)**: changing a non-compiled file inside the project with a whitelisted extension triggers an automatic relink / repack (setting `codeblocks.build.linkInputExtensions`, **default `.xm` only**; add `.ld`/`.lds`/`.icf`/`.def` etc. as needed, or set `[]` to disable; Code::Blocks has no such automatic detection and requires manual External dependencies entries).
- **Forced relink on compile item counts (aligned with CB)**: in Code::Blocks, stale files in the compile list produce an item (a log line or the command itself) and therefore force a link / repack (`directcommands.cpp:585`); the extension replicates this — files without an executable command (a custom empty command `buildCommand=" "`, unmatched tools), compile units with **real custom commands**, and **files with missing sources** (WARNING entries, else branch :562-566) all force a relink **on every build** (objects are never produced / sources are missing, consistent with CB; the build log notes the reason for the empty-command case).
- **post-build gating**: a project-level post-build step runs only when the last target actually produced a compile/link/repack command (or the project sets alwaysRunPostBuildSteps) — a pure incremental build after a Rebuild no longer re-runs the post script.
- **Script completion detection (aligned with CB)**: pre/post-build scripts treat **the exit of the command body (cmd.exe)** as the completion signal — background programs started by the script (`start`, `start /b`, GUI programs, daemons) no longer hold the build hostage (aligned with the Code::Blocks synchronous wait semantics; before the fix they kept the build waiting until they exited, and a measured `start /b` case wasted 5.1s). After the command exits, **the pipeline continues as soon as it has been quiet for about 0.25s** (tail output is still streamed live; the quiet period only confirms there is no in-flight data), **capped at 1.5s** (setting `codeblocks.build.scriptExitGraceMs`; `0` = finish immediately, fully aligned with CB); when a background process really exists the log prints an explanatory line (`[script i-N] background process is still running (it does not block the build…)`), and when a single command exceeds 3s a `took x.xs` line is printed for diagnosis (the `plainCbLog` mode prints neither). Scripts that **must wait for a background program** should use a foreground command or `start /wait`.
- **Live streaming of script output**: stdout/stderr of script commands is **written line by line to the build log while the command runs** (indented by two spaces; output is no longer replayed only after the command finishes) — when a long run is blocked by a network drive (SMB reconnect), an upload service, etc., the log still shows progress instead of staying "completely blank".
- **Heartbeat lines for long commands**: from 5s of runtime, a script command prints `[script i-N] still running (x s)…` every 5s (the first line carries the hint "network drive/service wait → set a timeout inside the script, or click 'Stop Build' to terminate"), so you can tell "the script itself is slow / waiting on the network" from "the extension is stuck" at a glance (silent in `plainCbLog` mode).
- **Optional timeout for script commands**: setting `codeblocks.build.scriptCommandTimeoutMs` (default `0` = no timeout, consistent with Code::Blocks' infinite wait; upper limit 3600000) — on timeout the **whole process tree of that command is forcefully killed**, the log prints a timeout line and the build is marked as failed. It suits blocking scenarios such as network drive reconnects inside scripts (`if not exist Z:\…`) and upload services (.NET default 100s timeout); it applies to script commands only and does not affect compilation/linking.
- **Timeout kills the tree with no stragglers**: `taskkill /T /F` is a **snapshot** operation — descendants created after the snapshot escape; worse, if the command body has already exited before taskkill runs, the whole kill becomes a no-op (observed output "process not found"), the script keeps interpreting the remaining lines and may start `start /b` background processes (1–10s after the kill, new processes were still observed living on). Therefore, when a timeout is enabled, the extension **samples the command's process tree PIDs multiple times at runtime** (starting 150ms after launch, every 2.5s, at most 4 times; after the intermediate cmd exits, its children still point to that PID as PPID, so they can be traced), and after a timeout it reaps in rounds (6×800ms) on the rule "parent PID ∈ terminated set", so a terminated script does not quietly leave background processes behind. Background programs started by the script being killed along with it is expected behavior (timeout semantics = terminate the whole command tree); exit code note: a timed-out command is recorded as failed.
- **Single-file compile (Build File)**: right-click a source file in the project tree → `Build File`; it compiles that file only without linking; incremental detection (source/header dependency mtime) and cancellation support match a whole-target build, and the compile command is byte-identical to a whole-target build (aligned with Code::Blocks `CompileFile`).
- **Single-file clean (Clean File)**: right-click a file in the project tree → `Clean File`; deletes that file's object file and `.depend` dependency file (aligned with `GetCleanSingleFileCommand`).
- **Output clearing**: whole-target / workspace / single-file compile / clean clear the output automatically when they start; `Clear Build Output` (Build Log title bar `$(clear-all)`) clears the output panel + Build Log tree + Problems diagnostics at any time; the Output channel uses normal mode by default (`codeblocks.build.persistLog` defaults to `false`) — history disappears when the window reloads, and only when enabled is it written to disk and kept across windows.
- **Normal output style** (`persistLog=false`): each line can carry a timestamp (format `2026-09-29 15:11:20.222`, the same as the log file; setting `codeblocks.build.outputTimestamp`, default `false`, takes effect when enabled); warning lines get a `⚠️` marker and error lines a `❌` marker (the VS Code output panel does not render colors, so text markers are used for emphasis; markers are disabled in `plainCbLog` mode); the build completion summary block (`✅ Build finished…`) is printed after the "build succeeded/failed" line (at the very end of the build output) and includes a "🕒 Compile time" line (format `2026-09-29 15:11:20`).
- **Run terminal reuse**: `Run` / `Build and Run` / run after a project-less compile / custom tools (terminal mode) all execute in a **terminal with the same name** — an existing same-named terminal is closed first and a new one created (always a single tab, fresh output every time, cwd/env applied each round; name matching only affects terminals "created by the extension in this session" or "whose name has been used by the extension before" (a persistent registry in workspaceState, so old tabs are reclaimed after a window reload), and names never used before are unaffected; Debug uses the debug console and is unaffected).
- **Compiler validation before running (aligned with CB)**: before `Run` starts (including the host-run branch of library / `CommandsOnly` targets) the target compiler is validated (aligned with `CompilerGCC::Run`) — if the compiler ID is not registered or the toolchain path is invalid, the same full error output as a build is printed (last line `Run aborted...`) and the run is aborted even when the executable already exists; `CommandsOnly` targets and the `null` compiler are exempt.
- Unsaved files are saved automatically before a build (can be disabled in settings).

> **Known limitation**: compile / link commands are executed through a shell (to support `.bat` scripts, redirection, etc.). If a project path or file name contains shell metacharacters (such as `&` `|` `^` `;` `%`), they may be misparsed by the shell; avoid such characters in these paths.

## 7. Build targets and compilers

### 7.1 Build targets (Target)

- Click **Target** in the status bar to switch the build target; or use the `Code::Blocks: Select Build Target` command.
- Each target can have its own compiler options, output file and object directory.
- **Build targets are remembered per project**: each project remembers its own last selected target (aligned with the per-project `m_ActiveTarget` in Code::Blocks), so switching the active project does not affect the others, and it is still remembered after a window reload.
- `F9`/`Ctrl+F9` build the **active project** (aligned with CB Build: active project only; with several projects and no active project, a picker appears); `Code::Blocks: Build Workspace` builds **each project's own active target** in turn (dependency topology order, aligned with CB BuildWorkspace).

### 7.2 Compiler detection

- Command: `Code::Blocks: Detect Compilers`
- Automatically detects GCC / MinGW / Clang / MSVC (vswhere) as well as **RISC-V cross compilers**.
- Cross compilers are read from `/compiler/user_sets/<id>` in `%APPDATA%\CodeBlocks\default.conf`,
  so a custom compiler ID such as `compiler="riscv32-elf"` in a `.cbp` works without extra configuration.

### 7.3 Compiler options

- Command: `Code::Blocks: Compiler Options`
- The Webview lists the `<Option>` entries of `options_<id>.xml` grouped by Category; checked items are written back to the project / target compiler options.
- Key points of the Project properties panel (`Properties…`): the build targets page has the "**Dependencies and additional outputs**" group (`external_deps`/`additional_output`, forcing a relink when newer than the output), the "**Environment variables**" group (`<Environment>`, one `name=value` per line) and the "**Advanced**" group (run working directory / deps output directory / platform / host program / console runner / import library·def file / library prefix·extension policy); the project settings page has "**Environment variables**" and "**Project custom variables**" (for the `$(name)` macro) as well as "**Project compilation and output**" (platform / PCH policy / extended object naming) and "**Makefile mode**" (custom Makefile / file name / execution directory).
- The target list supports **Move Up/Move Down** (changing the target order, which affects export and traversal order, aligned with CB Re-order) and "**Export as project**" (exporting the selected target as a standalone `.cbp` containing only its files, aligned with CB Create project from target; also reachable from the Command Palette / Project menu `Create Project from Target…`).
- The "Build scripts" page supports **running post-build even when there is no build command** (`Mode after=always`, aligned with the CB Pre/post page option); all other pages (run parameters / search directories / virtual targets, etc.) are also present.

### 7.4 Mixed-compiler projects

- Each target can declare its own compiler (`<Option compiler="..."/>`): builds, single-file compile/clean,
  `compile_commands.json`, error/warning regexes all switch according to the **compiler declared by the target**
  (aligned with Code::Blocks `GetCompiler(target->GetCompilerID())`).
- When a target does not declare a compiler, the project default compiler is used; when the compiler ID is not registered, the current compiler is kept.

### 7.5 Environment variables (aligned with CB Build options → Custom variables)

- **Editing entry points** (Project properties panel): the **project settings page** "Environment variables" + the **build targets page** "Environment variables" group,
  both one `name=value` per line; written back to `<Build><Environment>` / `<Target><Environment>` in the `.cbp`
  (aligned with the Custom variables page of the Code::Blocks build options dialog).
- **Use 1 · macro expansion**: `$(NAME)` in build/run commands expands by "**target overrides project**"; macro name lookup is case-insensitive
  (`$(port)` and `$(PORT)` are equivalent, aligned with CB `Upper()`); on a miss it falls back to system environment variables.
- **Use 2 · process environment**: programs started by `Run` and `Debug` are injected with these variables (project level + target level).
- Note: **built-in macros take precedence** over environment variables with the same name (for example `TARGET_OUTPUT_FILE` is never overridden; a protective difference);
  "Project custom variables" are an extension enhancement (written to the Extensions node, for the `$(name)` macro) and are not the same mechanism as CB Custom variables.

## 8. Debugging (GDB)

- Command: `Code::Blocks: Debug` (or `F8`); attach to a running process: `Code::Blocks: Attach to Process…`
- **F5 is wired up** (0.8.128): without a `launch.json`, pressing F5 **starts debugging directly with the active target of the active project** (the same derivation as F8: output file / host program, run directory, arguments, environment variables, source search directories, remote target); when the output file does not exist it says "build first" instead of failing silently. `Code::Blocks GDB` (dynamic configuration) also appears in VS Code's `Select debugger` and `Select and Start Debugging` lists and can be started directly.

**Debugger settings** (aligned with CB Debugger settings, see §13): `initCommands` (initialization commands), `userArguments` (extra GDB command-line arguments), `disableInit` (on by default: GDB is passed `-nx` so the user's `.gdbinit`/`gdb.ini` is not executed, aligned with CB "Disable startup scripts (-nx)"), `printPretty` / `printElements` (variable display), `disassemblyFlavor` + `instructionSet` (disassembly flavor, including custom), `charset`, `gdbPath` (GDB path), `addOtherProjectDirs` (other project search directories). Every session also receives CB's fixed initialization commands (`set confirm off` / `width 0` / `height 0` / `breakpoint pending on` / `print asm-demangle on` / `unwindonsignal on` / `filename-display absolute` / `style enabled off`; items unsupported by older GDB are ignored automatically).

**Project-level debugger configuration (rounds 3 R3/R4)**: the Project properties panel gains a "**Debugger**" tab —

- **Source search directories** (one per line, `$(VAR)` macros supported): the debug session sends the `directory` command to GDB (aligned with CB debugger search paths);
  the project root and the common top-level directory are always included; with `codeblocks.debug.addOtherProjectDirs` enabled, directories of other open projects are appended.
- **Remote target** (project-level default + per-target override, aligned with CB project-level debugger options): connection type TCP / UDP / serial,
  serial port and baud rate, IP and port, extended-remote, skipping PATH/LD_LIBRARY_PATH injection, plus pre/post-connect GDB commands and shell commands;
  command order: pre-connect commands → pre-connect shell → [`set remotebaud`] → `target [extended-]remote` → post-connect commands → post-connect shell;
  with a valid connection (serial needs port + baud rate; TCP/UDP need IP + port) startup uses `continue` instead of `run` (aligned with CB; suits OpenOCD / serial targets).
  Written to `<Extensions><debugger><remote_debugging>` in the `.cbp` (bidirectionally compatible with Code::Blocks).

**launch.json support (introduced in 0.8.122-dev, wired to F5 in 0.8.128)**: `"type": "codeblocks"` in `launch.json` provides the configuration schema and the "Add Configuration" template (launch requires `program`, plus optional `cwd` / `args` / `stopOnEntry` / `environment` / `gdbPath` / `searchDirs` / `remoteDebugging`; attach requires `pid`, plus optional `program` symbol file etc.), so hand-written configurations no longer show unknown-property warnings. When creating / adding a configuration, a real `program` is generated from the **current project target** (no longer a placeholder path); an explicit `program` written by the user wins, and if that file does not exist after variable substitution it falls back to the active target output and records the reason in the Output channel; **F5 and F8 share the same derivation logic** (active target → output file → GDB → run directory / arguments / environment / source directories / remote target).

- **`stopOnEntry`** (launch, default `false`): when `true`, a one-shot entry breakpoint is inserted before running; when hit, `stopped(reason=entry)` is reported (VS Code shows "paused on entry"), without changing existing breakpoint/continue behavior. The entry is chosen in the order **`main` → `WinMain` → `wWinMain`**, and only resolutions **with a source location** are accepted — for GUI programs (`-mwindows` / `-municode`), `main` is a stub symbol supplied by the MinGW CRT (no source line, never hit), so it is discarded in favor of the real entry `WinMain` / `wWinMain` (stopping on the first line of user source); when none of the three is available (e.g. no symbol table after `strip -s`), it **falls back to the program entry address** (`Entry point` from `info files`; that stop has no source line and the frame name shows `??`, consistent with the DAP "entry" semantics) and prints a one-line Chinese note in the Debug Console. **Limitations**: launch only (attach and "remote target already running" show a hint and run as usual); for **relocatable images** (PE built with `DYNAMICBASE`, on by default in recent binutils) the program entry address is unknown before loading, so no entry-address breakpoint is attempted and a note is printed (compiling with debug symbols gives a normal first stop); in other cases where no entry can be obtained it falls back to "no initial stop + a one-line Chinese note" (never fails silently, never blocks the program, and **never prevents the program from starting** — if an entry breakpoint causes a start failure it is removed automatically and the launch is retried).

**Debugger toolchain compatibility:** the built-in GDB/MI front end (no cppdbg / CodeLLDB dependency) locates GDB by "explicit configuration → compiler masterPath/bin → PATH" and can debug GCC/Clang toolchain artifacts (MinGW 32/64-bit, TDM, LLVM-MinGW, etc.). To accommodate GDB builds of different eras, the front end applies several compatibility measures: conditional breakpoints/hit counts/logpoints are evaluated by the front end (some GDB 8.1 builds crash when hitting conditional breakpoints), Step Out is implemented with a "temporary breakpoint at the caller's return address" (`-exec-finish` crashes on some GDB builds), and register reading is off by default (reading registers crashes on some GDB builds). Joint debugging verified: MinGW-w64 GCC (64-bit) + GDB 8.1, MinGW.org GCC 6.3 (32-bit) + GDB 7.6.1.

**Known limitations:** Pause depends on the GDB platform interrupt support: native Windows GDB cannot interrupt a running process, and `-exec-interrupt` makes GDB permanently unresponsive — so on that platform the extension **no longer sends an interrupt command** and instead reports "the current debug target does not support pause… (use a breakpoint or 'Stop' to end the session)" while keeping the session usable; remote targets and Linux/macOS (where interrupts work) are unchanged. MSVC (cl.exe, PDB debug information) is out of GDB's scope; use a GCC/Clang toolchain for debugging.

## 9. Code completion and IntelliSense

When a project is opened, the extension generates the clangd assets **outside the workspace** and **writes no files into the project directory** (no `.clangd` is created, and your own `compile_commands.json` is never overwritten):

1. **`compile_commands.json` (written to the extension cache directory)** — reuses the compile commands aligned with Code::Blocks (the expanded `$compiler $options $includes ...`), and makes each command clang-compatible: GCC-only flags that clang does not understand (`-march=custom-extension`, `-msave-restore`, etc.) are removed, and the compiler's default include search paths are appended automatically (`-isystem`, so that system headers of cross toolchains such as RISC-V are also found by clangd).
2. **User-level clangd configuration `config.yaml`** — uses `If.PathMatch` to scope the compilation database per project tree to the cache directory above (`%LocalAppData%\clangd\config.yaml` on Windows), without affecting the user's other content.

- Command: `Code::Blocks: Generate compile_commands.json (IntelliSense)` (regenerate manually and detect clangd)
- Regenerated automatically when a project is opened and when the active project switches; **changing any `codeblocks.clangd.*` setting also triggers one regeneration** (~150ms debounce with coalescing; clangd reloads `config.yaml` itself, so no restart or window reload is needed), and both generation and skips are recorded in the Output channel. Nothing is generated when no project is open (the scope is unknown); the next project open generates with the new settings.
- **Compiler changes take effect immediately as well**: the compile commands in the compilation database, `--target` and system-header `-isystem` are all derived from the current compiler, so changing `codeblocks.compilerId` / `codeblocks.masterPath` / `codeblocks.compilerPrograms` **regenerates with the new compiler** and, once the compilation database actually changes, **restarts clangd** (otherwise open files keep reporting errors/completing against the old compile commands), and the bottom status bar `Compiler:` refreshes accordingly. No opt-out is offered for compiler changes (not restarting means the setting did not take effect); the restart on active project switch can be disabled with `codeblocks.clangd.restartOnActiveProjectSwitch`.
- **Tolerant setting values**: `suppressedWarnings` / `forcedIncludes` / `excludeDirs` are all string arrays. If you edit `settings.json` by hand and accidentally write a string (e.g. `"codeblocks.clangd.suppressedWarnings": "-Wunused-function, -Wempty-body"`), the extension **splits it by comma/semicolon/whitespace** before use; any other type **falls back to the setting default** and prints an `invalid value type` hint in the Output channel (otherwise "configured in settings but not written to `config.yaml`" is hard to diagnose). Array values are also trimmed, cleared of empty entries and de-duplicated.
- **Automatic cleanup of stale leftovers**: the extension only rewrites fragments for "the scope opened this time", so after a project is deleted/moved the old fragments remain forever (and clangd parses them every time). Each configuration generation therefore **also cleans up dead fragments** (those whose scope directory or compilation database directory no longer exists) and prints the count to the Output channel; you can also use the `Code::Blocks: Clean Stale clangd Config Fragments` command to preview + clean manually (it also cleans orphan `compile_commands.json` directories in the extension cache directory that no longer have a matching fragment, which can be rebuilt). **Safety boundary**: only fragments marked by the extension itself (`# >>> codeblocks-vscode <hash> begin`…`end`) are touched and user-owned content is never modified; network drives / unmounted drive letters (such as an unmapped `Z:` or a USB stick) and `\\server\share` paths are always skipped, so nothing is deleted by mistake.

**Using it with clangd (recommended):**

1. Install the VS Code extension **clangd** (`llvm-vs-code-extensions.vscode-clangd`) and run its `clangd: Download language server` command (or install an LLVM toolchain on the system).
2. After opening a project, clangd finds the compilation database through `config.yaml` automatically and you get:
   - code completion and signature help
   - go to definition / find references / hover info
   - rename and document symbols

> If you use the Microsoft C/C++ extension (cpptools), you can run `Code::Blocks: Generate compile_commands.json` manually and then point the `compileCommands` field of `c_cpp_properties.json` at the `compile_commands.json` in the cache directory.

**Diagnostic ownership (after clangd is detected):**

- **Problems panel**: produced by clangd; the build engine no longer reports errors (to avoid duplicates).
- **Build Log view**: the source is decided by the `codeblocks.clangd.buildLogDiagnostics` setting:
  - `build` (default): the build engine's full diagnostics, covering every compiled file;
  - `clangd`: clangd diagnostics (only files that have been opened; may be incomplete/stale after a build).
- **Header completion/navigation**: fallback compile flags (`-I`, `-isystem`, `--target`) are injected automatically for headers, and when `include.h` exists it is force-included (avoiding false positives such as `unknown type name u8/u16`).
- **Unused header hints**: off by default (the fragment writes `Diagnostics.UnusedIncludes: None`); set it to `strict` to let clangd report unused `#include`s, or to `omit` to leave the key out and defer to the clangd default (`strict` in clangd 17+) or your own configuration.
- **Completion does not insert headers automatically**: `Completion.HeaderInsertion: Never` by default — the clangd default `IWYU` inserts the `#include` owning the symbol when a completion is accepted (embedded/bare-metal projects often have no matching standard header to insert), so the extension disables that behavior by default; the `codeblocks.clangd.headerInsertion` setting switches back to `iwyu` or to `omit` (do not write the key, leave it to your own configuration).
- **Header diagnostics suppressed entirely by default**: headers of embedded SDKs are generally not self-contained, so opening one alone lacks context and produces many `unknown type name` / `too many errors` false positives, hence by default (`codeblocks.clangd.suppressHeaderDiagnostics = true`) all diagnostics for header files are suppressed. **Cost**: while editing a header you also see no error hints (diagnostics for `.c` sources are unaffected). If header diagnostics matter more to you and you can accept false positives, set it to `false`.

**Let the configuration be yours (settings = only write the keys that "need writing"):**

Every key in the extension fragment is driven by a setting; **with the default/`omit` value the key is not written**, and the clangd default or your own configuration decides. Defaults match historical behavior, so upgrading does not change existing output:

- **Precedence note**: the extension writes the **user-level** `config.yaml`, which per clangd's rule "user config > inner project `.clangd` > outer project" **overrides** a `.clangd` you put in the project. To yield to the project configuration, set the corresponding setting to `omit` (or change the value to match your `.clangd`).
- Switchable keys: `Diagnostics.UnusedIncludes`, `Completion.HeaderInsertion`, `Index.Background` (`skip` can greatly reduce clangd's CPU/memory usage on large SDKs at the cost of weaker cross-file navigation), `Index.StandardLibrary`, `Diagnostics.ClangTidy` (`off` silences clang-tidy noise), `Completion.AllScopes`, `InlayHints.Enabled`, `Documentation.CommentFormat` (`doxygen` shows parameter/return descriptions on hover), `If.PathExclude` (`excludeDirs` excludes directories such as `obj` / `bin`).
- **Free-form YAML**: `codeblocks.clangd.extraConfig` injects your YAML as a **post fragment in the same scope** (the extension adds `If.PathMatch` for you, so you do not write `If`), so it can override any key above, for example:
  ```yaml
  Diagnostics:
    MissingIncludes: Strict
  Completion:
    ArgumentLists: Delimiters
  ```
  Note: a YAML syntax error makes clangd discard the **entire** `config.yaml` (including the extension fragment); the extension prints hints in the Output channel for "tabs / `---` separator lines / top-level `If:`".

**Cross-compiler fidelity (optional, keeping the defaults is recommended):**

By default the extension uses "`--target` + hand-written `-isystem`/`-include`" to make clangd understand a cross toolchain. A more faithful approach is to let clangd query the project compiler directly:

1. Command `Code::Blocks: Configure clangd --query-driver` — generates `--query-driver=<compiler directory>/*` from the active project's compiler path and **merges** it into VS Code's `clangd.arguments` (you can choose to write to workspace settings / user settings / copy to the clipboard only; there is a preview confirmation before writing, and your other existing arguments are not overwritten).
2. Setting `codeblocks.clangd.builtinHeaders = queryDriver` — makes clangd use the built-in headers extracted from the cross compiler (`stddef.h` etc.) instead of clangd's own built-in headers.
3. With `codeblocks.clangd.queryDriver = true`, if `clangd.arguments` does not contain `--query-driver` yet, the extension prints an actionable hint in the Output channel (your settings are never changed automatically).


**Fallback when clangd is not installed (lightweight symbol completion):**

The extension embeds a lightweight, project-local symbol index (following the lexical-scan approach of Code::Blocks codecompletion; it extracts identifiers only and builds no full syntax tree) that takes effect automatically when clangd is unavailable, providing:

- **Code completion** for functions / macros (`#define`) / structs, enums and classes / variables in the project
- Hover showing the symbol signature and `file:line`
- `Ctrl+click` (or F12) **go to definition**
- An **outline (Outline / document symbols)** for the current file

The fallback is disabled automatically once clangd is detected, to avoid duplicating clangd completions.

**Symbols browser (always available, independent of clangd):**

The **Symbols** view in the sidebar is aligned with the Code::Blocks Symbols panel: it lists the symbols of all open projects grouped by **Function / Macro / Type / Variable**, and clicking a node jumps precisely to the definition.

## 10. Build Log

The Build Log view lives in the **bottom Panel** (ways to open it: press `Ctrl+J` and select the "Build Log" tab, use the menu Build → Build Log, or let it focus automatically when a build finishes — the timing is controlled by the `codeblocks.ui.buildLogAutoFocus` setting, **by default only when the build has errors**; when there are errors it also jumps to the first error by default, and that can be disabled with `codeblocks.ui.buildLogFocusFirstError`). Each build produces one structured summary tree:

```
Build succeeded / failed (root, showing elapsed time · N errors · N warnings)
└── project name (target · succeeded/failed)
    ├── compiler path
    ├── compiled N · skipped N · failed N
    ├── link succeeded/failed (output file)
    ├── errors (3)          ← group node, the count is the statistic
    │   ├── main.c:12:5   error message
    │   └── ...
    └── warnings (5)        ← group node
        ├── util.c:30:2   warning message
        └── ...
```

- **Error / warning groups**: the group node label shows the count directly (e.g. `errors (3)`), with the actual diagnostics hanging one level below it.
- Clicking a diagnostic node jumps precisely to `file:line:column`.
- `F4` jumps to the next error, `Shift+F4` to the previous one (cyclically).
- When the number of errors exceeds the limit (50 by default, adjustable with the `codeblocks.maxReportedErrors` setting) the list is truncated automatically.
- The raw compiler output is still kept in the **"Code::Blocks" output panel** for troubleshooting.
- The **"Code::Blocks" output panel** uses a log channel (LogOutputChannel): every line carries a timestamp; the build prints single-line completion-style progress (`✔️ [Compiled] 123-248 xxx.c (2.0s)` / `✗ [Failed]`), `[Skipping]` / `[Linking]` / `[Archiving]` states, and finishes with an emoji summary block (compiled / skipped / failed statistics + error / warning counts + elapsed time + slowest Top3).
- **The linked/archived artifact size line is printed** (aligned with Code::Blocks `Output file is %s with size %.2f %s`), e.g. `Output file is bin\Debug\hello.exe with size 478.53 KB`. Sizes use the CB rule: three tiers with two decimals (`bytes` / `KB` / `MB`; anything ≥ 1 MiB is reported in MB). It is printed **in plain CB log mode too** (`codeblocks.build.plainCbLog`), so the output can be compared line by line with Code::Blocks; it is omitted when the artifact is missing.
- When the user stops the build it prints `⚠ [Interrupted]` and "⚠ Build cancelled"; interrupted files are not counted as failures.
- Verbose mode (setting `codeblocks.build.verboseOutput`) additionally prints the full compile command lines, the per-file Clean list and the skip list.
- **HTML build log** (setting `codeblocks.build.saveHtmlLog`, off by default): at the end of a build, writes `<project file name>_build_log.html` into the project directory (aligned with CB SaveBuildLog); the sub-switch `codeblocks.build.saveHtmlLogFullCommandLine` (off by default, aligned with CB `full_command_line`), when enabled, prepends a block with the complete command lines executed in this build before the diagnostics summary table.

Three entry points to the **keybinding settings panel**: the command **`Code::Blocks: Keybinding Settings`**, Menu → Settings → Keybindings…, and the one-click links embedded in the descriptions of `Keybindings: Cb Style` / `Keybindings: Overrides` in the **extension settings UI** (`Ctrl+,` → Extensions → Code::Blocks) (click to open the panel / check conflicts):

- Lists all 30 configurable items on one screen (grouped by "Build / Run / Project", "External command aliases", "CB fidelity group"; collapsible and searchable);
- Each row shows: command name and id, `when` condition, current keybinding, default keybinding, effective state (effective / not written), conflict annotation (conflicts with a VS Code default / duplicated with another item);
- Inline actions: **Record** (click, then press the key combination to record; Esc cancels, Backspace = unbind), **Manual** (type something like `ctrl+alt+b`, `ctrl+k ctrl+c`; use this for combinations VS Code/the OS takes first), **Unbind**, **Default** (restore the command's default keybinding);
- Top bar: **Apply** (safety net for consistency between settings and file), **Reset All** (modal confirmation), **Check Conflicts** (invokes the three-source detection), **Open keybindings.json**, **Export Scheme / Import Scheme**;
- Changes **take effect immediately**: they are written to the `codeblocks.keybindings.overrides` setting and synced to the user's `keybindings.json` (reusing managed writing: managed entries only, first-time backup, read-back verification with rollback).

**Keybinding scheme import/export**: the panel button or the `Export / Import Keybinding Scheme` command — exports JSON (`{ version, generatedBy, overrides }`, stable ordering); importing accepts either the wrapper or a direct mapping, with optional **merge / overwrite**; invalid and unknown items are ignored with a notice.

**Settings (advanced/scripted route)**: `codeblocks.keybindings.overrides` remains the single source of truth and can be edited directly:

```jsonc
"codeblocks.keybindings.overrides": {
  "build": "ctrl+alt+b",   // 改键：写入正向条目 + 对默认 Ctrl+F9 写移除规则
  "cbQuit": "",             // 空字符串 = 解绑
  "debug": "default"        // 向导中输入 default 可恢复默认（设置中删除该项亦可）
}
```

**Other command entry points**: `Configure Keybindings…` (QuickPick for quickly changing a single item), `Apply Keybindings`, `Reset Keybindings` (equivalent to the panel's "Reset All").

Note: keybindings are **user-level** (shared across windows); combinations taken first by VS Code/the OS cannot be captured in the panel (use "Manual" input); if you also change the same command manually in the Keyboard Shortcuts UI you may end up with double bindings — use "Check Conflicts" to inspect and "Reset All" to clean up.

## 13. Settings reference

> Since 0.8.79-dev the settings page is presented in **7 sections** (section titles are shown inside the VS Code Settings editor; `configuration` array mechanism).
> Section titles follow the VS Code display language (`package.nls.json` English default + `package.nls.zh-cn.json` Chinese).
> Path-like settings `codeblocks.masterPath` / `codeblocks.compilerPrograms` / `codeblocks.debug.gdbPath` / `codeblocks.build.compilerCache` / `codeblocks.build.compilerCachePath` are declared **machine-overridable**: they do not take part in Settings Sync (avoiding broken paths synced across machines) while still being overridable per workspace.

### 13.0 UI language and Chinese/English switching

> **In one sentence**: command titles and the settings UI follow the **VS Code display language** (`package.nls.json` English default / `package.nls.zh-cn.json` Chinese; a window reload applies it); dialogs, QuickPicks, the status bar and WebView panel titles are controlled by the **`codeblocks.ui.language`** setting and **take effect immediately**.

| What you want to see | How to do it |
| --- | --- |
| All Chinese (including the Command Palette) | Set the VS Code display language to Chinese (`Ctrl+Shift+P` → `Configure Display Language`); keep `codeblocks.ui.language` at `auto` |
| All English (including the Command Palette) | Set the VS Code display language to English; keep `codeblocks.ui.language` at `auto` |
| Command Palette in English, extension runtime text in Chinese (or vice versa) | Use the **`Code::Blocks: Switch UI Language…`** command or set `codeblocks.ui.language` directly to `zh-cn` / `en` |

- How `auto` decides: the display language starts with `zh` (`zh-cn` / `zh-tw` / `zh-hans`…) → Chinese; anything else → English (`zh-tw`/`zh-hk` are currently treated as Simplified Chinese).
- The switch command (`Code::Blocks: Switch UI Language…`) offers a three-state choice, marks the current mode, and after switching shows "command titles/settings UI need a window reload" + a one-click reload.
- **Already open WebView panels**: after a language switch only the title is refreshed, while the body and tabs render in the new language the next time they are opened (so unsaved edits in the Project properties panel are not discarded).
- **Coverage (full since 0.8.132)**: build logs, tree view nodes, debug hints, clangd/keybinding/statistics tool text, menu labels and the internal fields of the three WebView panels are all bilingual;
  the only exception is that with `codeblocks.log.english=true` the build log is forced to English (independent of `ui.language`; see §14 FAQ).

## 14. Complete RISC-V cross-compilation example

> This example uses a RISC-V cross-compilation project (compiler ID assumed to be `riscv32-elf`, already configured in Code::Blocks) to demonstrate a zero-configuration cross-compilation workflow.

### 14.1 Prerequisites

1. Code::Blocks is installed and this RISC-V cross compiler has been configured (it exists in `/compiler/user_sets/riscv32-elf` of `%APPDATA%\CodeBlocks\default.conf`).
2. The extension reads program paths such as `C_COMPILER` / `LINKER` from that configuration automatically, **no manual path entry is needed**.

> If Code::Blocks is not configured, you can also specify them manually in the `codeblocks.compilerPrograms` setting:
> ```json
> {
>   "codeblocks.compilerPrograms": {
>     "C": "D:\\riscv-toolchain\\bin\\riscv32-elf-gcc.exe",
>     "CPP": "D:\\riscv-toolchain\\bin\\riscv32-elf-g++.exe",
>     "LD": "D:\\riscv-toolchain\\bin\\riscv32-elf-g++.exe",
>     "LIB": "D:\\riscv-toolchain\\bin\\riscv32-elf-ar.exe"
>   }
> }
> ```

### 14.2 Project structure

```
my-project/
├── app.cbp
├── platform/            ← platform source files
├── drivers/             ← peripheral driver source files
├── common/              ← shared component source files
└── Output/
    ├── bin/             ← final firmware app.elf
    └── obj/             ← object files (including the custom.o linker script object)
```

### 14.3 Key `app.cbp` configuration

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes" ?>
<CodeBlocks_project_file>
  <FileVersion major="1" minor="6" />
  <Project>
    <Option title="app" />
    <Option pch_mode="2" />
    <Option compiler="riscv32-elf" />

    <Build>
      <Target title="Debug">
        <!-- type="1" = 控制台应用；RISC-V 下会走 LinkConsoleExeCmd，不加 -mwindows -->
        <Option type="1" />
        <Option output="Output/bin/app.elf" />
        <Option object_output="Output/obj/" />
        <Option compiler="riscv32-elf" />

        <Compiler>
          <Add option="-march=rv32imac" />
          <Add option="-mabi=ilp32" />
          <Add option="-Os" />
        </Compiler>

        <Linker>
          <Add library="platform" />
          <Add library="drivers" />
          <Add library="common" />
          <Add option="-TOutput/obj/custom.o" />
        </Linker>

        <Unit filename="main.c" />
        <Unit filename="platform/uart.c" />
        <Unit filename="drivers/gpio.c" />
        <!-- ... 其余 Unit ... -->
      </Target>
    </Build>
  </Project>
</CodeBlocks_project_file>
```

### 14.4 Procedure

1. Open the project root directory in VS Code; the extension detects `app.cbp` and prompts you to open it.
2. The status bar **Compiler** shows the detected RISC-V toolchain (e.g. `RISC-V GCC (riscv32-elf)`).
3. Select `Debug` in the status bar **Target**.
4. Press `Ctrl+F9` to build. The extension automatically:
   - compiles each `.c` with `riscv32-elf-gcc`, writing objects to `Output/obj/`;
   - links with `riscv32-elf-ld` (through `LinkConsoleExeCmd`), adding `-lplatform -ldrivers -lcommon` and `-TOutput/obj/custom.o`;
   - produces `Output/bin/app.elf`.
5. Check the **Build Log**: the group nodes show `errors (0)` / `warnings (N)`; with errors, use `F4` to jump to each one.

### 14.5 Notes

- **The console application type must be used** (`<Option type="1"/>`). If the Windows GUI type (`-mwindows`) is used by mistake, the RISC-V linker reports `unrecognised emulation mode: windows`.
- **Without a dedicated `options_riscv32-elf.xml`**, the extension reuses the GCC template (`options_gcc.xml`) to generate command lines; this is expected behavior.
- Cross compiler program paths come from Code::Blocks' `default.conf`; if a path becomes invalid, re-run `Code::Blocks: Detect Compilers`, or write `codeblocks.compilerPrograms` manually.
- The build artifact is named `app.elf` with no `.exe` suffix; incremental skip detection already handles extension-less outputs (falling back to matching `.exe`).

## 15. FAQ

**Q: Why does an incremental build still relink / recompile?**
A: Make sure the link output and the object files are on the same disk, and that the output was not deleted manually. The extension already falls back to matching for extension-less outputs (MinGW appends `.exe` automatically).

**Q: If I change a `.ld` linker script (or `.xm` / `.def` / `.icf`), will incremental builds notice it?**
A: There are two cases:
- The file has `compile="1"` (including the custom empty command `buildCommand=" "` commonly used in CB): by the Code::Blocks item-count rule, it **relinks / repacks on every build** (such a file's object is never produced, aligned with `directcommands.cpp:585`; the build log notes "forced link (aligned with CB item counting)") — fully consistent with Code::Blocks behavior.
- Ordinary link inputs (not explicitly compiled, including those with custom commands): compared by mtime, so newer than the output triggers an automatic relink / repack (protective enhancement, since 0.8.96-dev); add or remove extensions with the `codeblocks.build.linkInputExtensions` setting or set it to `[]` to disable (**default `.xm` only**; add `.ld` etc. yourself if needed, e.g. `["xm","ld"]`; `xm`/`.xm`/`*.xm` forms are accepted, case-insensitive, and a comma-separated string is allowed). Note: Code::Blocks itself does not detect these files automatically (you must fill in the target's External dependencies); for files outside the project use External dependencies.

**Q: What is the `Debug_link.respFile` (or `main.c.respFile`) that appears after a build? Can I delete it?**
A: It is a **response file**: when a link / compile command line exceeds the length threshold, the extension (aligned with Code::Blocks `CheckForToLongCommandLine`) writes the trailing arguments of the command (usually the object list) into an `@file` for GCC to read — a normal build artifact that **can be deleted safely** (it is regenerated when needed). It lives in the object output directory (`.objs/` by default, or the `object_output` set in the `.cbp`); Code::Blocks itself does not clean it either. To have Clean / Rebuild remove it automatically, enable the `codeblocks.build.cleanResponseFiles` setting (off by default). To generate fewer of them, change `codeblocks.build.responseFile` to `cb` (threshold 32767), but going through cmd above 8191 is risky, and the `safe` default exists precisely to avoid that risk.

**Q: The error jump path in the Build Log shows duplicated segments (Chinese paths)?**
A: Fixed. Since 0.4.0 the character class for file paths in compiler error lines supports Chinese (`\u0080-\uFFFF`).

**Q: The build fails but failedCount is 0?**
A: Fixed. Since 0.4.0 the failure branch also returns and accumulates statistics.

**Q: RISC-V linking reports `unrecognised emulation mode: windows`?**
A: The target type was set to a Windows GUI application by mistake. Change it to a console application (`<Option type="1"/>`).

**Q: The compiler name in the status bar is wrong?**
A: Run `Code::Blocks: Detect Compilers` to detect again; toolchains with the same name are distinguished by install directory `masterPath` and version number.

**Q: clangd reports `typedef redefinition with different types` (`redefinition_different_typedef`)?**
A: This is a cross-boundary conflict between embedded SDK headers (such as `typedef.h`) and toolchain system headers (such as `_stdint.h`) over types like `__int32_t` — GCC compiles it but clangd/clang reports it. Since 0.8.98-dev this diagnostic is **suppressed by default** (written to the clangd user configuration `Diagnostics.Suppress`). To show it again, remove `redefinition_different_typedef` from the `codeblocks.clangd.suppressedWarnings` setting and save — the extension regenerates the clangd user configuration automatically and clangd reloads it; you can also run `Code::Blocks: Generate compile_commands.json…` manually.

**Q: I added a suppression (such as `-Wempty-body`) to `codeblocks.clangd.suppressedWarnings`, but clangd still reports it?**
A: Check three places in order: ① whether `Diagnostics.Suppress` in this project's fragment in `%LocalAppData%\clangd\config.yaml` contains the entry (after a settings change the extension regenerates it automatically and the Output channel prints "settings changed, regenerating with the new settings" and "clangd user configuration updated"); ② whether the value is written as a **string array** (a string is split by comma/whitespace with a hint in the Output channel, and any other type falls back to the default); ③ whether clangd actually reloaded the configuration (`clangd: Restart language server` forces a reload). In addition, diagnostics under headers (`.h`) are suppressed entirely by `codeblocks.clangd.suppressHeaderDiagnostics` by default, independent of the suppression list.

**Q: I changed the compiler settings (`compilerId` / `masterPath` / `compilerPrograms`) but clangd still reports errors against the old compiler?**
A: Since 0.8.131, changing these three settings immediately regenerates the compilation database with the new compiler and **restarts clangd automatically** when the database **actually changes** and open C/C++ files exist (the Output channel prints "compiler settings changed, regenerating the clangd compilation database with the new compiler" and "compiler settings changed, restarting clangd to refresh open files"); the bottom status bar `Compiler:` refreshes accordingly. If you only see "compile_commands.json unchanged, skipping write", the database content is identical (for example the project's compile commands do not use the setting you changed), and clangd is not restarted needlessly.

**Q: After disabling `codeblocks.clangd.enabled`, clangd still shows red squiggles from the old project?**
A: Disabling only makes the extension **stop generating/updating** the user-level `config.yaml`; fragments already written are user-level configuration (higher priority than a project `.clangd`) and are still read by clangd. When disabling, the extension shows a reminder; click "Open clangd configuration" to delete the `# >>> codeblocks-vscode …` marked block, then run `clangd: Restart language server`.

**Q: After changing `codeblocks.build.persistLog` the log is still not written to disk (or the history is still there)?**
A: The Output channel type is created when the window activates and cannot be switched at runtime (rebuilding it clears the current output). After a change the extension shows a reminder and you can click "Reload Window" to apply it; otherwise the behavior stays as before until the window reloads.

**Q: Should `Ctrl+/` in assembly files (.s / .S) insert `//` or `#`?**
A: `//` by default (safe for `.S` processed by the C preprocessor); **raw `.s` (assembled directly by GAS) does not recognize `//`** (measured on RISC-V, both whole-line and end-of-line forms fail; `#` is the GAS-native comment). To use `#`, enable the `codeblocks.editor.asmHashComment` setting (takes effect immediately; `Ctrl+/`, `Ctrl+K Ctrl+C/U` and all other comment actions follow it consistently). Note that block comments (`Shift+Alt+A`) are always C-style and unaffected by this setting.

**Q: I set `codeblocks.ui.language` to `en` but the Command Palette is still Chinese?**
A: Command titles and the settings UI are static contributions of `package.json` that VS Code resolves only by **display language** (`%key%` is expanded before the extension loads), so the extension cannot rewrite them at runtime. To make the Command Palette English too: `Ctrl+Shift+P` → `Configure Display Language`, choose English and reload the window. `ui.language` governs runtime text (dialogs / QuickPicks / status bar / panel titles).

**Q: After switching the language, already open panels still use the old language?**
A: Switching refreshes panel **titles** and subsequent dialogs immediately; panel bodies/tabs render in the new language the **next time they are opened**. This is intentional: the editing state of the Project properties panel lives only in the WebView, and re-rendering would discard unsaved changes.

**Q: Which wins, `ui.language` or `codeblocks.log.english`? How is the build log language decided?**
A: They control different things and never override each other:

| Setting | What it controls | Effect of the value |
| --- | --- | --- |
| `codeblocks.ui.language` | **UI text** (dialogs / QuickPicks / status bar / tree views / debug hints / WebView panels / menu labels) | `auto` (follow the display language) / `en` / `zh-cn`, **effective immediately** |
| `codeblocks.log.english` | **Build log** (build process, phase summaries, `[profile]` blocks in the Output channel) | `true` → **always English** (aligned with the Code::Blocks original, ignoring `ui.language`); `false` (default) → follow `ui.language` |

That is: if you want the **log to always be English** (to compare against CB output while troubleshooting) → enable `codeblocks.log.english`; if you want **UI and log to change together** → change only `ui.language`.

**Q: Is the build log (Output channel) fully bilingual now?**
A: **Fully covered** (0.8.132 batch 2). Build engine logs, tree view nodes, debug layer hints, clangd/keybinding/statistics tool hints, 148 status bar menu labels and the internal fields of the three WebView panels all follow `ui.language` and are bilingual;
the only exception is that with `codeblocks.log.english=true` the log is forced to English (see the previous item). If you find a missing translation, run the guard check in [Internationalization](./国际化.md) §6.

## 16. Unsupported features (known limitations)

The following Code::Blocks features have not been ported yet; when you hit the related configuration, the extension either warns explicitly or ignores it silently:

| Feature | Description |
|------|------|
| **Squirrel build scripts** | `<Script file="*.script"/>` is not supported; the build prints the warning "Squirrel build scripts are not supported yet; skipped" (decision taken: keep as is, no port) |
| **makefile project mode (partial)** | Build/Rebuild/Clean through the `<MakeCommands>` subset are supported; DistClean / single-file compile are not wired up |
| **console runner** | Code::Blocks' cb_console_runner is not ported |
| **EvalXMLCondition exec branch** | Evaluating compiler XML conditions `<if exec="program">` by actually running the external program is not implemented (simplified to returning default; the gcc/clang XMLs do not use it) |
| **`stopOnEntry` launch parameter** | Supported (0.8.129-dev): for launch, the entry symbol is chosen in the order `main` → `WinMain` → `wWinMain` (excluding the CRT `main` stub of GUI programs), a temporary breakpoint performs the initial stop and reports `reason=entry`, and when none is available it falls back to the program entry address (no source line; relocatable images excepted); if the launch is aborted by the entry breakpoint, the breakpoint is removed and the launch retried; attach/remote show a "not applicable" hint (see §8) |
| **Extension-less executables (Windows)** | Run/Debug need an artifact with an executable extension (a requirement of `cmd.exe` / `CreateProcess`, aligned with upstream Code::Blocks). With toolchains such as TCC where "`-o` does not append `.exe`", write the full `.exe` in the target's output file name |
