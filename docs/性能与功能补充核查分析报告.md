## 2. 性能问题详析

### P1 书签装饰：每次按键整文档拆分（编辑热路径）

- **现状**：激活时注册 `onDidChangeTextDocument`（`extension.ts:1526-1529`）——凡**可见编辑器**发生任何文本变更（每次按键、粘贴、撤销、多光标编辑）都进入 `refreshBookmarkDecorations()`（`:4232`）。函数第一行（`:4235`）就是：
  ```ts
  const lines = ed.document.getText().split(/\r?\n/);
  ```
  即**把整篇文档拆成行数组后**，才去 `bookmarks.filter(...)`——**该文件没有任何书签时同样走全量**。
- **影响**：1 万行文件（约 300–500KB 文本）每次按键产生一次全量字符串拷贝 + 1 万项数组分配；持续输入时 GC 压力明显，低配机可感知输入延迟。当前所有打字场景都在无谓付出该成本（多数学员文件没有书签）。
- **修复方案**（推荐组合，均为纯函数/局部改动）：
  1. **空书签早退**：入口先 `bookmarks.filter(b => b.file 与本文件匹配)`；为空时 `setDecorations(bookmarkDecoration, [])` 后直接 return（可用"上次是否有装饰"缓存避免重复 setDecorations）。
  2. **按需取行**：新增 `locateBookmarkLineInDocument(bm, doc, radius)`——用 `doc.lineAt(i)` 只在书签行 ±50 行窗口取样（替换全文档 split）；纯函数放 `bookmarks.ts`，注入 `lineAt/lineCount` 便于单测。
  3. （可选）编辑场景 100–150ms 去抖：书签装饰无需逐键更新。
- **预期**：每次按键开销 O(文档) → O(书签数 × 小窗口)，常见场景（无书签）→ O(书签表长度)。

### P2 兜底符号索引：打开工程时同步全量读文件（clangd 场景纯浪费）

- **现状**：
  - `openProject` 成功路径调用 `rebuildFallbackIndex()`（`extension.ts:2179`）；`removeProject` 同样调用（`:3371`）。
  - `rebuildFallbackIndex`（`:2994-3005`）收集**所有打开工程及目标**的全部文件后，调用 `fallbackIndex.rebuild([...files])`——**同步**执行。
  - `SymbolIndex.rebuild`（`codeCompletion.ts:87`）逐文件 `scanFile`（`:117`）：`fs.readFileSync` 全文 + 逐行 8 类正则扫描。
  - **冗余点**：`fallbackEnabled` 仅在**未检测到 clangd** 时为 true（`:2865`），兜底 provider 此时才生效；已装 clangd 的用户（推荐配置）**索引永远不被使用**，但每次打开工程都付全量读文件成本。
  - `persistProjectAndReload()`（属性面板保存、虚拟文件夹增删改、文件重命名等）都走 `openProject` → **每次操作都重新全量扫描**。
- **影响**：数百文件的工程，打开/保存属性时扩展宿主同步阻塞（估 100ms–1s 级，逐文件读取数千行）。
- **修复方案**：
  - **A. 懒构建**（推荐）：`rebuildFallbackIndex` 只置 dirty 标志；在第一个兜底请求（completion/hover/definition，均支持异步）时**异步构建一次**；构建前返回空结果（clangd 用户永不构建）。
  - **B. clangd 已知时跳过**：模块级缓存 clangd 检测结果（与 P7 共用），`fallbackEnabled === false` 时跳过重建。
  - **C. 增量缓存**（可选后续）：`scanFile` 结果按 文件 mtime+size 缓存，重复 openProject 只扫变更文件。
  - 推荐 A+B（C 可作为后续增强）。

### P3 活动工程跟随：O(项目×文件) 全扫（两个函数叠加）

- **现状**：
  - `syncActiveProjectToEditor`（`extension.ts:2744-2766`）在每次活动编辑器变化时执行 `openProjects.filter(p => p.files?.some(f => normPath(...) === norm))`——对**全部项目×全部文件**做 `normPath`（两次字符串分配），文件多时单次开销线性增长。
  - 精确匹配不唯一时还有第二段 `commonTopLevelPath` 前缀扫描（便宜，可保留）。
  - `setActiveProject(owner, {persist:true})`（`:2250-2262`）在**切换成功时**调用 `hasSharedFiles()`（`:2724-2742`）——**再一次**全项目×全文件 `normPath` + 小写，构建两个 Set 只为找 1 个重复。
- **影响**：编辑器切换可非常频繁（头文件/源文件间反复跳转、分屏焦点切换）；大工程下每次切换都是数万次字符串操作。
- **修复方案**（推荐 1+2）：
  1. **属主索引**：维护 `Map<normalizedPath, Project[]>`——只在工程结构变化时重建（openProject `:2179` 附近、`persistProjectAndReload`、`removeProject`、addFile/renameFile/recursiveAdd 后的刷新点）；`syncActiveProjectToEditor` 与 `hasSharedFiles` 改为查索引（共享判定 = 索引存在 count>1 的路径，收益同时覆盖 `setActiveProject`）。
  2. **事件记忆化**：记住上次 `(fsPath → ownerFilename)`；同一文件重复触发（焦点在输出面板/调试控制台间切换时 VS Code 也会触发 active editor 变化）直接跳过扫描。

### P4 新建工程向导：同步探测器阻塞（可感知卡顿）

- **现状**：向导第 4 步 `pickCompiler()`（`extension.ts:1902-1928`）→ `getDetectedCompilers()`（`:1889-1899`）→ **同步** `detectAllCompilers`（`detector.ts:414`）：gcc/clang `spawnSync --version`、MSVC `spawnSync vswhere`、RISC-V 目录 `readdirSync/statSync` 扫描（`detector.ts:217`）。
  - 同会话仅按 masterPath 缓存一次，**不读跨会话缓存** `loadDetectCache()`（跨会话缓存已存在，状态栏命令在用），也不走异步并行实现。
  - 历史基准（0.8.68-dev 记录）：同步 **1518ms** → 异步 **251ms**（约 6×）。
- **影响**：向导在「选择编译器」弹窗前窗口无响应 0.3–1.5s（视机器/工具链而定）。
- **修复方案**：
  - **A.（推荐，最小改动）** 改为与状态栏命令 `detectCompilers` 相同模式：`loadDetectCache()` 预填 + `createQuickPick` busy 提示 + `await detectAllCompilersAsync(masterPath)` 后台刷新列表。
  - **B.** 至少把 `getDetectedCompilers` 换成异步探测并回填 `cachedCompilers`（后续包内复用）。

### P5 构建状态栏 250ms 常驻定时器

- **现状**：`setInterval(..., 250)`（`extension.ts:623-638`）随激活常驻；两个分支**无条件**重新赋值 `text/tooltip/command`：
  - 空闲分支每次都 `buildStatusHoverTooltip()`——新建 `MarkdownString` + 数组 join；
  - 构建中分支每次都 `buildStopHoverTooltip(secs)`——同样新建对象。
  - 即：无项目、无构建时，也每秒 4 次唤醒 + 4 个 MarkdownString 垃圾。
- **修复方案**：缓存渲染状态（`{building, secs}`），**仅状态/秒数变化时**重建 tooltip 并赋值（空闲时零操作，定时器保留用于状态迁移检测）；或空闲时动态降频至 1s、构建开始恢复 250ms。两者可结合。

### P6 编译器 XML 每次 `getCompiler()` 重解析

- **现状**：`getCompiler`（`extension.ts:3961`）每次 `compilerLoader.load(id)`；`CompilerOptionsLoader.load`（`optionsLoader.ts:61-95`）**无缓存**——`loadFile` 每次 `readFileSync + XMLParser.parse`，并跟随 `extends` 链读取多个文件（gcc：options_gcc + options_common_* ≈ 8 个文件）。
  - 调用点共 28 处（构建/清理/运行/调试/包含文件打开/面板打开…）；其中 `BuildEngine` 的 `switchCompiler`（`buildEngine.ts:122`）与 `resolveTargetCompiler`（`extension.ts:4029`）在**单次构建**按"每目标/每阶段"触发，即一遍构建/清理会重复加载数次至十几次。
  - `queryCompilerVersionString` 已有缓存（0.8.97 修复项），XML 主体尚未缓存。
- **修复方案**：
  - 在 `getCompiler` 层对**最终结果**做 LRU 缓存，key = `id + masterPath + compilerPrograms(JSON) + default.conf mtime`（配置变更与 default.conf 变化自动失效）；注意缓存的是"最终可用的 Compiler 实例"，调用方会 mutate 字段（masterPath/programs/name/…），要么返回深拷贝、要么约定调用方只读（现状各处均会将实例交给 BuildEngine 一次性使用，实例内无跨构建共享状态，直接复用实例已足够）。
  - 备选：`CompilerOptionsLoader` 内部缓存"XML 模板"，`getCompiler` 每次基于模板浅拷贝再应用覆盖（改动略大）。
- **预期**：单次构建减少数次至十几次 XML 读+解析（约 30–150ms，视盘速）。

### P7 `detectClangd()` 每次生成都探测（spawnSync + 递归扫描）

- **现状**：`detectClangd`（`clangd.ts:88-109`）先读 `clangd.path` 设置；否则 `findOnPath`（`spawnSync where clangd`，`:22-33`）；未命中再 `commonLocations()`（可能触发 `findClangdUnder` 对 `%APPDATA%\...\install` 深度 5 递归扫描，`:36-57`）。
  - 每次 `generateClangdForWorkspaceInternal` 都调用（`extension.ts:2865`）；打开 N 个工程 = N 次生成（去抖合并后仍可能多次）。
- **修复方案**：模块级缓存检测结果（**成功与失败（负结果）都缓存**）；clangd 安装/卸载不频繁，可选 5 分钟 TTL 或由 `clangd.path` 配置变更失效。P2 的"跳过索引"判定可复用同一缓存。

### P8 工程树文件节点同步 `fs.existsSync`（低优先）

- **现状**：`fileNode`（`projectTreeProvider.ts:600-610`）在节点缓存未命中时 `fs.existsSync(f.absolutePath)` 决定「缺失」描述。树为懒加载 + 节点缓存，成本分散在各次展开；大工程（数千文件）首次全展开时 UI 线程出现成批同步 stat。
- **修复方案**（可选）：先按"存在"渲染，异步 stat 后仅对差异节点 `fire` 局部刷新；或维持现状（低频操作）——建议**维持**。

## 3. 功能问题详析

### G1 `build.outputTimestamp` 修改需重载窗口生效（一致性优化）

- **现状**：通道创建时一次性读取（`extension.ts:150-155`），`opts.timestamp` 为固定布尔；同组的 `plainCbLog/log.english/strictQuoting/quietSuccess` 已有缓存失效监听（`:167-175`）可即时生效，outputTimestamp 不在其中。package.json 描述已注明「修改后需重载窗口生效」——属**已文档化的限制**，非缺陷。
- **方案**：`cbChannel.ts` 的 `opts.timestamp` 改为 `() => boolean`（惰性读取，与 `plainCb` 同款）；`extension.ts` 传 `() => vscode.workspace.getConfiguration('codeblocks').get<boolean>('build.outputTimestamp', false)`。同步修正 G3 的注释矛盾。零行为风险。

### G2 `deactivate()` 不取消进行中的构建（保护性增强，已实施 0.8.115-dev）

- **现状**：`deactivate()`（`extension.ts:6602`）原先只 `dispose` 输出通道与诊断集合；`currentBuildCancel`（`:113`）仅由 `codeblocks.build.stop` 命令取消（`:1072`）。关闭窗口时若构建进行中，扩展宿主退出后 gcc 等子进程是否被回收取决于系统/宿主进程树管理（Windows 无 POSIX 进程组语义），无保证。
- **实施（0.8.115-dev，用户确认方案 A）**：`deactivate()` 中追加 `currentBuildCancel?.cancel()`（内部 `taskkill /T /F` 杀整棵进程树，`cancelToken.ts`）；无构建时为空操作；行为变化＝关窗/重载即刻中断（不再可能后台跑完）。

### G3 `cbChannel.ts` 注释与默认值矛盾（文档级）

- **现状**：接口注释「（默认 true…）」与实现注释「默认开」，实际 `package.json` 默认 **false**、extension 传实际设置值。属注释误导。
- **方案**：随 G1 一并修正注释（若 G1 不做，也建议单独改注释）。

## 5. 非问题（已核查，防误报）

- `updateClangdUserConfig` 已有「内容未变跳过写入」（`clangd.ts:352-358`）——生成图配置不会反复触发 clangd 重载；
- 缓存体系完善：`parseXmlCached`（mtime+size + LRU 128）、`depsIncludeCache`（LRU 2000）、`shortPathCache`（512）、
