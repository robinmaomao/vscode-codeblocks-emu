# Internationalization (Chinese/English) — conventions, implementation and batch ledger

> Language: **English** ｜ [中文](./国际化.md)
>
> This document is the **single source of truth** for Chinese/English support in the extension: static contributions go through `package.nls.*.json` (following the VS Code display language),
> while runtime strings go through `i18n.t()` + the dictionary (controlled by the `codeblocks.ui.language` setting and switchable immediately).
> Batch progress is in §4; outstanding work is in §5.

## 1. The two pipelines (why two mechanisms)

| Pipeline | Covers | How to switch | When it takes effect |
| --- | --- | --- | --- |
| **Static contributions** | Command titles, setting descriptions/enum descriptions, view names, view container titles, welcome text, debugger snippet descriptions, `displayName` / `description` | VS Code display language (`package.nls.json` English default, `package.nls.zh-cn.json` Chinese) | **Reload window** after a language pack/display language change |
| **Runtime strings** | Dialogs, QuickPick/InputBox text, status bar text and tooltips, WebView panel titles and shell | Setting `codeblocks.ui.language` (`auto` / `en` / `zh-cn`) | **Immediately** (refreshed by the setting-change listener) |

This is not design redundancy but a hard constraint of VS Code: the contributions in `package.json` are resolved by the host **before the extension loads**,
and the `%key%` placeholder can only be expanded according to the current display language (see `replaceNLStrings` in VS Code's `extensionNls.ts`:
**the replacement happens only when the whole string is exactly `%key%`**; a missing key is shown as `%key%` as-is), so extension code cannot rewrite them at runtime.
Conversely, if runtime strings followed only the display language, needs such as "English VS Code UI, but I want Chinese in this extension" could not be met.

> Therefore, when `ui.language` and the VS Code display language are **inconsistent**, a "mixed language" state occurs: the Command Palette / Settings UI follow the display language,
> while dialogs/panels follow `ui.language`. The switch command's notification states this explicitly and offers a "Reload Window" button.

## 2. Runtime implementation

| File | Purpose |
| --- | --- |
| [`src/i18n/core.ts`](../src/i18n/core.ts) | Pure logic (no vscode dependency, unit-testable headlessly): `resolveLanguage(setting, envLanguage)`, `formatSource(template, args)`, `lookupTemplate`, `translate` |
| [`src/i18n/index.ts`](../src/i18n/index.ts) | Extension entry: resolves and caches the effective language (`uiLanguage()`), `t(source, ...args)`, `tr(Chinese source)`, `htmlLang()`, `refreshUiLanguage()`, `translationsTable()` / `webviewTranslationsTable()` |
| `src/i18n/strings.zh-cn.json` | Dictionary: **English source string as key** → Chinese translation (consistent with the "English default" of `package.nls.json`) |
| `src/i18n/strings.zh-cn.webview.json` | WebView reverse lookup table: **Chinese source as key** → English source string (used by the `i18n.tr()` calls instrumented in panel templates) |
| [`src/build/logLang.ts`](../src/build/logLang.ts) | Unified build log entry `logT(English source, ...args)` (controlled by `codeblocks.log.english`, see "The three runtime APIs" below) |

### The three runtime APIs (choosing the wrong one breaks language consistency)

| API | Used for | Language rule |
| --- | --- | --- |
| `i18n.t('English source', ...args)` | Dialogs / QuickPick / InputBox / status bar / progress and other **UI text** | Follows `codeblocks.ui.language` |
| `logT('English source', ...args)` (`build/logLang.ts`) | **Output channel logs** (build log, diagnostic dumps, clangd status lines…) | `codeblocks.log.english=true` → **always English** (aligned with the CB originals); otherwise the same as `i18n.t` |
| `i18n.tr('Chinese source')` | **WebView panel templates** (including inline `<style>`/`<script>` text) | Chinese is the key; in English mode the reverse lookup table yields the English source string, in Chinese mode the text is returned as-is |

- Build-related logs **must** use `logT`: direct calls to the legacy `msg(zh, en)` in `src/build/**` are already banned by the guard (S8b);
  the legacy `msg(zh, en)` entry point is kept for compatibility only.
- `logT` replaces `i18n.t` only in "log text" scenarios; it uses the same `{0}` placeholder rules, so the two can replace each other without touching dictionary entries.
- The legacy `msg(zh, en)` (`logLang.ts`) still exists in a few dual-write scenarios where "the English side is the CB original and the Chinese side is the notification text" (build result toasts);
  do not add new ones.

Conventions:

1. **English is the source string**: the code writes `i18n.t('Build finished')`; Chinese appears only in the dictionary file.
2. **Placeholders `{0}` / `{1}`** (consistent with `vscode.l10n.t`): `i18n.t('Jumped to line {0}', line)`;
   when an argument is missing the **placeholder is kept as-is** (not silently swallowed, which makes a missing argument easy to find); Chinese may reorder placeholders (`{1} of {0}`).
3. **Message templates must not interpolate `${}`**: `i18n.t(\`Finished ${n} item(s)\`)` is flagged as a violation by the guard — always write
   `i18n.t('Finished {0} item(s)', n)` (otherwise the source string cannot be aligned with dictionary entries).
4. **A missing entry falls back to the English source string**; no blank output or leaked key names.
5. Namespace calls `i18n.t(...)` (not bare `t(...)`): a local variable named `t` already exists in some files (e.g. `const t = …trim()`).

### Language resolution

```
设置值 explicit（en / zh-cn）  → 直接采用（覆盖 VS Code 显示语言）
设置值 auto（默认）           → 显示语言以 zh 开头（zh-cn / zh-tw / zh-hans…）→ zh-cn；其余 → en
设置值非法                    → 按 auto 处理
```

- How to switch: Command Palette `Code::Blocks: Switch UI Language…` (`codeblocks.ui.switchLanguage`, QuickPick with three states + current item marker),
  or change `codeblocks.ui.language` directly in Settings.
- The setting-change listener calls `refreshUiLanguage()` + refreshes the status bar + refreshes the **titles of open panels**;
  panel bodies/labels render in the new language the next time they are opened — HTML is deliberately not re-rendered: edit state in the Project properties panel exists only in the WebView,
  and re-rendering would discard unsaved changes wholesale, while language is an appearance preference.
- The effective language is a **process-wide cache**: `t()` does not read the configuration on every line (avoiding hot-path overhead); it is refreshed only on setting changes and on activation.

## 3. Static contribution implementation

- All user-visible text in `package.json` is `%key%`, with these key naming conventions:

| Object | Key pattern | Example |
| --- | --- | --- |
| Extension name/description | `extension.displayName` / `extension.description` | `Code::Blocks for VS Code` |
| Command title | `command.<command id>.title` | `command.codeblocks.newProject.title` |
| Setting description | `configuration.<setting key>.description` / `.markdownDescription` | `configuration.codeblocks.parallelJobs.description` |
| Setting enum description | `configuration.<setting key>.enumDescription.<n>` | `configuration.codeblocks.ui.language.enumDescription.0` |
| View / container | `view.<view id>.name` / `viewsContainer.<container id>.title` | `view.codeblocks.projectTree.name` |
| Welcome text | `viewsWelcome.<view id>.contents` | `viewsWelcome.codeblocks.projectTree.contents` |
| Debugger snippet | `debugger.snippet.<n>.description` | `debugger.snippet.0.description` |

- The two nls files **must have identical key sets** and non-empty values; English values must not contain Chinese; Chinese values must be real translations
  (product names/proper nouns such as `Code::Blocks`, `IntelliSense (clangd)` are whitelisted, see the tests).
- nls values **must not themselves be `%key%`** (a second-level placeholder would be displayed as-is).
- Tests that read static text should use [`tests/_harness/nls.js`](../tests/_harness/nls.js) (`cmdTitle()` / `nlsText()` /
  `setLanguage('en'|'zh-cn')`) instead of asserting on `%key%` directly.

## 5. Known limitations

1. **Command titles / the Settings UI cannot be switched at runtime** (VS Code constraint, see §1); when `ui.language` differs from the display language, a mixed-language state occurs.
2. **The panel body language is fixed when it is opened**: after switching the language, the body/labels of an already open panel do not change (the title is refreshed); reopening renders it in the new language.
3. **`zh-cn` is the only Chinese dictionary**: display languages such as `zh-tw` / `zh-hk` are treated as `zh-cn` under `auto` (no distinction between simplified and traditional).
4. **One value per key**: the dictionary is keyed by the English source string, so the same English text can have only one Chinese translation; scenarios that need two Chinese wordings (such as the
   bilingual keybinding-panel label vs. the confirmation button for `Clean`) are distinguished by **different English source strings** (`Clean` / `Clean now`), without introducing a second table.
5. **Two switches for build logs**: with `log.english=true` logs are always English (ignoring `ui.language`); all other UI text still follows `ui.language`.
   These two settings control "CB original fidelity" and "UI language" respectively, which is intentional.
6. Adding a language (e.g. `ja`) requires: a new `src/i18n/strings.<lang>.json` + a `resolveLanguage` branch + `UI_LANGUAGE_VALUES` /
   `package.json` enums + the two nls files (static contributions).
