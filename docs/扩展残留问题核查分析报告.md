## 1. 新增发现（此前报告未覆盖）

### X1（中低）工程缺 `<Option compiler>` 时被误判「无效编译器」——且与 UI 行为自相矛盾

- **现象**（三处按「无效」处理）：
  - 构建：目标被预过滤 → 输出 “invalid compiler … Skipping...” 并跳过（`buildEngine.ts:265-272`）；
  - 运行：`run()` 前校验直接中止 “Run aborted...” （`extension.ts:6348-6358`，0.8.121-dev 新增）；
  - Clean：视为「编译器未注册」跳过对象清理（`buildEngine.ts:1781-1787`）。
- **但 UI/单文件路径相反**：`getCompiler('')` → `optionsLoader.load('')` 回退加载 `options_gcc`（`optionsLoader.ts:56-96`；`extension.ts:4085`）→ 状态栏/属性面板显示 **gcc**、单文件编译可用。
- **CB 依据**：项目加载器缺省 `compilerId = "gcc"`（`projectloader.cpp:396`，有 `<Option>` 节点时；完全无 `<Option>` 时沿用构造默认，`cbproject.cpp:69`）；目标继承工程（`projectloader.cpp:547/664`）→ **CB 中编译器 ID 永不为空**，不存在此分支。
- **扩展根因**：`parser.ts:198` 默认 `compilerId: ''`；目标继承空串（`:439`）；`resolveTargetCompiler('')` 直接 `return undefined`（`extension.ts:4172-4174`）。
- **影响**：外来/手写/精简 `.cbp`（无 compiler 属性）在 CB 可正常构建，在扩展被跳过且提示「无效编译器」；同仓内「构建失败、单文件可编、Clean 不删对象」互相矛盾，增加排障成本。CB 生成的 .cbp 保存时总会写入该属性，故日常触发概率低，但作为等价性问题成立。
- **建议方案（二选一，推荐 A）**：
  - **A（最小改动）**：`resolveTargetCompiler` 空 ID → `'gcc'`（对齐 CB 字面默认）；若 `'gcc'` 未注册再回退设置 `codeblocks.compilerId`（默认亦为 gcc）。UI/构建/运行/Clean 四处立即一致。
  - **B（模型层）**：`parser` 默认 `compilerId: 'gcc'`——同时会在保存时把 `compiler="gcc"` 写回 `.cbp`（与 CB 保存行为一致，但属于对用户文件的静默补写）。
- **成本**：≈10 行 + 2–4 断言测试（覆盖：无属性工程构建/运行/清理）。

### X2（低）目标级「平台不支持」跳过无任何日志

- **CB 依据**：`PreprocessJob` 对每个不支持当前平台的目标输出警告 `"<工程> - <目标>" does not support the current platform. Skipping...`（`compilergcc.cpp:2749-2756`）。
- **扩展现状**：`buildEngine.ts:260` 直接 `filter` 静默剔除（工程级跳过已有中文提示，`extension.ts:4929` 等）；`collectCompileCommands` 两处过滤（`:416/:481`）本就静默——CB `GenerateCommandLine:238` 同样静默，**那两处无需改**。
- **影响**：多平台工程构建时，日志比 CB 少行、用户不知道目标为何未被构建（尤其刚做完 0.8.121 无效编译器日志对齐，这是同族缺口）；`对齐对照.md` 现有行仅声明「过滤已对齐」，未记录无警告差异。
- **建议**：`build()` 预过滤时逐目标输出 CB 原文警告（保持与无效编译器条目同风格的英文原文）；`对齐对照.md` 对应行补注。**成本**：≈10 行 + 1 测试。

### X3（低）`contributes.debuggers` 缺配置 schema（launch.json 体验缺口）

- **现状**：`package.json` 调试器仅 `type/label/languages`；无 `configurationAttributes`、`initialConfigurations`、`configurationSnippets`。适配器实际支持 launch（`program / cwd / args / environment / gdbPath / searchDirs / remoteDebugging`，`gdbDebugAdapter.ts:296-380`）与 attach（`pid`、可选 `program`，`:405-435`）。
- **影响**：手写 `launch.json`（如 Attach 会话、自定义参数/远程目标）时无 IntelliSense、无「添加配置」模板，未知属性可能被标记警告；**不影响** F8 / 命令流程（内置路径不依赖 launch.json）。
- **建议**：补 `configurationAttributes`（launch/attach 两套）+ `initialConfigurations` + `configurationSnippets`（与适配器读取字段一一对应）。**成本**：≈60 行 JSON + 1 测试。

### X4（低）asm（`.S`/`.s`）语言无 language-configuration

- **现状**：`ld`/`xm` 均配置 `language-configurations/*.json`；`asm` 贡献了语法但无 `configuration`（目录仅 `ld.json`、`xm.json`）。
- **影响**：`.S/.s` 的注释切换、括号/缩进等编辑器规则走 VS Code 默认（注释标记可能与汇编语法不符——GAS 常用 `#`，预处理 `.S` 常用 `//`）。
- **建议**：补 `language-configurations/asm.json`（行注释标记需二选一：`//`（`.S` 预处理安全）或 `#`（GAS 通用，但 ARM 汇编中 `#` 是立即数前缀）），或明确「记录不做」。**成本**：小。

## 7. Y2 / Y3 详解（待确认，2026-10-08 追加）

### 7.1 Y2 — 同步 `spawnSync` 阻塞面

**机制**：以下四处都在**扩展宿主主线程**同步执行子进程（VS Code 扩展宿主是**所有扩展共享的单线程事件循环**，阻塞期间所有扩展的心跳/命令处理都会停摆，界面本身仍能重绘，但感觉为“整个 VS Code 卡一下”）：

| # | 位置 | 触发时机 | 超时上限 | 缓存行为 |
|---|---|---|---|---|
| 1 | `src/compiler/commandGenerator.ts:193` 反引号（backtick）命令求值 | **每轮 Build/Rebuild**（`build()` 开头 `clearBackticksCache()`，对齐 CB `cbClearBackticksCache`）；每个不同的反引号命令 1 次 | 15s | 同轮构建内 LRU 256；跨轮清空重执行 |
| 2 | `src/compiler/compilerVersion.ts:46` `<C> --version` | 首次/编译器 exe 变更后（PCH include 前置需主版本号） | 8s | exe+mtime 键缓存（含负结果） |
| 3 | `src/tools/clangd.ts:26/155/206`（`where clangd` / `-E -x c -v` 系统头 / `-dumpmachine`） | 生成 compile_commands / 检测 clangd 时（首查） | 无显式（系统默认） | `detectClangdCache` TTL 5min + 各自缓存 |
| 4 | `src/tools/pathCase.ts:35`（`cmd /c for %I … %~sI` 短路径） | 路径规范化首次命中 | 无显式 | LRU 512 |

**案例**（按实际影响排序）：

- **案例 A（每轮构建，最值得关注）**：工程 `.cbp` 的编译选项里写反引号命令（CB 语义：`` `cmd` `` 输出拼进选项，如 `-DVERSION=`git describe --tags``、`` `xmaker -q` `` 类代码生成器、`python -c …`）。
  正常命令 10–300ms；**若命令挂起等待输入/卡死/被杀软拦截，每轮构建卡满 15s**；命令退出码非 0 不是问题（失败缓存空串）。
- **案例 B**：`masterPath` 指向网络盘/被 AV 拦的包装脚本 → `--version` 卡满 8s（仅首次或 exe 变更后，之后永久缓存）。
- **案例 C**：冷启动首批 `pathCase`/`clangd` 查询累计 0.2–1s（小而分散）。
- **CB 对照**：CB 同样同步执行（阻塞自身 UI）——所以这不是对齐缺口，而是 **VS Code 宿主共享**放大了阻塞面；且 CB 无超时（挂起命令会永久卡死构建），扩展 15s/8s 超时已是保护性偏差。

**可选处置**：

| 选项 | 内容 | 风险/成本 |
|---|---|---|
| **A（已选，2026-10-08）** | 超时下调（反引号 15s→**3s**；`--version` 8s→**3s**），失败照旧空串/undefined 回退 | 已实施于 0.8.124-dev；两处常量 + 测试断言（test-backticks-and-owner / test-compiler-version-cache） |
| B | 保持现状，文档说明 | 零风险 |
| C | 彻底异步化命令生成链路 | 成本高（buildEngine/commandGenerator 大量同步接口）；阻塞总时长不变，仅不堵 UI；不推荐 |

### 7.2 Y3 — 性能候选（A2 惰性命令生成 / R4 ccache 前缀）

**A2 惰性命令生成**

- **现状**：收集阶段对**每个**编译单元先做增量判定、再**无条件生成完整编译命令**（renderTemplate 宏展开/目录去重/选项合并），随后 up-to-date 的单元丢弃命令只打 `[Skipping]`。
- **实测（0.8.120 M0，boombox 487 文件/248 单元，4C/8T）**：noop 构建总墙钟 2.48s（冷）/ **1.13s（热）**，其中命令生成浪费 **0.25–0.31s**；增量改 1 文件 6.46s 中收集 1.10s（判定 0.76 + 命令生成 0.31）。
- **案例**：日常反复 F9 的“无改动/小改动”场景——热 noop 1.13s → 约 **0.85s（-25%）**；增量构建快 4–5%；rebuild/首次构建无收益。
- **实现要点**：判定提前、仅 stale 单元生成命令；必须逐项保留既有对齐语义（compile=1 空命令/不可编译文件的 `staleNoopFiles` 条目计数强制重链（0.8.100/0.102）、autoGeneratedBy 跳过、PCH 头、deferredUnits、verbose 日志顺序）。
- **风险/成本**：中；golden 命令快照 + 20+ 构建对齐测试护航；≈1 天。
- **建议**：可做（收益小但明确、无行为变化）。

**R4 ccache / sccache 前缀**

- **现状**：编译命令直接 spawn `gcc`；无编译缓存集成（CB 也无——CB 用户惯用包装脚本或把“C 程序”指到 wrapper）。
- **案例**：C++ 大工程 rebuild/切分支后全量重编（如 248 单元 ≈35s 编译）——ccache 全命中时单文件 10–50ms，理论 35s → **8–15s（视命中率）**；对“首次全量”与“单文件增量”几乎无收益。
- **实现选项**：①扩展设置 `codeblocks.build.compilerWrapper`（枚举 ccache/sccache/自定义）+ 探测 + 命令模板前缀（增强，超出 CB 语义）；②维持现状，文档指引用包装脚本（最小）。
- **风险/成本**：低（②≈0；①≈0.5–1 天，需注意含空格路径/`-MD` 依赖文件兼容）。
- **建议**：需求驱动——若未来以「频繁 rebuild 的大型 C/C++ 工程」为主再做；否则记录。
- **2026-10-08 回执：均暂缓（A2 与 R4 均不实施）**。
