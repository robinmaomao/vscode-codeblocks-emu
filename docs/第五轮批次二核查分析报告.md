## 1. D1 Detach（分离调试器，进程继续运行）

### 1.1 CB 源码行为

| 环节 | 取证 |
|---|---|
| 菜单项 | `debugger_menu.xrc:92-93`：`idDebuggerMenuDetach` → label **Detach** |
| 事件绑定 | `debuggermenu.cpp:141`：`EVT_MENU(idMenuDetach, DebuggerMenuHandler::OnDetachFromProcess)` |
| 处理函数 | `debuggermenu.cpp:724-728`：`m_activeDebugger->DetachFromProcess();` |
| 实现 | `debuggergdb.cpp:2486-2491`：`Driver()->Detach(); m_PidToAttach = 0; Driver()->Stop();` |
| 驱动 | `gdb_driver.cpp:639-642`：`QueueCommand(new GdbCmd_Detach(this))` |
| **实际命令** | `gdb_commands.h:354-375`：CLI **`detach`**（解析输出中含 `Detaching` 的行记日志） |
| 输出识别 | `gdb_driver.cpp:768`：输出含 `Target detached` → 视为「程序已结束」→ 入队 `quit`、`m_IsStarted=false` |
| 启用条件 | `debuggermenu.cpp:522-523`：**`isRunning && stopped && isAttached`**（仅附加会话 + 暂停时） |
| 工具栏语义 | `debuggermenu.cpp:878-890`：附加模式下「停止」按钮弹菜单——暂停时提供 **Detach**、未暂停时给「Detach (debugger is running)」置灰项，另有「Stop debugger (kills the debuggee)」 |

即：**CB 的 Detach = 给 GDB 发 `detach` → 放弃驱动（结束调试）→ 被附加进程继续运行**；
仅附加会话可用，且要求暂停状态。CB 无「launch 模式分离」入口。

### 1.2 真机实验（MinGW-w64 GDB 8.1，本机实测）

| 实验 | 步骤 | 结果 | 结论 |
|---|---|---|---|
| A | 外部启动 loop.exe → `-target-attach <pid>` → `-target-detach` | `^done`；进程 **存活** | 附加模式 detach 干净可用 |
| B | launch 模式断点停住 → `-target-detach` | `^done`（回带 bkpt 信息）；随后 `tasklist` 确认被启动进程**继续运行** | GDB 对 launch 会话同样支持分离 |
| D | attach → `-gdb-exit`（**当前扩展停止路径**） | 被附加进程 **存活** | 现有实现不会误杀附加进程（无隐性缺陷） |
| E | attach → 强杀 GDB 进程（dispose 500ms 兜底路径） | 被附加进程 **存活** | 兜底路径安全 |
| F | launch → `-gdb-exit`（对照） | 被启动进程 **被杀死**（实例数 1→0） | 与 DAP「停止=终止」语义一致，不应改动 |

### 1.3 扩展现状（核对）

- 无任何 detach 命令；适配器 `gdbDebugAdapter.ts:90` 已维护 `private attached`（onAttach 置 true，
  `:289-325`），但**未暴露**；`onDisconnect`（`:1014-1017`）直接 `dispose()`；`onTerminate`（`:1019-1026`）
  发 `terminated` 后 dispose；`gdbMiSession.ts:344-349` dispose = `-gdb-exit` + 500ms 后 `kill` 兜底。
- 全代码搜索无 `-target-detach`。

### 1.4 实施方案

- **适配器**：新增 `async detach(): Promise<void>`
  1. 会话存在 → 发 `-target-detach`（两种模式均已实测可用；附加模式为 CB 语义，launch 模式为保护性扩展）；
  2. 捕获 `~`/`&` 输出写 Debug Console；`^error` 时报错返回；
  3. 置 `detached` 标记 → 发 `terminated` 事件 → dispose（此后 `-gdb-exit` 不再涉及进程）。
  - 暴露 `isAttached()` / `isDetached()`；`onDisconnect` 对**附加会话**先尝试 `-target-detach`
    （实验 D 证明即使不做也安全，显式化更稳）。
- **扩展命令** `codeblocks.debug.detach`：取活动适配器（沿用 `getActiveAdapter()` 模式，
  与 setNextStatement/sendGdbCommand 一致）；无会话 → `showWarningMessage`；会话未暂停 → 提示先暂停
  （对齐 CB 启用条件 `stopped`）；成功后状态栏「已分离；进程继续运行」。
- **菜单**：Debug 菜单新增 **Detach**（D1）。CB 仅在附加时启用；VS Code 侧为运行时守卫 + 清晰提示
  （自定义状态栏菜单不做逐项动态置灰，保持简单）。
- **记录项**：CB 工具栏「Detach (debugger is running)」置灰语义 = 我们「未暂停时提示」；launch 模式分离
  为保护性扩展（CB 无），在文档注明。

### 1.5 测试

- 适配器级：mock-vscode + **真实 GDB** e2e（沿用第五十/五十一轮已有 e2e 模式）：
  附加 → 暂停 → detach → 断言进程存活、会话收到 `terminated`、GDB 进程回收；
  launch → 暂停 → detach → 断言进程存活（保护性扩展路径）。
- 守卫路径：无会话 / 未暂停的用户提示（可在 e2e 或 dist 冒烟断言）。

## 2. D2 Add symbol file…（运行时加载附加符号）

### 2.1 CB 源码行为

| 环节 | 取证 |
|---|---|
| 菜单项 | `debugger_menu.xrc:77-78`：`idDebuggerMenuAddSymbolFile` → label **Add symbol file** |
| 启用条件 | `debuggermenu.cpp:514-515`：`isRunning && stopped` |
| 处理函数 | `debuggergdb.cpp:1795-1808`：弹出文件选择框（过滤器 `Executables and libraries\|*.exe;*.dll`）→ `ConvertToGDBDirectory(file)` |
| **实现状态** | `debuggergdb.cpp:1794`：**`// TODO: should reimplement`**；`:1807` `QueueCommand(new DbgCmd_AddSymbolFile(this, file))` **被注释** → 该项在 CB 25.03 **实际不可用** |
| 原命令类 | `gdb_commands.h:268-291`：`GdbCmd_AddSymbolFile` → CLI `add-symbol-file <file>`（**无地址参数**）；ParseOutput 丢弃首行、其余记日志 |

即：CB 保留菜单与文件选择框，但真正下发命令的代码被注释（待重写）；且**即使不注释**，其命令缺
地址参数——本报告实验 C3 证明该形式在 GDB 8.1 必失败。

### 2.2 真机实验（GDB 8.1）

| 实验 | 命令 | 结果 |
|---|---|---|
| C0 | `info address cb_symbol_probe`（负对照） | `^error`：`No symbol "cb_symbol_probe" in current context.` |
| C1 | `-file-symbol-file "C:/…/symp.o"` | `^done`；随后 `info address cb_symbol_probe` → `at address 0x0`，但 **`main` 消失**（`No symbol "main"`）→ **`-file-symbol-file` 是「替换主符号」语义，不可用于本功能** |
| **C2** | `console add-symbol-file "C:/…/symp.o" 0x10000000`（**带地址**） | `^done`；输出 `add symbol table from file "…" at .text_addr = 0x10000000` + `(y or n) [answered Y; input not from terminal]` + `Reading symbols … done.`；探测：`cb_symbol_probe` @0x10000000 **且 `main` 仍在** → **add 语义、主符号不受影响** ✔ |
| C3 | `console add-symbol-file "<file>"`（**CB 原样，无地址**） | `^error`：`The address where <file> has been loaded is missing` → **CB 形式不可用**（双重原因） |
| **G** | `-interpreter-exec console "add-symbol-file \"<反斜杠路径>\" 0x20000000"`（**按扩展 `session.quote()` 双写转义**） | `^done`；`add symbol table …`；探测 `cb_sym2` @0x20000000 ✔ → **扩展沿用 `quote()` 即可，无需像 CB 那样转正斜杠**（CB 转斜杠是因为它不做 MI 转义） |

补充事实：`(y or n)` 确认提示在 MI 管道输入下自动按 Y（"input not from terminal"）；扩展会话已固定下发
`set confirm off`（第五十轮），实际无提示。

### 2.3 扩展现状（核对）

- 无 add-symbol-file 命令；现有 `Send GDB Command…`（`:180-194` 扩展侧）可手工执行任意 CLI，
  但无地址提示、无已加载库列表；`onAttach` 注释（`:311`）明确「失败不阻断，可用 Send user command 手动」。
- 适配器未跟踪 `=library-loaded` 异步记录（`handleAsync` 仅处理 stopped/running/thread-*）。

### 2.4 实施方案（做成**可用版**，保护性差异）

- **适配器**：
  1. `handleAsync` 增加 `library-loaded` / `library-unloaded` 分支：缓存 `{ hostName, from }`
     （`ranges=[{from="0x…",to="0x…"}]` 取首段），暴露 `loadedLibraries()`，为地址预填提供数据源；
  2. `async addSymbolFile(file: string, address?: string)`：
     - 会话存在 + 暂停（对齐 CB `stopped`）→ 否则报错提示；
     - 地址必填校验：空 → 明确报错（说明 GDB 需要 .text 加载地址；库列表可选自动预填）；
     - 发送 `-interpreter-exec console add-symbol-file <quote(file)> <address>`（实验 G 形式）；
     - 捕获输出写 Debug Console；失败原样回显（含 `address … missing` 的提示解释）。
- **扩展命令** `codeblocks.debug.addSymbolFile`：
  1. 取活动适配器 → 无会话/未暂停提示；
  2. QuickPick：**已加载库列表**（`hostName` + `@0x…`，description 显示地址）＋「选择文件…」项
     （`showOpenDialog`，过滤器 `Executables and libraries (exe/dll)` + 所有文件，对齐 CB 对话框）；
  3. 选「已加载库」→ 自动预填其 `ranges.from` 地址，仍可改；选文件 → 地址 InputBox（提示 DLL/EXE 的
     .text 加载地址可从「已加载库」获得）；
  4. 执行成功 → 状态栏「已加载符号: <name>」。
- **菜单**：Debug 菜单新增 **Add Symbol File…**（label 对齐 CB「Add symbol file」）。
- **保护性差异（记录）**：CB 实现被注释且命令缺地址 → 扩展实现为可用版 + 地址必填/库列表预填。

### 2.5 测试

- 纯函数/适配器级：`=library-loaded` 解析（ranges 取 from）与 `addSymbolFile` 命令组装（`quote()` 转义、
  地址格式、空地址拒绝）。
- e2e（真实 GDB）：暂停 → 用 `-c` 编译的探针对象 add-symbol-file → `info address` 断言符号可见且主符号未丢；
  QuickPick 流不可 headless，走适配器 API 断言。

## 5. 风险与边界

1. **D1**：detach 后 VS Code 会话结束但进程仍在运行——需在文档/状态栏明确提示（CB 同语义）；
   未暂停时拒绝（对齐 CB）；launch 模式分离为保护性扩展，已实测可用。
2. **D2**：地址必填是 GDB 硬约束（实验 C3）；库列表地址来自 `=library-loaded` 的 `ranges.from`
   （首段 = .text），对「非调试器启动、后加载的 DLL」同样会出现该事件；符号文件与主程序 ABI 无关，
   仅影响符号解析，不改断点/栈行为。
3. **M2**：`editor.debug.action.runToCursor` / `workbench.debug.viewlet.action.removeAllBreakpoints`
   为 VS Code 稳定内置 ID（后者已在源码核实）；`Run to Cursor` 需调试暂停且编辑器聚焦，否则原生命令
   自行提示。
4. 与既有能力重叠核对：`Send GDB Command…` 保留（手工兜底）；`Refresh Registers`/Registers 视图不受影响。
