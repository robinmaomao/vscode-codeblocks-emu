# 第四轮：编译链接对齐核查报告

> 核查日期：2026-09-27 ｜ 参照实现：Code::Blocks **25.03**（`codeblocks-src/` 检出，所有结论均含 file:line 取证）
> 被核查对象：本扩展 **0.8.85-dev** 的编译/链接链路（命令生成 → 增量判断 → 进程执行 → 清理 → 打包）
> 上一轮（第三轮）已完成 R1–R14 全量实施并推送；本报告为**用户要求再次专项核查编译链接**的结果，待确认后按批次实施。

---

## 0. 结论速览

- **核心链路已对齐**：命令模板展开（逐字节同源 XML）、选项/目录/库合并、对象与依赖命名、增量判断（源/头/输出时间戳 + 外部依赖）、链接/打包/清理命令、执行环境与退出码、构建状态机（pre/post 门控）、并行模型、makefile 项目模式——共 **11 个主题、40+ 处**双方证据核对通过（见 §2）。
- **本轮新发现 19 项差异/缺口**（`L1`–`L19`），其中：
  - **高价值 2 项**：`L1` PCH 头文件 include 前置缺失（gcc 默认 PCH 模式实际失效）、`L2` 编译失败「失败即停」策略差异；
  - **中价值 2 项**：`L3` 编译器资源覆盖缺口（直接影响批次5 新增的 AVR/MSP430 模板可用性）、`L4` `includeInTargetAll` 解析/默认值口径；
  - 其余 15 项为低/极低风险的细节差异（响应文件细节、跨卷对象路径、日志文案、序列化微差等），多数建议**记录差异或提供开关**，不强制改。
- **无阻断性缺陷**：无头真机构建 `EXIT 0`；命令样本实测与 CB 源码推导逐项一致（附录 A）。
- 建议分 **3 批**实施（§5），并**同时引入「命令快照」回归测试**固化对齐成果（§4）。

### L1 ✖（高）PCH 头文件的 include 前置缺失（`-iquote`/`-I.`）

- **CB 证据**：`compilerMINGWgenerator.cpp:34-95` —— `CompilerMINGWGenerator::SetupIncludeDirs` 在
  「项目 PCH 模式 == `pchObjectDir`（**现代 .cbp 的默认模式**，`projectloader.cpp:400`）」且工程内存在
  `compile=true` 的头文件时，向 include 串**前置**（去重后按目录）：
  - gcc≥4：每目录一条 `-iquote<dir> `；gcc<4：每目录一条 `-I<dir> ` + 额外 `-I- `；
  - **随后无条件为同一批目录再各加一条 `-I<dir> `**（第二循环，`compilerMINGWgenerator.cpp:80-88`）；
  - 末尾固定 `-I. `；
  - 该生成器只挂给 GCC 类编译器（`compilerMINGW.cpp:48-52`；`compilergcc.cpp:925` 注册），clang/MSVC（纯 XML 编译器类）不启用。
  - 附注：UseFlatObjects 时 PCH 对象名取扁平名（`fn.GetFullName()`），目录相应为对象输出根目录（`compilerMINGWgenerator.cpp:58-63`）。
- **扩展证据**：全源码检索 `iquote`/`-I- ` **0 命中**；`commandGenerator.setupIncludeDirs` 只做关系合并 + 全局目录，
  `buildEngine` 编译头文件产出 `obj\Debug\util.h.gch` 后，其它文件编译时 gcc **找不到该 .gch**（`#include "util.h"` 从源目录/`-I` 命中 `.h` 而非 `.gch`）。
- **影响**：PCH 生成但**从未生效**——大项目编译时间损失；与 CB 同项目行为不一致（CB 会实际使用 PCH）。
- **建议**：在 include 串组装处实现 MINGW 生成器前置逻辑（仅 gcc 家族 + `pchMode==1` + 存在编译头文件时）；
  逐目录去重；`-iquote` 用当前编译器开关的 `includeDirs` 风格拼接。成本 ≈ 60 行 + 测试。

### L2 ✖（中）编译失败「失败即停」策略

- **CB 证据**：`compilergcc.cpp:3955-4030 OnJobEnd` —— 某命令失败（exitCode > `statusSuccess`）时
  `m_CommandQueue.Clear()`、`ResetBuildState()`、清空剩余 `m_BuildJobTargetsList`：**不再派发任何后续命令**（在跑完的并行任务自然结束），链接/后续目标全部跳过。
- **扩展证据**：`buildEngine.ts:1806 runInParallel` 无失败短路——同 weight 组与其后所有组、以及 deferredUnits 会**全部编译完**才汇总 `failedCount`（`buildTarget` 至 2. 链接前的失败分支）。
- **影响**：出错时会继续编译其余文件（出更多冗余报错、耗时更长）；与 CB「首个失败即放弃」语义不一致。功能上文件均正确报错，风险低。
- **建议**：在 worker 调度循环加失败短路（首个失败后不再启动新单元，in-flight 自然结束；deferred 批次同样检查）；
  保留现有统计与「取消 ≠ 失败」语义。成本 ≈ 30 行 + 测试。

### L3 ✖（中）编译器资源覆盖缺口（新模板 AVR/MSP430 实际不可用）

- **CB 证据**：`resources/compilers/` 提供 **60+ 个** `compiler_*.xml`（自动探测的 masterPath 搜索 + include/lib 路径模板）与
  `options_*.xml`（含 `options_avr-gcc.xml`、`options_msp430-gcc.xml`、`options_sdcc.xml` 等）；`compiler_*.xml` 由 autodetect 流程消费。
- **扩展证据**：`resources/compilers/` 只打包 **16 个** `options_*`（gcc/clang/msvc 系 + common），**没有任何 `compiler_*.xml`**；
  `resolveTargetCompiler` 对未打包且未在 `default.conf` 定义的编译器 ID（如 `avr-gcc`、`msp430-gcc`）→ 报「invalid compiler」并跳过目标。
- **影响**：批次5 新增的 **AVR / MSP430 模板**（以及未来更多 CB 模板）在当前实现下，用户即使安装了 avr-gcc/msp430-gcc，
  也无法在扩展中选择/构建对应编译器（除非手工在 `default.conf` 建用户集）。编译器选项面板同样看不到这些编译器。
- **建议**（二选一或组合）：
  - **A（推荐，低风险）**：打包 CB 的 `options_avr-gcc.xml` / `options_msp430-gcc.xml` / `options_sdcc.xml`（+ 常用 `compiler_*.xml`）并接入探测（PATH/常见安装目录）；
  - **B**：提供「从 Code::Blocks 安装目录导入编译器定义」命令（读取其 `share/codeblocks/compilers/*.xml`）。
  成本：A ≈ 资源拷贝 + 20 行探测注册；B ≈ 100 行 + 目录选择。

### L4 ◐（中低）`includeInTargetAll` 解析/默认值/「All」合成

- **CB 证据**：`projectloader.cpp:551/619-620/682` —— 属性名 **`includeInTargetAll`**（camelCase），**现代 .cbp 默认 false**；

### L5 ◐（低-中）编译器 `logging` 开关未消费（含 make 的 `silentBuild`/`askRebuildNeeded`）

- **CB 证据**：`compiler.cpp:943-952` XML/设置中的 `logging`（full/simple/none）决定构建日志详细度；

### L6 ◐（低）`target.files` 为空时回退 `project.files`

### L7 ◐（低）汇编文件（`.s/.S/.asm`）的编译器选择

### L8 ◐（低）`hasCppFilesToLink` 口径（AutoDetect 链接器选择）

## 6. 复验记录（L1–L5 实测，2026-09-27 第二次核查）

> 方法：真实 MinGW gcc/g++ + 扩展 `dist` 引擎直跑（stub vscode）；L1 用 `gcc -H` 的 PCH 标记（`!` = 使用有效 PCH）；
> L2 用 `parallelJobs=1` 串行构建观察失败后的调度；L4 用三目标夹具解析 + 保存往返；L3/L5 为代码/资源清点 + CB 源码复核。

| 项 | 复验结论 | 关键证据（本次实测输出） |
|---|---|---|
| **L1** | **✔ 成立（端到端实测）** | 扩展真实命令：`g++.exe … -c …\guard.h -o obj\Debug\include\guard.h.gch`（产物 2,003,344 字节）+ `g++.exe … -c main.cpp -o obj\Debug\main.o`（无 `-iquote`）；`-H` 头解析="`.. include/guard.h`"（**未用 PCH**）；仅补上 CB 式 `-iquote obj/Debug/include -I obj/Debug/include -I.` 后 `-H` 变为 "`! obj/Debug/include/guard.h.gch`"（**有效 PCH 被使用**） |

**L1 描述修正**（并入上方 §3-L1 正文）：CB 前置串对同一批 PCH 目录会**同时**输出 `-iquote<dir>` 与 `-I<dir>`（两段循环），gcc<4 另有 `-I- `，末尾 `-I. `；实施时需按此完整规则拼接（实测已验证该组合可让 gcc 以 `!` 命中有效 PCH）。

**L1 附注（新微项，归入 L19 类）**：`UseFlatObjects=true` 时 CB 的 PCH 对象名/目录取扁平名（`obj/Debug/guard.h.gch`），
扩展 `objectPathRelative/objectPathRelativeFlat` 对头文件直接返回 `pchObjectRelative`（始终含源目录层级）→ 该组合下对象路径与 `-iquote` 目录与 CB 不同；建议随 L1 一并处理（或按 `L19` 记录）。
