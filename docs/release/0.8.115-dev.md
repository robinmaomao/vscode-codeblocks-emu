# 0.8.115-dev

> G2 实施（用户单独确认，方案 A）：`deactivate()` 终止进行中的构建——关闭/重载窗口/禁用扩展时不再依赖宿主对进程树的回收行为。

## 背景

性能与功能补充核查（`docs/archive/性能与功能补充核查分析报告.md`，已归档）G2：`deactivate()` 原先只销毁输出通道与诊断集合；构建取消链路（`BuildCancelSource.cancel()`＝置取消标志 + Windows `taskkill /PID <pid> /T /F` 杀 `cmd.exe→gcc→cc1/as/ld` 整棵进程树 / POSIX SIGKILL）只在「停止构建」命令消费。窗口关闭/重载时若构建进行中，编译子进程是否被回收取决于宿主进程树管理（Windows 无 POSIX 进程组语义），**无保证** → 可能遗留孤儿编译进程或未受控的半成品产物。

## 实现（方案 A）

- `src/extension.ts` `deactivate()` 开头追加 `currentBuildCancel?.cancel();`——与「停止构建」命令（`:1072`）同一链路；无构建时为空操作（`undefined` 短路）。
- 行为变化：关闭/重载窗口时若构建进行中 → **立即中断**（此前可能继续跑完）；与 Code::Blocks「关程序即终止构建」语义更接近。
- 边界说明：强杀可能留下截断的对象文件——该语义与既有「停止构建」一致（非本项引入）；不额外清理（保持 CB 的 Abort 语义）。
