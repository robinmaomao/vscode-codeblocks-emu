# Code::Blocks for VS Code 0.8.140

> 发布日期：2026-11-05 ｜ 正式版（0.8.139 → 0.8.140 里程碑汇总）

## 概述

🎯 本版把构建结束的五类「性能归因告警」收进新设置 `codeblocks.build.performanceAdvisor`（**默认关闭**）：普通构建不再刷屏，诊断模式（`build.profile` / `build.sampleSystem`）下仍然自动输出。

- 🔇 **默认静默**：宿主卡顿占比、第三方实时防护 CPU、VS Code 文件扫描器、CPU 饱和归因、构建开始低内存检查五类告警统一受门控；
- 🧪 **诊断模式自动放行**：`build.profile` 或 `build.sampleSystem` 开启时自动启告警，无需额外设置；
- 🔍 **根因**：0.8.135 引入的归因告警在每次构建结束时**无条件**执行（仅受阈值约束），而卡顿占比取自 100 ms `setInterval` 的实际漂移 —— 满核并行编译时扩展宿主自身也被调度出去，占比被放大（现场 59% / 最长 975 ms），与同一轮的 `dispatch wait 11 ms` 自相矛盾；
- 🧭 **边界不变**：`[profile]` 计时块、`build.traceProcesses` 子进程统计行、`build.sampleSystem` 系统 CPU 汇总块、`plainCb` 纯日志模式、并行编译与增量判定流程全部保持原样。

同时包含：设置项 82 → **83**、新增回归 `tests/test-build-performance-advisor.js`（31 断言）、四份文档与双语 nls 同步。

## ⚠️ 现象

0.8.135 引入的宿主卡顿判定在正常构建上也会触发，一次典型输出：

```text
⚠️ [Code::Blocks] The extension host was stalled for 59% of this build (longest single stall 975 ms). ...
⚠️ Suggestions: close memory-hungry applications / add RAM, ...
⚠️ CPU saturation is a cause too, not a symptom: 8 parallel compiler jobs on 8 logical CPUs (4 physical cores) ...
⚠️ Host stalls did not throttle this build: workers waited only 11 ms in total between units (57 units), ...
```

## 🔍 根因

- 卡顿占比来自 `startHostLagSampler()` 的 **100 ms `setInterval` 实际漂移**（`lag = now - last - period`）；
- 8 路编译器跑满 4 物理核 / 8 逻辑核时，扩展宿主**自己也被调度出去**，定时器回调被推迟几十~上百毫秒，累加后占比被显著放大；
- 判定门槛只有三个数值（构建 ≥5 s、占比 ≥20%、单次 ≥500 ms），且**与任何设置无关** —— 告警在 `if (!prof) return;` 之前就无条件执行。

## 🔧 修复

新增设置 **`codeblocks.build.performanceAdvisor`**（boolean，默认 `false`），统一门控：

| 方法 | 输出内容 |
|------|----------|
| `reportHostStalls` | 宿主卡顿占比 + 建议 + `dispatch wait` 两分支判定 |
| `reportSecurityCpu` | 第三方实时防护 CPU 归因（≥10%） |
| `reportWatcherStorm` | VS Code 文件扫描器（`rg` + `conhost`，≥8%） |
| `reportMeasuredSaturation` | 整机 CPU 饱和归因（≥85%） |
| `reportSystemHeadroom` | 构建开始时的低内存检查（可用 <15%） |

`codeblocks.build.profile` 或 `codeblocks.build.sampleSystem` 开启时自动启用（诊断模式），无需额外设置。

## ⚠️ 行为变化与升级提示

- 默认（`performanceAdvisor=false`）**不再输出**五类归因告警；需要排障时开启该设置，或直接开 `build.profile` / `build.sampleSystem`；
- `[profile]` 计时块、`build.traceProcesses` 行、`build.sampleSystem` 汇总块**不受影响**（采样本身照旧运行，只是告警输出被门控）；
- 已知限制：满核并行时「宿主卡顿占比」天然偏高（定时器自身被饿死），只能作诊断参考；判断扩展开销应看 `dispatch wait`。
