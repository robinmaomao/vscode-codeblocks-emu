# 0.8.135-dev

> **主题**：构建期进程/CPU 收口（去 shell 层 · 进程预算 · 扫描让出）
> 开发迭代说明（未发布）｜对应问题：编译大型 `.cbp`（如 RISC-V SDK）时 VS Code 子进程/线程数暴增、CPU 100%
> 逐条对齐依据见 [对齐对照](../guide/alignment.md)；设置项见 [使用说明](../guide/usage.md) §13。

## 概述

本轮把「一条编译命令 = `cmd.exe → gcc → cc1 → as` 四层进程」压到三层，并给并发加上与机器规模挂钩的**进程预算**；
同时把构建「收集阶段」的同步文件系统扫描改为分片让出，构建期的编译数据库生成整体推迟到构建结束。

默认行为变化只有一处：**并发受进程预算约束**（`min(请求值, 32, max(8, 逻辑核数))`），默认值仍为 `8`。

## 一、进程/线程收口

| 项 | 现状 | 本版 |
| --- | --- | --- |
| 编译/链接命令派生 | `spawn(cmd, { shell: true })` —— Windows 上每条命令先起 `cmd.exe /d /s /c`，再起编译器 | 新增 `src/build/shellSplit.ts`：命令行拆成 `program + args` 后直接 `spawn`，**每单元少一个 `cmd.exe`**；含 cmd 元字符（`\| & < > ^ ` % !`）、引号内转义引号、未闭合引号、`cmd`/`powershell` 自身、**cmd 内建命令**（`echo`/`copy`/`del`…）或拆分失败时**回退 `shell: true`**，行为零变化 |
| PCH 旧产物删除 | 命令前缀拼 `` `cmd /c if exist "…" del "…"` `` ⇒ 每个头文件单元多两层进程，且命令变多行（多行会被拆成多次派生） | 改宿主内 `fs.rmSync(…, { force: true })`，编译命令保持单行；删除只在**真正派发该单元前**执行（命令收集 / Makefile 导出 / compile_commands 生成无副作用） |
| pre/post-build 脚本 | `spawn(…, { shell: true })` 未设 `windowsHide` ⇒ 每次建控制台 | 补 `windowsHide: true`（不再出现「控制台窗口主机」刷屏） |
| 并发上限 | 只按「任务数」限流：`0` = 逻辑核 × 2（最多 32），旧版还写过 64 | 新增 `processBudget()` / `resolveJobBudget()`：**实际并发 = `min(请求值, 32, max(8, 逻辑核数))`**，被收敛时构建开始打印一行说明；默认值仍为 `8` |
| 子进程统计 | 只有 `[profile]` 的 `spawn count` | 新增 `spawn peak (live child processes)` 峰值、`spawn without shell` 计数；新设置 `codeblocks.build.traceProcesses`（默认关）在构建结束打印一行「spawn 次数 / 同时存活峰值 / 并发上限 / 逻辑核数」，供现场对照任务管理器 |

## 二、扩展宿主 CPU 收口

- **收集阶段分片让出**：增量判定 + 命令生成是同步文件系统扫描（含 `#include` 依赖递归），现在每 32 个文件 `await setImmediate` 让出一轮，构建期间 UI 与其它扩展保持响应。
- **include 解析命中缓存**：`resolveInclude` 增加「搜索目录签名 + 引用方式 + 源目录 + include 名 → 路径」缓存（每轮构建清空，负结果只在同一轮内复用，构建中新增头文件不会被旧负缓存挡住）；同一 SDK 里 50+ 源文件共享头文件图时，不再为每个 include 做「目录数」次 `existsSync`。
- **构建期不生成编译数据库**：`generateClangdForWorkspace` 在构建中只登记，构建结束（`flushPendingClangdRestart`）再生成 —— 生成链路要同步 `spawnSync` 交叉编译器取系统头（`-E -v` / `-dumpmachine`），构建中跑会与编译抢 CPU 并阻塞宿主。
- **探测缓存随工具链失效**：`queryCompilerIncludes` / `queryCompilerTarget` 的缓存键加入编译器 `mtime` —— 升级工具链后系统头/三元组自动重查（不再整个会话沿用旧值）。

## 四、构建期「进程暴增」现场排查结论（RISC-V SDK 实测）

在大 .cbp 工程（131 Unit / 56 编译单元）上复测后确认：**扩展侧并发已被压到上限**，任务管理器里成百上千的进程来自**工作区级 ripgrep 风暴**，与编译无关。

| 观测 | 数据 |
| --- | --- |
| 扩展自报 | `spawn count 57`、`peak 8`、`spawn without shell 57` |
| 工具链进程（`riscv32-elf-gcc`/`as`） | 峰值 13 |
| `rg.exe` / `conhost.exe` | 峰值 **190 / 204**（构建结束后仍持续约 1 分钟才回落） |
| 命中特征 | `rg --files --hidden … --no-config`（**无 `-g` glob**、搜索根=工作区根）⇒ 调用方是 `workspace.findFiles('**/*')` 级别的全量枚举 |

复现方式（**不需要编译**）：按 2 秒一个的节奏往 `Output/obj` 里造 40 个假 `.o`（换成 `.txt` 同样复现，与文件类型无关）→ `rg.exe` 逐步堆积到 90+。定位到的调用方模式：某「搜索历史」类扩展 `createFileSystemWatcher('**/*')` + `onDidCreate/onDidChange/onDidDelete` → 重跑全库正则搜索（`findFiles('**/*')` + 逐个读取文件）。构建产物每落盘一个文件就触发一次全量扫描，请求堆积 ⇒ CPU 100%、构建墙钟从理论 ~11s 拖到 148s。

### 4.3 新增的三项现场判据

- **`host event loop lag max / total / samples` + `host stalled ratio (%)`**（`[profile]` 内）：区分「编译器本身慢」与「扩展宿主被饿死」。实测值为 `lag max 2913 ms`、`lag total 35.2 s / 总时长 40 s`、仅 41 次采样 ⇒ **宿主 87% 时间处于卡顿**，构建吞吐被派发延迟限制（56 单元 / 8 并发 = 7 轮，每轮等 2~3 s）。

### 4.5 第五轮：把「宿主被饿死」变成可量化、可自愈

现场数据（用户实测，112 进程截图那一轮）：`Total 35.4 s`、`lag total 31.1 s`、`host stalled ratio 88%`、
`lag samples 30`（同长时间正常应 ~354）、`lag max 3627 ms`、`spawn peak 8`、`compile wall clock 27.2 s`。
上一级结论是「宿主被饿死」，但当时还少两件事：一是能不能**把卡顿直接折算成秒数**，
二是能不能**不减并发也把宿主从饥饿队列里让出来**。

- **`dispatch wait` / `dispatch wait max`**（`[profile]` 内）：每个 worker 记录「上一单元结束 → 下一单元开跑」的间隔并累加。
  这是将 `host stalled ratio` 直接折算成秒的指标：卡顿型构建里它应接近「Total − 编译墙钟」。
  56 单元 / 8 并发 = 7 轮，每轮被拖 2–3 s 就是十几秒的纯等待。
- **编译器子进程降级**（新设置 `codeblocks.build.lowerCompilerPriority`，默认 `true`）：
  `os.setPriority(pid, PRIORITY_BELOW_NORMAL)`——Windows 走 `SetPriorityClass(BELOW_NORMAL)` 且被 `cc1`/`as` 继承，POSIX 等价 nice +10。
  **零额外进程**：不改并发数、不加包装器，只是把宿主从饥饿队列里让出来；权限/进程已退出等失败**静默忽略**，绝不影响构建结果。
- **`spawn priority demoted`**（`[profile]` 内）：实际降级成功的子进程数——用来确认设置真的生效（而不是被其它路径绕过）。
- **卡顿告警补充 CPU 饱和成因**：新增一行 `CPU saturation is a cause too…`，给出「N 路并发 / M 逻辑核 / ≈P 物理核」
  与建议并发值（`estimatePhysicalCores`：>4 逻辑核时按一半估算，本机 8 逻辑核 → 4）。
  原告警只提「其它扩展/换页/杀软」，会让现场误以为自己机器「没问题」——实际上 8 路编译器跑满 4 物理核本身就是主因。
- **统计按轮重置**：`spawn count` / `peak` / `demoted` / `dispatch wait` / 预算提示在 `build()` 入口清零，
  多目标构建不再把上一轮数字串进本轮 `[profile]`。

量化教程：构建完对比 `Total`、`compile wall clock`、`dispatch wait` 三个数字——
若 `dispatch wait` 占 `Total` 一半以上，说明时间花在等宿主（降优先级 + 降并发/排除产物目录直接有效）；
若 `compile wall clock` 占大头，那就是真的编译器/磁盘慢，降并发无益。

### 4.6 第六轮：`dispatch wait` 推翻了「宿主卡顿拖慢编译」的推断

用户将并发降到 4 后的实测：`Total 48.2 s`、`lag total 37.8 s`、`stalled ratio 79%`、`lag max 1869 ms`、
`spawn peak 4`、`spawn priority demoted 57`（降级确实生效），而 **`dispatch wait` 仅 4 ms**。

这个数字直接推翻了上一轮的推断：「完成事件排队→worker 无法派发下一个单元」
根本不成立（否则 4 ms/x 不可能出现，56 个单元至少要堆出十几秒）。卡顿发生在**编译器运行期间**：
子进程在跑，扩展宿主抢不到 CPU，但这**不会减慢构建**（没有任务在等宿主）。结论：
`compile wall clock 43.3 s / 56 单元` 是**编译器 + 磁盘 + 安全软件**的真实耗时，不是扩展的派发开销。

同期用户任务管理器截图：`Visual Studio Code (95)` 27% CPU / 2.5 GB，
**腾讯电脑管家-实时防护 (32 位) 26.7% CPU** —— 与 4 路 gcc 抢同一批核心。
`gcc` 每写一个 `.o`、每读一个头文件都要被扫一遍，在同一块 HDD 上就是成倍的墙钟。

本轮交付：

- **新增 `codeblocks.build.sampleSystem`**（默认关；`profile` 开启时自动跟随）：构建期每 ~2 s 采一次
  「整机 CPU% + 编译器/编辑器/已知安全软件各组 CPU%」，构建结束输出归属块：
  `system CPU avg (total %)` / `(compilers %)` / `(editor + helpers %)` / `(third-party security %)` / `(other %)` + `system CPU top process`。
  实现上避开了两个坑：① `Get-Process | %{$_.CPU}` 全量枚举 308 个进程要 **2.5 s**
  （观测者会吃掉一个核）→ 改为按名字过滤（约 20 个进程，0.18 s）；
  ② `Get-Counter` 每次约 1 s → 改用 `PerformanceCounter`（初始化一次性，之后 <15 ms）。
- **实时防护告警**：安全软件占用 ≥10% 时点名一行（带进程名），并给出排除清单
  （工程目录 / 目标文件输出目录 / 工具链目录）。
- **告警文案纠正**：卡顿告警不再一味归因「派发受阻」，改为带 `dispatch wait` 判据的两分支：
  小 → 「宿主卡顿并未拖慢本次构建」；大 → 「确实拖慢，建议降并发/排除产物目录」。
  评估扩展开销应看 `dispatch wait`，而不是 `host stalled ratio`。

**采样口径说明（实测校准）**：

- 窗口 1 s，每窗口读一次 `PerformanceCounter`（初始化约 1 s CPU，之后 <15 ms）+ 按名过滤的
  `Get-Process -Name ...`（约 20 个进程；负载下 0.3~0.6 s），采样自身的 CPU 从 `other` 中扣除（`__self`）。
- 已知局限：**生命周期短于采样窗口的进程会被漏计**——快机器上单个 `gcc`→`cc1`→`as`
  只活 0.2~0.4 s，相邻两次快照几乎不重叠，导致「编译器 %」偏低、`other` 偏高；
  现场那台机器单个单元跳 3 s（磁盘 + 扫描），所以归属分布是准的。看指标时请以
  `total / editor / security` 三项为准，`compilers` 与 `other` 仅作参考。

### 4.7 第七轮：采样口径修正 + 「100% CPU 是谁」的实测回答

用户新数据（8 路并发：`Compiled 56 files (32.4s)` / `Total 43.1 s`）：

```
코스 ─ spawn peak (live child processes)        8
      dispatch wait (worker idle between units)  3.0 ms
      host stalled ratio (%)                     79
      system samples                             21
      system CPU avg (total %)                   97
      system CPU avg (compilers %)               0      ←！
      system CPU avg (editor + helpers %)        14
      system CPU avg (third-party security %)    2
      system CPU avg (other %)                   79
```

`compilers 0%` 是采样形式的缺陷，不是编译器没吃 CPU：
**1 s 窗口 + 「同一 PID 在相邻两次快照都存活」的差值口径，会把短命进程整个漏掉**：
`gcc→cc1→as` 单条链只活 0.2~1 s，两次快照几乎不重叠 ⇒ 差值恒为 0。
实测复现：60 个单元 / 5 s 编完 ⇒ 编译器 0%；24 个重文件 / 单元 5 s ⇒ 编译器 67%。

修正为**双速率采样**：

| 窗口 | 周期 | 内容 | 用途 |
| --- | --- | --- | --- |
| `C`（编译器） | 250 ms | `gcc* / *-gcc / cc1* / as / *-as / ld / *-ld / collect2 / ccache / make / clang*` | 抓住 0.2~1 s 的短命进程 |
| `S`（常驻） | 2 s | 整机 `PerformanceCounter` + `Code*` + 已知安全软件 + `__self` | 归因编辑器与安全软件 |

两类窗口各自归一（否则 250 ms 窗口会被 2 s 窗口稀释）后相加。修正后实测：
`total 92%` / `compilers 34%` / `editor 7%` / `security 1%` / `other 49%`（其中 `other` = 其它程序 + 系统，
标签已从「其它」改为「其它程序 + 系统」，不再让人以为是扩展自己）。

另新增**实测饱和归因**（总占 ≥85% 且 编辑器+杀软 ≤40% 时输出）：直接告知
「满 CPU 是本次构建的编译器工具链（剩余 X%），不是编辑器空转」，并给出
`parallelJobs` 取舍建议 —— 避免把「pu 100%」当成故障反复排查。

### 4.8 第八轮：真实命令行到手，以及采样诊断再加码

用户开启 profile 后拿到了慢单元的完整命令行（节选）：

```
riscv32-elf-gcc.exe -Os -Wall -march=rv32imacxbs1 -ffunction-sections -msave-restore
  -mjump-tables-in-text -I. -Idisplay -Imessage -Iport -Iplugin
  -I..\..\platform\header -I..\..\platform\libs -I..\..\platform\bsp
  -I..\..\platform\functions -I..\..\platform\gui
  -c ...\ab_gatt_app.c -o Output\obj\platform\app\ab_gatt_app.o
```

关键信息：开关集合只有 `-Os -Wall -march=rv32imacxbs1 -ffunction-sections -msave-restore
-mjump-tables-in-text` + 10 个 `-I`，**无 `-g` / 无 `-O2` / 无额外 `-D`**，与 Code::Blocks 从同一 `.cbp`
生成的命令行应当一致；`-march=rv32imacxbs1` 是厂商自定义扩展（`xbs1`）。
也就是说单元 2.5~4.8 s 的墙钟是工具链在 `-Os` + 自定义扩展下的真实开销。

本轮数据：`Compiled 56 files (25.2s)`、`Total 40.6 s`、`dispatch wait 3 ms`、
`host output parsing 1 ms`、`system total 91%`、`editor 11%`、`security 2%`、
`post-build 12.2 s`（脚本里的 `C:\upload\upload.bat` 网络上传，不是编译）。

但 `system CPU avg (compilers %)` 仍然只有 **1%**（而 `compiler samples 66`、性能实验里
同一机器能采到 60%+ —— 说明不是命令行或名字的问题，而是真实构建下的采样行为差异）。
为此再加三个诊断计数，直接区分三种可能：

| 计数 | 含义 | 为 0 时说明 |
| --- | --- | --- |
| `system compiler samples with matches` | `Get-Process -Name` 命中了进程的窗口数 | 名字没匹配上（工具链进程名异常） |
| `system compiler samples with data` | 窗口里真的算出了 CPU 差值 | 命中了但差值恒为 0（进程太短 / 句柄读不到） |
| `system compiler max matched processes` | 单窗口最多命中数 | 应接近并发数（8） |

三个数字能直接定位剩余的不一致，不再靠猜。

### 4.9 最终归一：不再猜「编译器占多少」，只报「可归因」的三项

双速率（250 ms）采样虽然能抓到 `cc1`，但它自身要吃 ~0.1 个核、且在真实构建里
仍会因为“窗口内同一 PID 才作差”而得到 1%~34% 不同结果（同一机器、同一工具链）。
它不值得占那个 CPU，也不应该给出不可解释的数字。于是收敏为：

| [profile] 行 | 含义 | 怎么用 |
| --- | --- | --- |
| `system CPU avg (total %)` | 整机利用率（`PerformanceCounter`，任务管理器口径） | 判断是否真的满载 |
| `system CPU avg (editor + helpers %)` | VS Code / 扩展宿主占用 | **判断扩展自身是否在空转**（97% 里只有 11~14%） |
| `system CPU avg (third-party security %)` | 已知安全软件占用 | >10% 会点名告警 |
| `system CPU avg (toolchain + other apps + system %)` | 剩余部分 | 满载时它就是编译工具链 + 其它程序 |

采样开销回到 ~0.06 核（1 s 窗口），且不再出现「编译器 0%/1%/34%」这种无法解释的数字。

实测结论（用户机器，两次构建）：`total 91~97%` / `editor 11~14%` / `security 2%` /
`dispatch wait 3 ms` / `host output parsing 1~4 ms` / `Compiled 56 files (25~32 s)`。
即：**CPU 满载来自本次构建的编译工具链（`-Os` + `-march=rv32imacxbs1` 共 56 个单元），
扩展本身开销已在 5 ms 量级，不存在「扩展空转导致 CPU 100%」。**

## 5. 决定性实测：慢的是「工作区内写文件触发的 VS Code 索引风暴」，不是编译器

用户给出的反证：**同一个 `.cbp` 用 Code::Blocks 做全量 Rebuild，CPU 峰值 ≤5% 而且更快**；
换到 4 核主机、32 核主机（无杀毒、内存充裕、系统 CPU 只用 20%）同样是「一编译就打满 100%，
越满越慢」。如果编译本身真有那么贵，32 核主机不可能被打满，CPU 占用也不可能与核数无关。
本轮在**用户机器**上、用**用户日志里的原样命令行**做了五组对照。

### 5.1 同一条 gcc 命令，扩展外只要 136~168 ms

命令行逐字取自扩展自己的慢单元诊断
（`Slow compile unit (4602 ms): ... riscv32-elf-gcc.exe -c app/platform/app/ab_gatt_app.c ...`），
工具链 `C:\Program Files (x86)\RV32-Toolchain\RV32-V3\bin\riscv32-elf-gcc.exe`，
开关原样照抄（`-c -Os -Wall -march=rv32imacxbs1 -ffunction-sections -msave-restore -mjump-tables-in-text`
+ `.cbp` 里的 11 个 `-I`）：

| 执行方式 | 墙钟 |
| --- | --- |
| PowerShell 直接执行同一条命令（4 次） | **274 / 136 / 168 ms**、`Process.Start` 复核 168 / 145 / 136 / 148 ms |
| 扩展内同一文件（`Slow compile unit`） | **3.0 ~ 5.5 s** |

而且它自己几乎不吃 CPU：`Process.TotalProcessorTime` 单次只有 **16~31 ms**。

### 5.2 派生参数不是原因（10 种 spawn 变体）

| 变体 | 墙钟 |
| --- | --- |
| A 纯 `spawn(argv, no options)` | 173 ms |
| B `windowsHide:false` | 124 ms |
| C 显式 `env` | 138 ms |
| D `os.setPriority(BELOW_NORMAL)` | 156 ms |
| E `detached:true` | 176 ms |
| F `stdio:'ignore'` | 138 ms |
| G `env` + 降级 | 146 ms |
| A2 / D2 / C2（重复） | 138 / 166 / 129 ms |

全部落在 124~176 ms。`windowsHide`、`env`、优先级降级、`detached`、`stdio` 都与延迟无关，
「扩展的派生方式有问题」这一假设排除。

### 5.3 真正的分水岭：扩展内外差了 20 倍，而多出来的 CPU 不是编译

| 实验 | 墙钟 | 进程 CPU | 整机 CPU |
| --- | --- | --- | --- |
| 单次 `Process.Start`（直接派生）× 4 | **168 / 145 / 136 / 148 ms** | 31 / 16 / 31 / 16 ms | — |
| 30 次串行循环（平均） | **175 ms/文件** | — | **avg 22.9% / max 41.3%**（8 逻辑核） |
| 输出改写 `C:\temp`（3 轮） | 388 / 1505 / 1535 ms | — | — |
| 输出写工程目录 `E:`（3 轮） | 1534 / 1555 / 2052 ms | — | — |
| 扩展内同一文件 | **3000 ~ 5500 ms** | — | — |

三条结论：

1. **编译本身很轻**：单文件 136~175 ms、进程 CPU 只有 16~31 ms；30 次串行才把整机拉到平均 22.9%
   （约 1.8 核）。56 个单元全部重编，CPU 总账也只有 **15~20 CPU 秒**。
2. 「写 `C:` 快、写 `E:` 慢」的差异在本轮重测中**消失**（两边都是 1.5 s，是机器瞬间负载噪声），
   所以**不能归因于磁盘或磁盘类型**。
3. 扩展内 3~5.5 s vs 扩展外 0.14~0.18 s：**同一个可执行文件、同一条参数、同一个目标目录**，
   差别只能来自「它被谁围着跑」——即 VS Code 对「工作区内新增文件」的反应。

关键校验：扩展内 56 个单元、构建期整机 27~32 s 满载（约 **210 CPU 秒**），
而编译器链只需 15~20 CPU 秒 —— **多出来的 ~190 CPU 秒不是编译**。
同时 `editor + helpers` 只有 11~14%、`third-party security` 只有 2%，这两组都没吃掉它。
剩下的只能是旧口径里被归进「其它」的 **`rg.exe` + `conhost.exe` 风暴**：
它们不是 `Code.exe`，但在任务管理器里显示为「Visual Studio Code」这一组的子进程。

### 5.4 风暴规模：`rg` 峰值 281、`conhost` 峰值 282，排除后为 0

| 观测 | 数值 |
| --- | --- |
| 全量枚举型 `rg.exe` 峰值（隔离实验，加排除前） | **281** 个进程 |
| 同时存在的 `conhost.exe` 峰值 | **282** 个 |
| 加上 `files.watcherExclude` 后峰值 | **0** |
| 卸载全部第三方扩展后 | **仍然出现 rg**（VS Code 核心行为） |
| 扩展内 56 文件 | 25~32 s（≈2.2 文件/s），基线 175 ms/文件 |

Code::Blocks 是裸的原生程序：没有文件监视器、没有搜索索引、不派生子进程解析输出，
所以它编同一个工程 **≤5% CPU**。这不是「Code::Blocks 的编译器更快」，
而是「VS Code 在构建写入大量文件时被自己的索引/监视机制反噬」。

### 5.5 采样口径补一组：把 `rg` / `conhost` 单列为「VS Code 文件扫描器」

旧口径只把 `Code.exe` 归为 editor、把已知杀软归为 security，剩下的都算 other。
而风暴里的 `rg.exe`/`conhost.exe` 正好落在 other 里，于是报表长成
`editor 11%` + `security 2%` + `other 79%`，看起来像「编译器真的吃了 79%」，把真凶掩盖了。

现在新增第四组：

| [profile] 行 | 含义 |
| --- | --- |
| `system CPU avg (VS Code file scanner %)` | `rg.exe` + `conhost.exe`（构建写文件 → 全工作区枚举的直接证据） |
| 文本模式同名一行 | 只开 `sampleSystem`、不开 `profile` 时输出 |

并新增对应告警：扫描器 ≥ 8% 时点名提示「启用 `autoExcludeOutputs` 并重载窗口」；
`CPU was saturated` 定位消息也同步列出四个分组，不再把扫描器算进编译器。

### 5.6 本轮据此做的产品化改动

| 改动 | 设置 | 默认 | 作用 |
| --- | --- | --- | --- |
| 构建前自动把产物目录写进 `files.watcherExclude` + `search.exclude` | `codeblocks.build.autoExcludeOutputs` | **开** | 直接把 5.4 的放大器关掉（实测 rg 峰值 281→0）；首次真添加时提示一次并可「重载窗口」 |
| 产物目录推导覆盖默认 `.objs` / `.deps` | 同上 | 开 | `object_output` / `deps_output` 为空时 Code::Blocks 默认写 `.objs` / `.deps`；这两个目录同样在工程内，必须排除（实测 800 文件构建时 `.objs` 会写入 800+ 个目标文件/响应文件） |
| 路径宏展开后再排除 | 同上 | 开 | `output` / `object_output` 里的 `$(PROJECT_DIR)` 等宏先展开，避免生成 `**/$(TARGET_OBJECT_DIR)/**` 这种无效 glob |
| 打开工程即静默预排除（不弹窗） | 同上 | 开 | 历史产物目录里的 `.o/.d` 在启动扫描时同样会触发枚举 |
| 全部构建/清理入口统一先排除 | 同上 | 开 | Build / Build Workspace / Clean / Clean Workspace / 右键单工程 Build / 单文件编译 / Rebuild All；单工程与单文件路径不经过主 Build 命令，最容易漏（清理会批量删除产物，同样触发枚举） |
| 取消编译器降级 | `codeblocks.build.lowerCompilerPriority` | **关**（原为开） | 编译只吃 16~31 ms CPU，降优先级只会让它在被抢 CPU 时更饿 |
| 系统 CPU 采样不再跟随 `profile` 自动开启 | `codeblocks.build.sampleSystem` | **关** | 采样器自身有开销，诊断够用时不该反过来拖慢构建 |
| 慢单元诊断 | `codeblocks.build.profile` | 关 | 单单元 ≥3 s 时打印**完整命令行**（前 3 个），便于像 5.1 那样拿原样命令做对照 |

### 5.7 给用户的可执行结论

1. **升级到本版本并重载窗口**：产物目录会被自动排除，这是收益最大的一步；
2. 若仍看到 `rg.exe`/`conhost.exe` 成百上千，说明还有别的扩展在工作区里反复调用
   `workspace.findFiles`，可用 `codeblocks.workspaceScanReport` 定位；
3. `codeblocks.build.parallelJobs` 保持 8（4 路实测更慢：43.3 s vs 27.2 s）；
4. 复测时开 `codeblocks.build.sampleSystem` + `codeblocks.build.profile`，
   看 `system CPU avg (VS Code file scanner %)`：它应当接近 0；`dispatch wait` 应 <10 ms；
5. 若换到干净工作区后仍然慢，用 `Slow compile unit` 打出的完整命令行做 5.1 式对照（扩展外直接跑一遍）。
