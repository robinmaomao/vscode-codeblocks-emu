> 增量编译识别 `.ld` 等编译相关文件改动（保护性增强）：工程内 `.ld` / `.lds` / `.icf` / `.def` / `.xm` 等非编译文件改动后，自动重链接 / 重新打包。

## 背景（问题）

- 工程内 `.ld`（链接脚本）等文件不产生对象文件，不参与对象时间戳比对；此前只有目标属性 `external_deps` 能让它触发重链接。
- 实验复现（真实 gcc）：`main.c` + `start.S` + `custom.ld` 工程，二者均已编译且输出存在时：
  - 改 `.S` 自身 → 重编译 ✓（已有）
  - 改 `.S` 的 `#include` 头文件 → 重编译 ✓（已有）
  - **改 `custom.ld`（未配 external_deps）→ `Nothing to be done` ✗（本次修复）**
  - 改 `custom.ld`（已配 external_deps）→ 重链接 ✓（已有逃生通道）

## CB 取证

- CB 链接新鲜度只有两路：对象时间戳（`directcommands.cpp:819-833`：`objtime > outputtime → force`）与外部依赖（`AreExternalDepsOutdated` `directcommands.cpp:1007-1140`：库 `:1022-1084`、`external_deps`/`additional_output` `:1087-1140`）。
- "Nothing to be done (all items are up-to-date)." 由 `compilergcc.cpp:4131` 输出。

## 修复（保护性增强）

- 新设置 **`codeblocks.build.linkInputExtensions`**（数组，默认 `["ld","lds","icf","def","xm"]`；设 `[]` 关闭，恢复 CB 1:1 行为）：

# 0.8.98-dev

> 修复 clangd 跨界 typedef 冲突误报：嵌入式 SDK 头文件与工具链系统头对 `__int32_t` 等类型的定义不一致时，
> clangd 报 `redefinition_different_typedef`（GCC 能编过）——现**默认压制**。

## 问题

- **现象**（clangd 诊断）：
  `In included file: typedef redefinition with different types ('__int32_t' (aka 'int') vs 'long')`，
  代码 `clang(redefinition_different_typedef)`；`_stdint.h(44,19)` 报错处、`typedef.h(11,26)` 为先前定义。
- **根因**：嵌入式 SDK 头文件（`typedef.h`）与工具链系统头（`_stdint.h`）对 `__int32_t` 的类型定义不同
  （`long` vs `int`）；GCC 因预处理宏/包含顺序不触发，clang（clangd 内置前端）按字面判定为不同 typedef 重定义。
  属**跨工具链解析差异导致的误报**，与用户代码无关。

## 修复

- clangd 用户配置生成（`src/tools/clangd.ts` → `Diagnostics.Suppress`）默认新增压制项 **`redefinition_different_typedef`**：
  `codeblocks.clangd.suppressedWarnings` 默认值 → `["-Wunused-function", "redefinition_different_typedef"]`
  （`package.json` 与 `src/extension.ts` 两处同步）。
  - **语义核实**（clangd 官方文档 + 源码 `Diagnostics.cpp`）：`Suppress` 匹配前会对 `err_`/`-W` 前缀做规范化，
    因此写诊断名（`redefinition_different_typedef`）或 clang 内部名（`err_redefinition_different_typedef`）等价；
    **错误级诊断同样生效**（在 `HandleDiagnostic` 阶段置为 Ignored，不再发布）。
  - **恢复显示**：从设置 `codeblocks.clangd.suppressedWarnings` 移除 `redefinition_different_typedef` 后重新执行
    `Code::Blocks: Generate compile_commands.json…`（clangd 会自动重载配置，无需重启）。
- **顺带健壮性**：`updateClangdUserConfig([])`（空作用域调用）不再留下悬空 `---` 分隔符。
- **打包修复**：`.vscodeignore` 增 `.cb-tools/**`——临时/审计脚本移入子目录后，裸模式 `.cb-*.js` 不再匹配嵌套路径（vsce 行为），此前会被误打进 VSIX（本次实装 16 文件已排除）。

## 背景（响应文件是什么）

- 链接 / 编译命令行超过阈值时，扩展对齐 Code::Blocks `CheckForToLongCommandLine`（`directcommands.cpp:200-260`）
  把命令末尾参数（通常是对象列表）写入响应文件，命令改为 `@"<respFile>"`（gcc 从 `@file` 读参数）：
  - 生成位置：链接 / 打包 `<对象目录>/<目标名>_link.respFile`；编译 `<对象目录>/<源文件名>.respFile`
  - 阈值：`safe` 默认 **8000**（为 cmd.exe 8191 上限留余量）/ `cb` 模式 **32767**（对齐 CB）
- Code::Blocks 自身**从不删除**响应文件（全源码仅创建逻辑）；扩展此前同样保留、Clean 也不清理。

## 修复 A：目录对齐（`objectOutput` 为空 → `.objs`）

- **问题**：`.cbp` 未设置 `object_output` 时（parser 默认空串，`parser.ts:440`），对象文件会正确落到 `.objs/`，
  但链接 / 打包的响应文件此前直接用空目录字符串 → `path.join(工程根, '', 'Debug_link')` →
  **落到工程根目录** `Debug_link.respFile`（与 CB 不一致，也是"构建后工程里冒出一个不认识的文件"的常见来源）。
- **修复**：新增 `linkRespBase()`（`src/build/commandLine.ts`），空值 → `.objs`
  （对齐 `CompileTargetBase::GetObjectOutput` 的空值默认，`compiletargetbase.cpp:203-216`）；
  `buildEngine` 链接（`:1017`）与静态库打包（`:1115`）两处接入。

## 功能 B（新设置，默认关）：`codeblocks.build.cleanResponseFiles`

- Clean / Rebuild 时**递归删除目标对象目录下的 `*.respFile`**（含嵌套的编译响应文件），数量计入 Clean 汇总（详细模式逐条列出）；
- **默认 false**：Code::Blocks 不清理响应文件，默认关闭保持对齐；开启后避免旧响应文件永久遗留。
- 说明：响应文件是随时可安全删除的临时输入（需要时会自动重新生成）。
