## 0.8.4

> 发布日期：2026-09-23

## 修复：文件类型判定对齐 Code::Blocks（`FileTypeOf`）

此前扩展用硬编码正则 `isCompilable()` 过滤「可编译文件」，只识别 `.c/.cpp/.cc/.cxx/.rc`，导致：

- **汇编源文件（`.S` / `.s` / `.asm` / `.ss` / `.s62`）被跳过**：例如 RISC-V 工程的启动/复位向量 `reset.S` 未被汇编、未参与链接，最终链接产物缺少 `reset.o`，二进制内容错误（链接日志只有 `main.o`，却显示「构建成功」的假象）。
- **链接脚本（`.ld`）与自定义构建命令语义不符**：`<Option compile="1"/>` + `<Option compiler="..." use="1" buildCommand=" "/>` 的 no-op 自定义命令未被按 Code::Blocks 语义识别（此前对 `buildCommand` 做了 `trim()`，`" "` 被误判为空）。

## 改动

- 新增 `src/model/fileTypes.ts`：`FileTypeOf` 等价实现（`FileType` 枚举 + `fileTypeOf()` + `isCompilableFileType()` + `isLinkableFileType()` + `isCppSource()` + `isClangdIndexable()` + `defaultCompilerVar()`），对齐 `codeblocks-src/src/sdk/globals.cpp`。
- `src/model/parser.ts`：`parseUnits` 按文件类型计算 `compile/link` 默认值（源/资源可编译；源/资源/对象/资源 bin/静态库可链接），`compilerVar` 按扩展名分配（`.c`→CC、Windows `.rc`→WINDRES、其余→CPP）；解析 `<Option use="1">`（缺省不启用，不 trim）。
- `src/build/buildEngine.ts`：编译与链接分两遍收集（对齐 `GetProjectFilesSortedByWeight`）；资源文件走 `CompileResourceCmd`（windres）、其余走 `CompileObjectCmd`；自定义命令展开后 `trim()` 为空则不执行（对齐 `AddCommandsToArray`）；`isClangdIndexable` 保持只索引 C/C++。
- `src/model/types.ts`：`customBuildCommands` 类型由 `Record<string,string>` 改为 `Record<string,{command,use}>`。
- `src/compiler/commandGenerator.ts`：汇编扩展名（`.s/.asm/.ss/.s62`）优先归 C 编译器（无论 `compilerVar`），避免 g++ 汇编/链接带入 C++ 运行库。

## 验证

- `npx.cmd tsc -p ./` 编译通过。
- 端到端模拟：`reset.S` 用 `riscv32-elf-gcc -c ... -o reset.o` 汇编并进入链接对象；`ram.ld` 归类为 `compile=true/link=false` 的自定义 no-op（不执行、不链接）；头文件默认 `compile=false/link=false`。

## 0.8.14-dev

> 发布日期：2026-09-24

## 新增：文件自定义构建命令右键快捷入口

工程树文件节点新增右键菜单「Edit Custom Build Command...」，可快速编辑该文件的 `<Option compiler buildCommand>` 自定义构建命令（留空则删除），写回 `.cbp`。此前只能通过工程属性面板「文件」页编辑，多行命令仍建议使用面板。

- 新增命令 `codeblocks.editFileBuildCommand`（`view/item/context`，`viewItem =~ /^file/`，位于 Compile File / Link File 之后）。
- 复用 `serializeProject` 全量写回路径，与面板保存行为一致；编辑后 `use="1"` 启用。

## 性能优化：三大缓存（大工程提速）

针对大工程（成百上千源文件、深层目录树）做三项缓存，均遵循「每次构建/解析新建实例 → 缓存必须模块级」原则。

- **include 依赖缓存（buildEngine.ts）**：`#include` 头文件依赖扫描结果跨构建复用，按「源文件 mtime + size + include 搜索目录」失效，避免每次增量判断重复读文件 + 正则扫描。
- **工程树懒加载（projectTreeProvider.ts）**：目录索引 `DirIndex`（`dirKey → 直接文件 / 直接子目录`）+ 目录/分组节点按需展开（`childrenLoaded` 缓存），项目节点展开只构建顶层骨架，深层目录与文件在展开时按索引生成；空虚拟文件夹照常显示。
- **XML 解析缓存（parser.ts）**：`.cbp`/`.workspace` 的 `readFile + fast-xml-parser` 结果按「绝对路径 + mtime + size」复用（`ProjectParser` 与 `WorkspaceParser` 配置不同，各自独立缓存）。

## 缓存健壮性（复查优化）

- **盘符归一化**：所有缓存 key 经 `upperDrive()` 归一化（`e:\` → `E:\`），同一文件以不同大小写盘符访问时命中同一缓存条目。
- **LRU 容量上限**：新增 `src/tools/lru.ts` `LruCache`（命中移动 + 超容量淘汰最久未用），防止缓存无界增长；`depsIncludeCache` 容量 2000、解析缓存各 128、目录索引 256。

## 验证

- `npx.cmd tsc -p ./` 编译通过。
- 全量回归 **29 个测试通过**（新增 `test-deps-cache.js` include 缓存失效、`test-tree-lazy.js`/`test-tree-lazy2.js` 懒加载树结构、`test-parse-cache.js` 解析缓存、`test-lru.js` LRU 语义）。

## 0.8.17-dev

> 发布日期：2026-09-25

## 修复：pre/post build 命令宏展开（用户 SDK 构建失败）

本轮修复了三处导致真实 SDK 工程（BT9000）与 Code::Blocks 编译结果不一致的问题：

### 1. `$(PROJECT_DIR)` 结尾分隔符缺失

- **症状**：pre-build 命令 `$(PROJECT_DIR)output\bin\...` 展开为 `...\boomboxoutput\...`（路径拼接错误，`cc1.exe` 报 `No such file or directory`）。
- **根因**：`$(PROJECT_DIR)` 在 `commandGenerator.ts` 的 `renderTemplate` 第 9 步 `expandBuildVars` 展开（对应 `compilercommandgenerator.cpp:579 ReplaceMacros`），此前值无结尾分隔符。
- **修复**：对齐 Code::Blocks `GetBasePath()`（`wxPATH_GET_SEPARATOR`）+ `UnixFilename`，展开为带结尾 `/` 的正斜杠路径。

### 2. `$compiler`/`$options`/`$includes` 在 pre-build 中未展开

- **症状**：`'$compiler' 不是内部或外部命令`。
- **修复**：pre/post build 命令先经 `expandScriptMacros`（`generateFromTemplate`，对齐 `directcommands.cpp GetPreBuildCommands` 的 `GenerateCommandLine` 调用）。

### 3. 链接对象遗漏自定义编译命令的 `.c` 文件

- **症状**：链接报 17 个 `undefined reference to music_pre_eq_effect_update_callback` 等（定义在带 `buildCommand` 的 `toolkit_effect.c`）。
- **根因**：链接收集曾把所有自定义 buildCommand 文件一刀切排除；Code::Blocks `GetProjectFilesSortedByWeight(target,false,true)` 只按 `link` 属性过滤（默认值由文件类型决定）。
- **修复**：只保留 `link` + 文件类型过滤，`toolkit_effect.o` 正常参与链接。

## 修复：post-build 顺序与条件对齐

- post-build 执行顺序改为 **目标级 → 项目级**（对齐 `bsTargetPostBuild → bsProjectPostBuild` 状态机）。
- 实现 `alwaysRunPostBuildSteps`（`<ExtraCommands><Mode after="always">`）条件：目标已最新时仅当标志为真才执行 post-build。

## 编译/链接七项全面对齐

| # | 修复项 | 说明 |

| 1 | 编译命令 PATH 注入 | 编译/链接子进程 PATH 前置工具链 bin 目录（对齐 Code::Blocks Init 的 PATH 重构，MSVC 等依赖 PATH 的工具链受益） |

## 0.8.19-dev

> 发布日期：2026-09-25

## 新增：generatedFiles 自动生成文件机制（A4）

对齐 Code::Blocks `cbProject::AddFile` 的 GenFilesHackMap 机制（`cbproject.cpp:815-978`）：

- **关系来源**：生成关系不写在 `.cbp`，由编译器 XML 的 `gen="file1;file2"` 属性声明（对应 CompileObject/CompileResource 工具，按扩展名匹配）。
- **加载建立**：打开项目时按声明自动建立「生成器 → 生成文件」关系，生成文件加入项目与目标（继承目标归属与默认 compile/link）。
- **宏展开**：生成名支持 `$file_name` / `$file_basename` / `$file_dir` / `$file_ext` / `$file`。
- **构建顺序**：生成器文件先编译，生成文件延后到常规编译完成后（生成器先产出源文件）。
- **对象命名**：生成器文件的对象 = 第一个生成文件的对象（对齐 `pfDetails::Update`）。
- **clean**：自动生成文件在 clean 时额外删除本体（对齐 `GetTargetCleanCommands`）。
- **保存**：`.cbp` 序列化时跳过自动生成文件（对齐 `projectloader.cpp:1794`）。

> GCC 默认工具链无 `gen` 声明，该机制仅在编译器 XML 声明了 `gen` 属性时激活（如 Qt uic/moc 场景）。
