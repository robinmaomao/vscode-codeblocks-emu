# 0.8.141

> 发布日期：2026-11-06 ｜ 正式版（0.8.140 → 0.8.141 里程碑汇总）
> **主题**：打开工程后 clangd 不分析 + 编译错误不自动跳转
> 测试结果见 [测试报告](../testing/test-report-0.8.142-archive.md)（滚动更新）；
> 对齐依据见 [对齐对照.md](../guide/alignment.md)。

本版修复两个现场反馈的问题：

1. 工作区自动检测到 `.cbp` 后**关掉弹窗**，再从状态栏「Code::Blocks projects」入口打开工程 → clangd 不分析；
2. 构建失败后**不会自动跳到出错的源码位置**（`ui.buildLogFocusFirstError` 开启时也无效）。

## 1. 问题 1：clangd 不分析（根因）

生成链路本身是好的：`openProject()` → `generateClangdForWorkspace()`（150ms 去抖）→ 写
`compile_commands.json`（工作区外缓存）+ 重写用户级 `%LocalAppData%\clangd\config.yaml` 片段。
缺的是**让已经启动的 clangd 重新加载**这一环：

| # | 缺陷 | 位置（修复前） |
|---|------|----------------|
| A | 打开工程**从不**设置重启原因：`restartClangdReason` 只可能是 `'project'` / `'compiler'` ⇒ 重启判定整段短路 | `openProject()` 末尾 |
| B | 唯一的"切换活动工程"重启触发点受 `codeblocks.clangd.restartOnActiveProjectSwitch` 控制（现场该设置为 `false`） | 重启判定 |
| C | 门槛 `hasOpenSourceFile()`：从状态栏打开工程时通常没有可见的 `.c/.h` 编辑器 ⇒ 即使 A/B 都满足也不重启 | `hasOpenSourceFile()` |

典型后果：上一会话残留的 clangd 进程按旧配置（甚至"没有编译数据库"）继续工作，`config.yaml` 与数据库
虽已刷新却没有重新初始化 —— 表现就是"没有触发 clangd 的分析"。

## 2. 问题 1：修复

- 新增重启原因 **`'open'`**：`openProject()`（新打开、以及"已打开再次打开刷新配置"两条路径）均置位；
  `'open'` 与 `'compiler'` 一样**不受** `restartOnActiveProjectSwitch` 限制（打开动作本身就是"让它开始按本工程分析"）。
- 触发条件从「数据库变化（`!skipped`）」扩展为「**数据库或配置片段**有变化」
  （`updateClangdUserConfig()` 的 `written` 结果现在参与判定）；两者都没变时仍然什么都不做（避免无谓整库重索引）。
- 门槛从 `hasOpenSourceFile()` 扩展为 **`clangdExtensionActive() || hasOpenSourceFile()`**：语言服务器已在跑
  （`llvm-vs-code-extensions.vscode-clangd` 处于激活态）时重启才有意义；没跑时无需唤醒，下次打开源文件会自然
  读到新配置。
- 可观测性：输出通道新增原因行「已打开工程，重启 clangd 以套用新的编译数据库 / 配置」；新增命令
  **`Code::Blocks: Restart clangd Language Server`**（菜单 `Code::Blocks → Settings`），便于现场一键验证。

## 3. 问题 2：不跳转（根因）

`buildLogTreeProvider.gotoError()` 通过命令参数传定位：

```ts
vscode.commands.executeCommand('vscode.open', vscode.Uri.file(d.file), { selection: range, preview: true });
```

`vscode.Range` 在扩展宿主里 `toJSON()` 返回 **`[start, end]`**（`Position` → `{ line, character }`），命令参数跨
进程走 JSON 序列化 ⇒ 主进程收到的 `options.selection` **不是 `IRange`**（应为 `{ start: { lineNumber, column } }`）。
结果：**文件被打开、定位被丢弃**；目标文件本来就打开时表现为"构建失败了，但没跳到错误处"。

同类缺陷还有两处：Build Log 树节点的 `command.arguments`（`[Uri, { selection: Range }]`）与 Symbols 视图节点。

## 4. 问题 2：修复

- 新增 [`src/ui/openLocation.ts`](../../src/ui/openLocation.ts)：`openFileAtLocation()` =
  `openTextDocument` → `showTextDocument({ preview, selection })` → `revealRange(InCenter)`
  （与仓库内的 `bookmarkGoto` / `locateInCbp` 同一套已验证做法；行/列越界自动钳制）。
- 新增内部命令 **`codeblocks.openLocation`**（参数为纯标量 `{ file, line, column }`，不进命令面板）：
  - Build Log 诊断节点、Symbols 节点改为该命令；
  - `gotoFirstError` / `gotoNextError` / `gotoPreviousError` 改为 `async`，逐条尝试并在失败时**继续找下一条**，
    全失败才返回 `undefined`；
  - `finishBuildSummary()` 改为 `async`：先 `await` 面板聚焦命令（`codeblocks.buildLog.focus` 现在返回内部
    命令的 Promise，消除"面板抢回焦点"的竞争），再跳转，并在输出通道留痕
    「已跳转到首个错误：`<file>:<line>:<col>`」/「首个错误没有可跳转的源码位置」。
- 导航列表过滤链接期伪文件（`ld.exe` / `ld64` / `lld` / `collect2.exe` / `link.exe` / `cl.exe`）：它们没有源码
  位置，跳过去必然失败（修复前会占用"首个错误"名额，导致整次跳转静默失败）。树视图仍照常显示这些错误。

## 6. 影响面与兼容性

- 无新增设置、无设置默认值变更；`codeblocks.clangd.restartOnActiveProjectSwitch` 语义不变（仍只作用于"切换活动工程"）。
- 行为差异：打开工程时若数据库/配置有变化且 clangd 正在运行 → 会多一次 `clangd.restart`（整库重索引的 CPU 峰值
  会出现在打开工程后，而不是"永远不重建"）。构建进行中仍走原有的"推迟到构建结束"路径。
- 跳转行为差异：错误定位由扩展显式 `revealRange`，不再依赖 `vscode.open` 的 options 序列化；链接期错误不再
  占用"首个错误"名额。
