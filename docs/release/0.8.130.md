# 0.8.130

> 发布日期：2026-10-13 ｜ 正式版（0.8.129 → 0.8.130 里程碑汇总）

## 概述

0.8.129 发布后的迭代（构建观感 / CPU 占用收口 + post-build 可观测性 + clangd 补全与配置治理）汇入 main，并以本正式版收束。产品行为变更五处：**post-build 脚本输出实时流式 + 长命令心跳 + 可选超时**（新增设置 `codeblocks.build.scriptCommandTimeoutMs`）、**post-build 宽限改「安静期 + 上限」**、**并行编译上限 64 → 32**、**Problems 诊断批量发布**、**clangd 补全不自动插入头文件 / clangd 配置治理**（新增 12 项 `codeblocks.clangd.*` 设置与 2 条命令）；其余为测试与 CI 稳定性、文档同步。

- **post-build 观感与阻塞治理（本版新增）**：脚本 stdout/stderr **实时流式**写入构建日志（不再等命令结束才回放，卡住期间不再「一片空白」）；长命令每 5s 输出「仍在运行 (x s)」心跳行（首条附排障提示）；新增可选超时 `codeblocks.build.scriptCommandTimeoutMs`（默认 `0` = 不超时，对齐 CB 无限等待；超时强杀进程树并记失败），用于脚本内网络盘（SMB）重连、上传服务（.NET 默认 100s 超时）等阻塞场景；杀树按「运行期采集进程树 PID + 超时后多轮收割」加固。
- **构建期 CPU 与 post-build 时长再收口（本版新增）**：宽限由「固定等满 1500ms」改为**安静期（250ms）+ 上限**（基准 B11：**1891ms → 约 600ms**）；并行编译自动值上限 **64 → 32**（降低编译期 CPU 峰值）；构建期 Problems 诊断按文件归集、约 200ms 批量发布（`diagnosticCollection.set` 调用数 **4000 → 20**）。
- **clangd 补全不再自动插入头文件（本版新增）**：生成的用户级 `config.yaml` 片段固定 `Completion.HeaderInsertion: Never` —— clangd 默认 `IWYU` 会在接受补全时自动插入符号所属 `#include`；如需恢复默认请自行覆盖该片段（下次生成会被重写），或用本版新增的 `codeblocks.clangd.headerInsertion` 设置改回。
- **clangd 配置治理（本版新增）**：失效片段（项目删除/移动、历史临时目录）**每次生成配置时自动清理**、并新增手动清理命令；片段键改为**设置驱动**（留 `default`/`omit` 即不写该键，用户配置说了算）+ `extraConfig` 自由 YAML 兜底；新增 `--query-driver` 保真命令（交叉工具链内建头）。

规模（0.8.130 时点）：命令 103 → **105** 项、设置 61 → **74** 项（7 分区 + 中英 nls）、视图 5 个；分层回归 `contract 2/2`、`unit 153 脚本 FAIL=0 SKIP=1`、`e2e 4/4`、`perf 13 项 0 fail`、`pack 14 pass`。

> 上一版（0.8.129）的 post-build **脚本结束判定**（以命令本体 `exit` 为结束信号，后台进程不再拖住构建）与测试分层体系、缺陷 D-01…D-20 / C-01 收口见 [0.8.129 发布说明](./0.8.129.md)。

## post-build 观感与阻塞治理（本版新增）

- **问题**：post-build 脚本卡在外部等待（网络盘 SMB 重连 `if not exist Z:\…`、上传服务 `.NET` 默认 100s 超时）时，构建日志**一片空白**直到脚本结束——用户无法判断是「脚本/网络慢」还是「扩展卡住」。
- **根因**：输出在命令结束后才整体回放；且引擎把脚本的全部等待时间都算作 post-build 时长，没有任何可观测信号或止损手段。
- **修复**：
  - **实时流式**：stdout/stderr 边运行边逐行写入日志（缩进两空格）；
  - **心跳行**：脚本命令运行 >5s 起每 5s 输出 `[script i-N] 仍在运行 (x s)…`（首条附「网络盘/服务等待 → 可在脚本内设置超时，或点『停止构建』终止」提示）；
  - **可选超时** `codeblocks.build.scriptCommandTimeoutMs`（默认 `0` = 不超时，对齐 CB 无限等待；上限 3600000）：超时强杀整棵进程树、日志给出超时行、构建记为失败；
  - **杀树加固**：`taskkill /T /F` 是**瞬时快照**式杀树 →（a）快照之后新生的子孙会逃逸；（b）taskkill 执行前命令本体已退出时整次杀树变成空操作（实测输出「没有找到进程」）。两种情况都会让脚本继续解释后续行并启动 `start /b` 后台进程（实测杀树后 **1s / 10s** 各出现一个，且长期存活）。因此在超时启用时**运行期多次采集命令的进程树 PID**（启动 150ms 后起、每 2.5s 一次、最多 4 次；枚举用 `wmic`≈0.4s，PowerShell `Get-CimInstance` 需 ≈2.7s——快照延迟直接决定能否在中间 cmd 退出前记下它的 PID；`wmic` 缺装时回退 CIM），超时后按「父 PID ∈ 已终止集合」多轮（6×800ms）收割，并排除自身 PID（防 PID 复用误杀）。
- **实测**：把超时点压在「前台等待结束」附近（最易出现 kill/start 竞态）——改造前（未收割）**15 轮中 14 轮**出现逃逸残留且 8s 后仍存活；加固后 **8 组超时点 × 3 轮 = 24/24 轮**零残留。
- **语义边界**：超时 = 终止整棵命令树，**脚本启动的后台程序会一并被终止**（这是超时的定义；不设超时则沿用「命令本体结束即继续」的 CB 语义）。单元回归 `tests/test-script-runner-exit.js` 覆盖流式实时性 / 心跳 / 超时 / 进程树快照 / 孤儿收割，E2E S16 覆盖「标记行在构建返回前出现」。

## 构建期 CPU 占用与 post-build 观感再收口（本版新增）

用户反馈「编译时大量占用 CPU，两三个文件的工程也明显比 Code::Blocks 慢」「post-build 仍比 CB 卡」。三项定位与修复（只改这三处，热路径宏展开/依赖扫描保持不动）：

| 项 | 根因 | 修复 | 实测 |
| --- | --- | --- | --- |
| post-build 宽限 | `exit` 后**固定等满** `scriptExitGraceMs`（默认 1500ms）才继续 | 宽限改为**上限**：管道安静 `SCRIPT_EXIT_QUIET_MS`（250ms，轮询 25ms）即收尾；`close` 到达仍立即收尾；到期仍无安静/close 才标记 `trailingBackground` | 基准 B11 **1891ms → 约 600ms**（`grace=0` 时 6ms 无回归；持续输出场景仍受上限约束） |
| 并行并发数 | 自动值 `min(逻辑核数 × 2, 64)`，并发越高宿主 CPU 越接近 100% | 上限 **64 → 32**（`MAX_PARALLEL_JOBS`，`parallelJobs` 设置范围 0–32；显式值仍优先） | 8 线程机自动值 16 不变；高核数机器峰值并发减半 |
| Problems 诊断发布 | 每条诊断一次 `diagnosticCollection.set`：`set` 会整数组拷贝 + 跨进程提交 ⇒ O(N²) 拷贝 + N 次 IPC | 构建期按文件 URI 归集、约 200ms 节流批量发布（`DiagnosticPublisher`），构建结束统一 `finish()` 最终发布并释放定时器；`clangdDiagnosticsEnabled` 早退、`maxReportedErrors` 截断语义不变 | 4000 条 / 20 文件：**4000 次 → 20 次** `set` 调用、40.2 万 → 4000 个元素；单测 `tests/test-diagnostic-publisher.js`（21 断言，含与逐条发布的顺序等价断言） |

- 诊断批量发布的可见行为一并核对：构建期间 Problems 仍逐步刷新；构建中点「清除错误/输出」会连同**未发布**的诊断一起丢弃（`clearPending()`），避免清除后「复活」一批旧诊断。
- 回归：`tests/test-script-runner-exit.js` 扩到 **57 断言**（新增安静期提前收尾、持续输出下上限生效、尾行不丢、`grace=0` 不回归）。

## clangd 补全不自动插入头文件（本版新增）

- **问题**：接受 clangd 补全时，编辑器会自动插入符号所属 `#include`（clangd 默认 `Completion.HeaderInsertion: IWYU`）。
- **修复**：扩展生成的用户级 `%LocalAppData%\clangd\config.yaml` 片段固定 `Completion.HeaderInsertion: Never`；本版起该键也由设置 `codeblocks.clangd.headerInsertion` 驱动（默认 `never` = 现状，留 `omit` 让位给用户自己的配置）。
- **注意**：扩展写的是**用户级**配置，冲突时按 clangd 规则 user config > inner project > outer project —— 它会压过工程内 `.clangd`；要让位就把对应设置设为 `omit`。

## clangd 配置治理（本版新增）

用户反馈：本机 `%LocalAppData%\clangd\config.yaml` 里堆了 **76 个扩展片段**，其中只有 **8 个**作用域目录还存在（68 个已失效，含 66 个指向 `%TEMP%` 的历史作用域），且只有 1 个含 `Completion` 块（其余都是 HeaderInsertion 修复前的旧内容）——扩展只重写「本次打开的作用域」，历史残留无人清理。

| 项 | 现状 | 修复 |
| --- | --- | --- |
| 历史残留 | 片段永久堆积，clangd 每次都要解析 | 解析扩展标记片段（`# >>> codeblocks-vscode <hash> begin/end`）→ 每次生成配置时**顺带清理**「作用域目录或 CompilationDatabase 目录已不存在」者并在输出通道留痕；新增命令 `Clean Stale clangd Config Fragments`（先打印明细，确认后清理；同时清理扩展缓存目录里已无对应片段的孤儿 `compile_commands.json` 目录） |
| 误删风险 | — | 只动扩展标记块，用户自有内容永不触碰；**卷未挂载（未映射的网络盘 / 未插的 U 盘）与 `\\server\share` UNC 路径一律跳过** |
| 硬编码策略键 | `UnusedIncludes: None`、`HeaderInsertion: Never`、`Suppress` 写死；用户改片段下次生成被覆盖 | 策略键全部由设置驱动，**留 `default`/`omit` 就不写该键**（交给 clangd 默认值或用户自有配置）；新增 12 项设置：`unusedIncludes`、`headerInsertion`、`indexBackground`、`indexStandardLibrary`、`clangTidy`、`completionAllScopes`、`inlayHints`、`documentationCommentFormat`、`excludeDirs`、`builtinHeaders`、`queryDriver`、`extraConfig`。默认值 = 历史行为（产物逐字一致，回归断言保护） |
| 用户自由配置 | 只能手改 `config.yaml`（会被重写） | `codeblocks.clangd.extraConfig`：自由 YAML 作为**同作用域后置片段**注入（扩展自动补 `If.PathMatch`），可覆盖扩展写入的任意键；对「制表符 / `---` / 顶层 `If:`」给出提示（YAML 错误会让 clangd 丢弃整个配置文件） |
| 交叉编译器保真 | 全靠手写 `--target` + `-isystem` 迂回 | 新命令 `Configure clangd --query-driver`：按活动工程推导 `--query-driver=<编译器目录>/*`，与既有 `clangd.arguments` **合并去重**，位置三选一（工作区/用户/剪贴板）+ 预览确认；设置 `builtinHeaders=queryDriver` 让 clangd 使用交叉编译器内建头 |

- 文档明确写出 clangd 的**优先级规则**（见上节「注意」），并给出「每次只更新需要更新的键、其余交给用户配置」的用法说明（[使用说明 §9](../使用说明.md)）。
- 回归：`tests/test-clangd-config.js` 扩到 **101 断言**（片段格式/omit/extraConfig/清理与安全边界/默认产物逐字一致）；新增 `tests/test-clangd-commands.js`（17 断言：清理命令预览/确认/取消与孤儿缓存、query-driver 合并去重与三选一写入）。
