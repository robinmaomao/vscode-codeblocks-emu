# 编译产物一致性排查经验（对齐 Code::Blocks）

## 背景

两个内容完全相同的 RISC-V 工程（`CB_TEST__SDK_AB565XA3_S921` 与 `TEST_SDK_AB565XA3_S921`），Code::Blocks 编译前者、本扩展编译后者，编译产物 `app.bin`、`app.dcf`、`app.rv32`、`map.txt` 字节不一致。经排查定位并修复。

## 现象

- 两个 `.cbp` 文件 MD5 完全相同；
- 编译产物（`app.rv32` 等）MD5 不同，但**文件大小相同**（内容不同）。

## 排查步骤

1. **对比工程配置**：`Get-FileHash` 两个 `.cbp` → 一致，排除配置差异。
2. **对比产物**：`Get-FileHash` 两个 `app.rv32` → 不一致，确认是编译/链接过程差异。
3. **对比 map.txt 逐行找第一个差异**：
   ```powershell
   $a = Get-Content $cb; $b = Get-Content $ext
   for ($i=0; $i -lt [Math]::Max($a.Count,$b.Count); $i++) { if ($a[$i] -ne $b[$i]) { $firstDiff=$i; break } }
   ```
   第一个差异在第 294 行，Code::Blocks 的链接顺序是 `... func.o → func_aux.o ...`，扩展是 `... func_aux.o → func_bt_hid.o ...`——**`func.o` 被错排到后面**。
4. **定位排序差异**：对照 `directcommands.cpp` 的 `MySortProjectFilesByWeight`，发现其用 `wxString::CmpNoCase`（字节序），而我们用 JS 的 `localeCompare`。

## 根因

`compareFilesByWeight` 用了 `localeCompare`（ICU 语言环境排序），与 Code::Blocks 的 `wxString::CmpNoCase`（字节序）排序规则不同：

| 比较 | Code::Blocks（字节序） | JS `localeCompare` |
|------|----------------------|-------------------|
| `func.c` vs `func_aux.c` | `.`=0x2E < `_`=0x5F → **func.c 在前** | 忽略标点 → **func_aux.c 在前** |

实测：
```
'func.c'.localeCompare('func_aux.c')  →  1   (func.c 排后 ❌)
'func.c' < 'func_aux.c'               →  true (func.c 排前 ✅)
```

排序不同 → 链接对象顺序不同 → 内存布局/符号地址不同 → `app.rv32` 字节不同 → 派生的 `app.bin`、`app.dcf` 随之不同。

## 修复

把 `compareFilesByWeight`（`src/build/commandLine.ts`）的 `localeCompare` 改为**字节序比较**，对齐 `wxString::CmpNoCase` / `Cmp`：

```ts
export function compareFilesByWeight(a: ProjectFile, b: ProjectFile): number {
  const dw = a.weight - b.weight;
  if (dw !== 0) return dw;
  // 字节序（对齐 wxString::CmpNoCase），而非 localeCompare
  const al = a.relativeFilename.toLowerCase();
  const bl = b.relativeFilename.toLowerCase();
  if (al < bl) return -1;
  if (al > bl) return 1;
  if (a.relativeFilename < b.relativeFilename) return -1;
  if (a.relativeFilename > b.relativeFilename) return 1;
  return 0;
}
```

## 经验教训（关键）

1. **对齐 Code::Blocks 的字符串排序时，必须用字节序，禁用 `localeCompare`**。
   - `wxString::CmpNoCase` / `Cmp` 是逐字节（码点）比较。
   - JS `localeCompare` 是语言环境感知排序，会把 `.`、`_` 等标点忽略，导致排序顺序不同。
   - JS 的 `<` / `>` 对字符串是 UTF-16 码元比较，对 ASCII 路径等价于字节序。

2. **编译产物一致性的核心要素**（按重要性）：
   - 链接对象顺序（决定内存布局）
   - 编译选项顺序与内容（决定 .o 内容）
   - 对象文件路径（决定 map.txt 内容）
   - 链接器选择（gcc vs g++ vs ld）

3. **排查产物不一致的利器是 map.txt**：逐行对比找第一个差异，能直接定位是哪个对象错位/缺失，从而缩小到排序或增量判断问题。

## 编译产物一致性检查清单

对齐 Code::Blocks 时，逐项确认：

- [ ] 文件排序：weight + 字节序（非 localeCompare）
- [ ] 对象路径：相对路径 + 反斜杠（`objectPathRelative`）
- [ ] 编译/链接模板：与 `options_gcc.xml` 一致
- [ ] 选项/目录/库顺序：按 `.cbp` XML 顺序
- [ ] 链接器选择：`AutoDetect` 的 `CPP==LD` 逻辑
- [ ] 资源对象分离：`$link_resobjects`
- [ ] 静态库归档：`LinkStatic` 模板 + lib 前缀
- [ ] 自定义 buildCommand 宏展开（`$compiler $options $includes ...`）
- [ ] `$(TARGET_OBJECT_DIR)` 等宏：原值展开
- [ ] 路径分隔符：Windows 下 `$file`/`$file_dir`/对象路径用反斜杠（`toNative`）
- [ ] 盘符大小写：Windows 下绝对路径盘符大写（`upperDrive`），`spawn` 的 `cwd` 同理
- [ ] clangd 旁路：`compile_commands.json` 保持正斜杠（`nativeSep:false`）

## 路径形态差异（斜杠 / 盘符）排查经验

### 现象

`.o` / `.a` 的 debug 段（`.debug_info` / `.debug_line` / `.debug_str`）与 `map.txt` 中，路径字符串与 Code::Blocks 不一致：

1. **斜杠正反**：扩展 `D:/Users/.../main.c`，Code::Blocks `D:\Users\...\main.c`。
2. **盘符大小写**：扩展 `d:\Users\...`，Code::Blocks `D:\Users\...`。

`.code` / `.text` 段与烧录产物（`.bin` / `.dcf`）不受影响，功能完全等价。

### 根因

两类都是「路径字符串形态」差异，不是编译逻辑差异：

| 差异 | Code::Blocks | 本扩展 | 来源 |
|------|-------------|--------|------|
| 斜杠 | 反斜杠 `\`（`UnixFilename(wxPATH_NATIVE)`） | 正斜杠 `/`（`unixJoin` → `absolutePath`） | 扩展内部路径统一正斜杠，早期未在命令边界转换 |
| 盘符 | 大写 `D:`（Explorer 打开给的路径） | 小写 `d:`（VS Code 工作区 URI / `findFiles().fsPath` 盘符小写） | 两个 IDE 拿到不同大小写的输入路径，各自忠实传播 |

### 修复原则（核心）

**只改「命令字符串边界」，不动全局规范路径 `absolutePath`。**

`absolutePath` 被 clangd（`compile_commands.json`）、增量判断（`isUpToDate`）、工程树、错误跳转、调试引擎多方消费，改它 = 大面积回归。正确做法是只在 `CommandGenerator.renderTemplate` 生成命令时转换形态：

```
absolutePath（正斜杠，全局规范，不动）
  → renderTemplate: nativeSep=false 时原样（clangd 旁路）
  → 否则 toNative（/ → \）→ upperDrive（盘符大写）→ $file / $file_dir
```

### 具体修复

1. **斜杠（0.8.10）**：`commandGenerator.ts` 新增 `toNative()`（仅 win32 才 `/`→`\`）；`$file` 改用 `fname = toNative(unquote(file))`（此前误用原始 `file`，转换不生效）。clangd 旁路：`GenerateParams.nativeSep=false`，`collectCompileCommands` 显式传 false。
2. **盘符（0.8.11）**：新增 `src/tools/pathCase.ts` 的 `upperDrive()`（win32 且 `/^[a-z]:/` 才大写首字母，相对路径 / UNC 不变）；`fname = upperDrive(toNative(unquote(file)))`；`buildEngine.runSingleCommand` 与 `scriptRunner.runScriptCommand` 的 spawn `cwd: upperDrive(cwd)`。

### 经验教训

1. **debug 段的路径差异是良性噪声**：只影响 `.debug_info` / `.debug_line` / `.debug_str` 的字符串字节，不影响 `.code` / `.text`、符号表、机器码、烧录产物。功能等价，GDB 对两种写法都能处理。
2. **区分「功能字节」与「调试字节」**：产物对比先定位差异在哪个 section（`objdump -h` 或逐段对比），落在 debug 段基本可判定为路径形态问题，落在 `.text` / `.data` 才是编译逻辑 / 排序问题。
3. **盘符大小写来自 IDE 的输入路径**：VS Code 工作区 URI 盘符小写、Explorer / Code::Blocks 大写，是环境差异而非 bug。修复只需归一化盘符首字母（VS Code 只小写盘符，其余路径大小写与磁盘一致）。
4. **clangd 偏好正斜杠**：路径形态转换必须给 clangd 留旁路，否则污染 `compile_commands.json`。
5. **`DW_AT_comp_dir` = cwd**：`.a` / `.o` 里以反斜杠结尾的目录路径（如 `...\libs\platform\`）是编译时的工作目录（`spawn` 的 `cwd`），不是源文件路径；要归一化它必须改 `spawn` 的 `cwd`，只改 `$file` 不够。
